Inside the [story model](/tutorials/llm-fundamentals/#story-model), a token starts as a row of 384 numbers. That vector keeps the same width as it passes through all six blocks. Each block keeps the vector it received and adds two updates to it. Those additions let a feature from an early block reach later ones.

A network built from these blocks is a **Transformer**. The story model uses a **decoder-only** Transformer, in which each position can read its own token and earlier ones. That fits the next-token task. The last section compares this arrangement with encoders and encoder-decoders.

The two updates do different jobs. [Attention](/tutorials/llm-fundamentals/attention-and-positional-information/#token-mixing) brings in information from other positions. The **feed-forward network** works on each position separately. Both read a rescaled copy of the running vector and add their results back to it.

![Residual stream](/images/llm-fundamentals/15d-residual-stream.png)

Before the final normalization, the 384 numbers in the residual stream are the token's embedding plus 12 updates, two from each of the 6 blocks. The identity branch gives the gradient a short path through a deep stack. At each addition, the identity branch passes the incoming gradient straight through. The gradient through the sublayer is added to it, so the full gradient can still change from block to block. If each block instead replaced its input with its output, the signal would be multiplied by every block's factors on its way down, and in a stack of dozens of blocks it could shrink to almost nothing before it reached the bottom. The additive design also changes what a block has to learn. A block does not rebuild the token's representation from scratch. It only learns a small edit that improves the next-token prediction, and a block with nothing useful to add can output numbers near zero and leave the stream as it was.

The stream is also shared. Every block reads everything earlier blocks have written, so a feature that attention adds in block 2 is still there for the feed-forward network in block 5 to use. The sum has a cost too. With 12 additions, the numbers in the stream tend to grow with depth, and a sublayer tuned for small inputs would see much larger ones near the top. That is why each sublayer reads a normalized copy, while the stream itself stays unnormalized so the gradient path through it stays clean.

Once the residual stream is clear, we can ask where normalization belongs. That choice affects how the gradient travels during training. Next we can follow a token through the feed-forward network, assemble one block, and count the matrices that make up the story model's 11,015,040 parameters.

Counting the weights tells us how much memory the model needs to store them. Counting how often those weights are used gives an estimate of the arithmetic. The distinction makes it easier to see how a mixture of experts can store more weights while using only a subset for each token.

## The residual stream

The input to the second block contains the original embedding and the first block's updates. The addition that preserves this path is also what makes it possible for gradients to flow directly between blocks. A **residual connection** adds a layer's output to its input. The **residual stream** is the running vector those additions build up, and each token has its own. It runs from the **embedding** to the final layer. The embedding is the learned starting vector looked up for the token, covered in [Tokenization](/tutorials/llm-fundamentals/tokenization-and-embeddings/). It was introduced for image networks by [ResNet](https://arxiv.org/abs/1512.03385) and is used in every transformer since the original [Transformer](https://arxiv.org/abs/1706.03762).

Each block contains two **sublayers**, attention and then the feed-forward network. Treating a whole block as one update for now, block $\ell$ changes the stream by $x_{\ell} = x_{\ell-1} + F_\ell(x_{\ell-1})$, where $x_{\ell-1}$ is the stream entering, $F_\ell$ is what block $\ell$ computes from it, and $x_\ell$ is the stream leaving. The [decoder block](#the-decoder-block) section shows that a block actually makes this addition twice, once per sublayer. Unrolling the sum over all $L$ blocks gives $x_L = x_0 + F_1 + F_2 + \dots + F_L$. Each $F_\ell$ is evaluated on the stream it read, so the final vector is literally the embedding plus every contribution.

The editing route changes what a block has to learn. In a stack that replaces its input, a block with nothing useful to add must still pass everything it received through its own weights, and a freshly initialized block with random weights scrambles that information instead. In a residual stack the same block only has to output something close to zero, and the stream flows past it unchanged. A new model therefore starts close to a short path from the embedding straight to the output head, and each block learns a correction on top of what the blocks below it already wrote. The same identity path carries the training signal back down to the first block without passing through the blocks above it, and the end of this section puts a number on how much that matters for a deep stack.

The addition itself is almost free. Each sublayer adds 384 numbers into the stream, so the 12 sublayers of the [story model](/tutorials/llm-fundamentals/#story-model) spend 4,608 additions per token, about 0.02% of the 22.0 MFLOPs that the [FLOPs per token](#flops-per-token) section counts for a forward pass. The real constraint is on shape. A sum needs two vectors of the same length, so every sublayer must read a vector of width $d$ and write one back, and the stream keeps the same 384 numbers from the embedding to the last block. Anything a block wants to leave for later blocks has to fit into those numbers, alongside everything every other block has written.

Step 4 is a simplified case of the property that keeps training possible at depth. Block 3's addition was held fixed there, so the final vector moved by exactly block 2's write. In a real model the later blocks would react to the change as well, but the direct route from any block's write to the output still carries it through one for one. The loss is a single number measuring how wrong the model's predictions are. A **gradient** is the signal saying how much the loss would change if a parameter moved, and training sends it backward from the output through every layer. In a plain stack each layer multiplies the gradient by its own local slope. If the story model's 12 sublayers were stacked that way and each scaled it by 0.5, the gradient reaching the bottom would be $0.5^{12} \approx 2.4 \times 10^{-4}$ of its size at the top. A 32-block model such as Llama 2 7B has 64 sublayers, and $0.5^{64} \approx 5.4 \times 10^{-20}$. This shrinking is the **vanishing gradient** problem. With residual connections the derivative of $x_L$ with respect to any $x_\ell$ always contains a term equal to 1 from the identity path, so block 1 receives the top-level gradient undiminished plus whatever the blocks above add to it. Interpretability work often reads the stream as a shared workspace that attention moves information into and the feed-forward network writes facts into, a view developed in Anthropic's [transformer circuits framework](https://transformer-circuits.pub/2021/framework/index.html).

## Layer normalization and RMSNorm

Adding contributions block after block lets the stream's numbers drift in size, and a sublayer that sees inputs ten times larger than the ones it learned on will behave differently. **Normalization** is a rescaling step that prevents this. It takes a vector and returns a version with a standard size, so the next layer always sees inputs on a predictable scale. **Layer normalization**, or LayerNorm, comes from [Ba et al.](https://arxiv.org/abs/1607.06450) and works within one token's vector. It subtracts the mean of the coordinates, divides by their standard deviation, then applies a learned scale and shift:

$$
\operatorname{LayerNorm}(x) = g \odot \frac{x - \mu}{\sqrt{\sigma^2 + \epsilon}} + b.
$$

Here $\mu$ is the average of the $d$ coordinates, $\sigma$ is their standard deviation, $\epsilon$ is a tiny constant such as $10^{-5}$ that keeps the denominator above zero, and $\odot$ multiplies coordinate by coordinate. The **gain** $g$ is a learned scale per coordinate and the offset $b$ is a learned shift per coordinate, which together let the model undo the standardization where that helps.

In plain terms, LayerNorm keeps the pattern of a vector and discards its overall level and spread. The pattern is which coordinates are high and which are low relative to each other. A token vector whose numbers sit around 100 and one whose numbers sit around 0.01 come out on the same footing before the gain and offset are applied. Both end up with average 0 and spread 1. It works on one token's vector at a time and never looks at other tokens or other sequences in the batch, so a token gets the same result in a large training batch as it does alone during generation.

LayerNorm shifts the vector to center it before rescaling. If the goal is to control the size of its coordinates, a simpler operation divides by a measure of size. **RMSNorm** comes from [Zhang and Sennrich](https://arxiv.org/abs/1910.07467). It skips the mean subtraction and the offset and divides by the root mean square $\operatorname{RMS}(x)$ instead. That is the square root of the average squared coordinate $x_i$. RMSNorm then multiplies by the same learned gain $g$:

$$
\operatorname{RMSNorm}(x) = g \odot \frac{x}{\operatorname{RMS}(x)}, \qquad \operatorname{RMS}(x) = \sqrt{\tfrac{1}{d}\textstyle\sum_i x_i^2 + \epsilon}.
$$

Dividing by the root mean square sets the typical size of a coordinate to 1 and leaves the vector's direction alone. With gain 1, every token leaves RMSNorm with a root mean square of 1, which for the [story model](/tutorials/llm-fundamentals/#story-model)'s $d = 384$ means a vector of length $\sqrt{384} \approx 19.6$. The useful property follows directly. Scaling the input by any positive factor scales $\operatorname{RMS}(x)$ by the same factor, so $\operatorname{RMSNorm}(10x) = \operatorname{RMSNorm}(x)$ apart from the tiny $\epsilon$. A sublayer behind the norm therefore sees the same input whether the stream entering it has grown to several times its starting size over the blocks below or has not grown at all. The price is that the sublayer can no longer tell how large the stream was. Only the direction reaches it, and the learned gain rescales each coordinate by a fixed amount that is the same for every token.

The two outputs disagree most on coordinate 1. Its input value of 1 is positive but below the vector's mean of 2, so LayerNorm turns it into $-0.447$, while RMSNorm keeps it positive at $0.333$. LayerNorm judges every coordinate against the vector's own average, and RMSNorm judges it against zero. The RMSNorm output therefore keeps a mean of 0.67, the input mean of 2 divided by the root mean square of 3, so a shift shared by all coordinates still reaches the next layer. The two denominators are closely linked. The squared root mean square equals the variance plus the squared mean, here $9 = 5 + 4$, so for a vector whose mean is already near zero the two methods give almost the same output.

RMSNorm saves the mean computation and the $d$ offset numbers, and the paper reports 7% to 64% lower running time across its test models with comparable quality. The paper's argument is that the rescaling carries the stabilizing benefit, while recentering adds little. Llama, Mistral, and most recent decoders use it, and so does the story model. Each of its RMSNorms holds 384 gain numbers. There are two per block plus one final, which is 4,992 parameters in total.

## Pre-norm and post-norm
Once a block has a normalization step, the remaining question is where to put it, either on the way into each sublayer or after the addition. **Post-norm** was used in the original Transformer. It normalizes after the addition, $x_\ell = \operatorname{Norm}(x_{\ell-1} + F_\ell(x_{\ell-1}))$. **Pre-norm** has been used from GPT-2 onward. It normalizes only the copy the sublayer reads and leaves the stream itself untouched, $x_\ell = x_{\ell-1} + F_\ell(\operatorname{Norm}(x_{\ell-1}))$. In both, $x_{\ell-1}$ is the stream entering, $F_\ell$ is the sublayer's computation, and Norm is LayerNorm or RMSNorm.

The difference is what happens to the identity path from the [residual stream](#the-residual-stream) section. In post-norm every normalization sits on that path, so a gradient travelling from the top to block 1 passes through one rescaling per sublayer, 12 of them in a stack shaped like the [story model](/tutorials/llm-fundamentals/#story-model). [Xiong et al.](https://arxiv.org/abs/2002.04745) showed that at the start of training the gradients near the output are much larger than those near the input. Post-norm stacks therefore need **warmup**, a schedule that starts the step size near zero and raises it over the first few thousand steps. Deep post-norm stacks still diverge easily. Pre-norm keeps the identity path free of any operation, so the 1 from the [residual stream](#the-residual-stream) section reaches every block. Deep stacks then train stably without the long [warmup](/tutorials/llm-fundamentals/pretraining-at-scale/#learning-rate-schedules) post-norm needs, though large runs still use a short one. Pre-norm has its own cost. The stream is never rescaled, so it grows. If the embedding has a root mean square of 1 and each of the story model's 12 sublayers adds a contribution of size 1 that is roughly unrelated to the others, the squared sizes add and the final stream has size about $\sqrt{1 + 12} \approx 3.6$. The last sublayer's write then changes the stream's direction by about one part in 3.6. With the 64 sublayers of a 32-block model, the same arithmetic gives $\sqrt{65} \approx 8.1$. That is one reason late layers in deep pre-norm models often contribute less, and it is why pre-norm models add a final normalization before the output head. Some recipes add extra norms or rescale the residual branches to recover late-layer influence, and those are refinements on a pre-norm base.

## The feed-forward network

Attention mixes information across tokens, but something also has to compute on what each token has gathered. The feed-forward network, or FFN, does that computation. It is a small two-layer network applied to each token's vector separately, with the same weights for every position. It widens the vector, applies a nonlinear function to each number, and narrows it back:

$$
\operatorname{FFN}(x) = \phi(x W_1)\, W_2.
$$

Here $x$ is the normalized stream for one token as a row of $d$ numbers, $W_1$ is a $d \times d_{\text{ff}}$ matrix that widens it, $\phi$ is the **activation function** applied to every number separately, and $W_2$ is a $d_{\text{ff}} \times d$ matrix that narrows it back. The **hidden width** $d_{\text{ff}}$ is the number of hidden units, classically $4d$. A matrix of shape $d \times d_{\text{ff}}$ holds $d \cdot d_{\text{ff}}$ parameters, so the classic FFN holds $2 \cdot d \cdot 4d = 8d^2$. At the [story model](/tutorials/llm-fundamentals/#story-model)'s width $d = 384$ that is 1,179,648, twice the $4d^2 = 589{,}824$ of standard attention. Two thirds of a block's parameters therefore sit in the part that never looks at another token. The story model shares its key and value heads, which shrinks attention further, as the [decoder block](#the-decoder-block) section shows.

The activation is what makes the network more than one matrix, because two matrices in a row with nothing between them collapse into a single matrix. The rectified linear unit, or **ReLU**, returns the larger of its input and zero. The Gaussian error linear unit, or **GELU**, comes from [Hendrycks and Gimpel](https://arxiv.org/abs/1606.08415). It returns $u\,\Phi(u)$ for an input $u$, where $\Phi(u)$ is the probability that a standard normal value falls below $u$. So it behaves like ReLU for large inputs and lets small negative inputs through as small negative outputs. GPT-2 and BERT use GELU.

## SwiGLU
A plain activation decides how much of each hidden unit passes based only on that unit's own value. A gate lets a second learned signal make that decision instead. That signal is computed from the same input. [Dauphin et al.](https://arxiv.org/abs/1612.08083) introduced the **gated linear unit**, which computes two projections of the input and multiplies them, one acting as the gate and the other as the value. The sigmoid linear unit, or **SiLU**, is $\operatorname{SiLU}(u) = u \cdot \frac{1}{1 + e^{-u}}$, a smooth curve close to GELU. **SwiGLU** uses SiLU on the gate branch, as proposed by [Shazeer](https://arxiv.org/abs/2002.05202):

$$
\operatorname{FFN}_{\text{SwiGLU}}(x) = \big(\operatorname{SiLU}(x W_{\text{gate}}) \odot x W_{\text{up}}\big)\, W_{\text{down}}.
$$

Here $W_{\text{gate}}$ and $W_{\text{up}}$ are both $d \times d_{\text{ff}}$ and produce the gate and the value, $\odot$ multiplies them coordinate by coordinate, and $W_{\text{down}}$ is $d_{\text{ff}} \times d$ and narrows the result back to width $d$. For a token whose gate pre-activations are $(2, -1)$ and whose values are $(3, 4)$, SiLU gives $2 \times 0.881 = 1.762$ and $-1 \times 0.269 = -0.269$, so the gated hidden vector is $(1.762 \times 3, -0.269 \times 4) = (5.285, -1.076)$. The first unit passes its value scaled up by 1.76, while the second shrinks its value to about a quarter and flips its sign, and the gate learned to make each call from the input.

Three matrices instead of two would raise the feed-forward network's (FFN's) parameters by half at the same hidden width, so the width is cut to keep the count near the classic $8d^2$. Setting $3 \cdot d \cdot d_{\text{ff}} = 8d^2$ gives $d_{\text{ff}} = \tfrac{8}{3}d$, which is the source of the $\tfrac{2}{3} \times 4d$ rule. For the [story model](/tutorials/llm-fundamentals/#story-model)'s $d = 384$ that is exactly 1,024. It is also a multiple of 256, so the matrices split evenly across hardware tiles. The story model's SwiGLU FFN holds $3 \times 384 \times 1{,}024 = 1{,}179{,}648$ parameters, exactly the $8d^2$ of a classic FFN. Widths that do not divide evenly get rounded up. Llama 2 7B has $d = 4{,}096$, which gives $10{,}922.7$, and it uses the next multiple of 256, $43 \times 256 = 11{,}008$. Shazeer's experiments found the gated variants beat ReLU and GELU at matched parameters and compute, and PaLM, Llama, Mistral and the story model all use SwiGLU. The paper offers no theory for why, so the usual explanation that multiplicative gates let a unit switch on context is a plausible reading rather than a proof.

## The decoder block

In the story model, attention runs before the feed-forward network. The second part therefore receives the updates from the first part as part of its input. A **decoder block** is the repeating unit of a text generator. It is a pre-norm attention sublayer followed by a pre-norm SwiGLU sublayer, each wrapped in a residual connection. For the attention sublayer it is enough here to know that multi-head attention splits the width into $h$ heads of width $d_h$, and each head scores every earlier token, turns the scores into weights that sum to 1, and returns a weighted average of their information. [Attention](/tutorials/llm-fundamentals/attention-and-positional-information/) develops the causal mask that makes it look only backward, along with positional information. One block then computes

$$
a = x + \operatorname{Attn}(\operatorname{RMSNorm}_1(x)), \qquad x' = a + \operatorname{FFN}_{\text{SwiGLU}}(\operatorname{RMSNorm}_2(a)).
$$

Here $x$ is the stream entering the block, $a$ is the stream after the attention sublayer has added its output, and $x'$ is the stream leaving. Each RMSNorm has its own gain. The [story model](/tutorials/llm-fundamentals/#story-model) stacks 6 identical copies, and each has its own weights. The input and output of every block are vectors of $d = 384$ numbers per token.

![Decoder block](/images/llm-fundamentals/15d-decoder-block.png)

Each block gives a token one chance to collect information from earlier tokens and then one chance to compute on what it collected. Attention is the only sublayer that looks at other tokens, so a stack without it would process each word in isolation, however deep. The feed-forward network reads the stream $a$ after attention has already added to it, so it works on what the token has just gathered from its context. The two jobs come at very different prices. In the story model, attention holds 393,216 parameters per block and the SwiGLU network holds 1,179,648, so the part that never looks at another token makes up three quarters of the block. The [parameter counting](#parameter-counting) section counts both exactly. Both sublayers branch off the identity path, which is also called the residual path. Each adds its result back at a plus sign, so a sublayer that outputs zeros leaves the stream as it entered. Attention splits the 384 numbers into 6 query heads of width 64 instead of widening them, so every edge of the block carries the same 384 numbers. That fixed width is what lets blocks be stacked, removed or inspected one at a time. The story model's attention also uses one of the later variants of this block. Its 6 query heads share 2 key heads and 2 value heads, three query heads to each pair, which is [grouped-query attention](/tutorials/llm-deep-dive/efficient-attention-mechanisms/#grouped-query-attention). The key and value matrices are therefore $384 \times 128$ instead of $384 \times 384$, which is why attention holds less than the $4d^2$ of the [feed-forward network](#the-feed-forward-network) section. [Head sharing](/tutorials/llm-fundamentals/attention-and-positional-information/#head-sharing) explains what the sharing saves and costs, and Modern LLM Architectures gives the full list of later variants, such as different position schemes.

## The output head

After the last block, the model has one 384-number vector per position and needs a probability for every possible next token. The **output head** is one matrix $W_{\text{out}}$ of shape $d \times V$ that turns the final normalized vector into one score per vocabulary entry. Each score is a **logit**, an unnormalized number where higher means more likely. **Softmax** then exponentiates every logit and divides by the total, producing probabilities that are positive and sum to 1:

$$
z = \operatorname{RMSNorm}(x_L)\, W_{\text{out}}, \qquad P(\text{token } j) = \frac{e^{z_j}}{\sum_{i=1}^{V} e^{z_i}}.
$$

Here $x_L$ is the stream after the last block, $z$ is the row of $V$ logits, $z_j$ is the logit for token $j$, and the sum runs over the whole vocabulary, $V = 4{,}096$ tokens in the [story model](/tutorials/llm-fundamentals/#story-model). A toy case has a three-token vocabulary of "cat", "dog", and "the", a final normalized vector $(1, 2)$, and output columns $(0, 1)$, $(0.6, 0.2)$, and $(0.1, 0)$. The logits are $0 + 2 = 2.0$, $0.6 + 0.4 = 1.0$, and $0.1$. Exponentials are 7.389, 2.718, and 1.105, which sum to 11.212, so the probabilities are 0.659, 0.242, and 0.099. If the true next token is "cat", the training loss for this position is $-\ln 0.659 = 0.417$, and [Language Modeling](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/) develops that cross-entropy loss and the softmax in full.

Both tables need one vector per vocabulary token. The story model can save a second copy by learning one vector to use in both places. This reuse is called **weight tying**. Its one $4{,}096 \times 384$ table supplies a token's starting vector when the token is read, and the same table turned on its side is $W_{\text{out}}$, which scores all 4,096 tokens at the output. Tying saves $V \times d = 1{,}572{,}864$ parameters, 12.5% of the 12.6 million an untied version would hold. The price is that one vector per token has to do two jobs. As an input row it describes the token once it has been read, and as an output column it decides which final vectors make the token a likely next choice. Separate tables would let the two drift apart. The size of the saving usually settles the choice. GPT-2 small has $V = 50{,}257$ and $d = 768$, and there the table is 38.6 million of about 124 million parameters, roughly 31%. That is why small models usually tie. In Llama 2 7B the table is 131 million numbers, only 1.9% of the model, and it keeps two separate tables. The story model's head costs $2 \times 384 \times 4{,}096 = 3.1$ million operations per token. That is 14.3% of the 22.0 MFLOPs forward pass that the [FLOPs per token](#flops-per-token) section counts, the same share the table has of the parameters, because the shared table is used as a matrix exactly once.

## Parameter counting

Each entry of a learned matrix counts as one parameter. A matrix with 384 rows and 128 columns holds 49,152 numbers, the product of the two. The model's total is the sum over every matrix and every normalization gain. The [story model](/tutorials/llm-fundamentals/#story-model) has $L = 6$ blocks, width $d = 384$, vocabulary $V = 4{,}096$, and SwiGLU hidden width $d_{\text{ff}} = 1{,}024$. Its 6 query heads of width 64 share 2 key and value heads, so the key and value projections are 128 numbers wide. Its parameters count as follows.

1. The embedding table has one row per vocabulary entry, giving $4{,}096 \times 384 = 1{,}572{,}864$. The output head reuses this table, so it is counted once.
2. Attention in one block has two $d \times d$ matrices for queries and output, $2 \times 147{,}456$, and two $d \times 128$ matrices for keys and values, $2 \times 49{,}152$. Together they give $393{,}216$.
3. The SwiGLU FFN in one block has three matrices of $d \times d_{\text{ff}}$, giving $3 \times 384 \times 1{,}024 = 1{,}179{,}648$.
4. The two RMSNorm gains in one block give $2 \times 384 = 768$. One block totals $1{,}573{,}632$.
5. All 6 blocks come to $6 \times 1{,}573{,}632 = 9{,}441{,}792$, and the final RMSNorm adds 384.
6. Add the three parts:

   $$
   1{,}572{,}864 + 9{,}441{,}792 + 384 = 11{,}015{,}040.
   $$

   That is about 11.0 million, and the notebook that builds the story model checks this count against the parameters it creates. The story model trains in float32, which takes 4 bytes per number, so its weights fill 44.1 MB. [bf16](/tutorials/llm-fundamentals/pretraining-at-scale/#mixed-precision) is a 16-bit number format with 2 bytes per number, and in it the same weights take 22.0 MB, or 21.0 MiB in binary megabytes of $2^{20}$ bytes. The same bookkeeping for Llama 2 7B, with 32 blocks of width 4,096, a 32,000-token vocabulary and separate input and output tables, gives 6.74 billion parameters and 13.5 GB in bf16.

![Parameter breakdown](/images/llm-fundamentals/15d-parameter-breakdown.png)

A quick estimate drops embeddings and norms and uses $4d^2$ for attention plus $8d^2$ for the feed-forward network (FFN), giving $N \approx 12 L d^2$. For the story model that is $12 \times 6 \times 384^2 = 10{,}616{,}832$, 3.6% below the exact count. The closeness is partly luck. The rule leaves out the 1,572,864-number embedding table and the 4,992 norm gains. It also charges full $4d^2$ attention, which over six blocks is 1,179,648 more than the narrower key and value matrices hold. The two errors cancel down to a net gap of 398,208. The SwiGLU term is exact, because $d_{\text{ff}} = 1{,}024$ is exactly $\tfrac{8}{3}d$. The estimate works well for large models with plain multi-head attention and badly for small ones, where embeddings are a big share. The story model's table is 14.3% of its parameters, and the GPT-2 small example in the [output head](#the-output-head) section showed a share of 31%. Two common changes break the $4d^2$ attention term. Grouped-query attention is the first, and the story model already uses it, with key and value matrices of $d \times 128$ each. A mixture of experts multiplies the FFN term, as the [mixture of experts](#mixture-of-experts) section shows.

## FLOPs per token

Parameter count says how much memory the weights need, and a separate count says how much arithmetic each token costs. A **FLOP**, or floating-point operation, is one addition or multiplication on a decimal number. Multiplying a token's vector by a $d \times d$ matrix takes $d^2$ multiplications and about $d^2$ additions, so every weight is used for about 2 FLOPs per token. The **forward pass** computes the output from the input. It therefore costs about $2N$ FLOPs per token, where $N$ is the parameter count. For the [story model](/tutorials/llm-fundamentals/#story-model) that is $2 \times 11.0 \times 10^6 = 22.0$ MFLOPs, where one MFLOP is a million FLOPs.

The $2N$ rule leaves out attention's own arithmetic, which has no weights. A token at position $t$ compares its query with $t$ keys and averages $t$ values, about $4td$ FLOPs per block across all heads. The **context length** $n$ is the number of tokens the model reads at once. Averaged over a causal sequence of that length, this adds about $2Lnd$ per token. At the story model's full $n = 512$ that is $2 \times 6 \times 512 \times 384 = 2.36$ MFLOPs, 9.7% of the forward pass. The last token of a full window pays the most, $4Lnd = 4.7$ MFLOPs, and the notebook that builds the story model adds that worst case to $2N$ for its estimate of 26.7 MFLOPs per token. The two terms are equal when $n = N/(Ld) \approx 4{,}800$ tokens, more than nine times the story model's window, so for this shape the weights dominate at every length it can read. Past the crossing, attention grows linearly per token while the weight term stays fixed. Because $N$ is roughly $12Ld^2$, the crossing sits near $12d$ tokens and moves out as models get wider, to about 51,000 tokens for a width of 4,096 as in Llama 2 7B.

![Flops versus context](/images/llm-fundamentals/15d-flops-versus-context.png)

</details>

The **backward pass** computes gradients and costs about twice the forward pass. For each matrix multiplication it needs two more of the same size, one giving the gradient for the layer's input so the signal can continue to earlier layers and one giving the gradient for the weights so they can be updated. Training per token is therefore $2N + 4N = 6N$, which is 66.1 MFLOPs per token for the story model. Over a training run of $D$ tokens this becomes the $6ND$ rule. The story model's run predicts about 45.4 million real tokens, so it costs about $3.00 \times 10^{15}$ FLOPs, which [Pretraining](/tutorials/llm-fundamentals/pretraining-at-scale/) turns into training time. Llama 2 7B read 2 trillion tokens, and the same rule gives it about $8.1 \times 10^{22}$ FLOPs, some 27 million times more. Some runs save memory by recomputing intermediate results during the backward pass instead of storing them. That adds roughly one more forward pass, bringing the total to about $8N$, so real runs often count more.

Almost every parameter in the model is a weight inside a matrix multiplication, so one small layer shows where the count comes from. Take a layer with 6 weights that turns a 3-number input into a 2-number output, $y = Wx$:

$$
W = \begin{bmatrix} 1 & 0 & 2 \\ 0 & 1 & 1 \end{bmatrix}, \quad x = \begin{bmatrix} 1 \\ 2 \\ 3 \end{bmatrix}
$$

**Forward pass, 2 FLOPs per weight.** Each output is a dot product, $y_1 = 1\cdot1 + 0\cdot2 + 2\cdot3 = 7$ and $y_2 = 0\cdot1 + 1\cdot2 + 1\cdot3 = 5$. Every weight is used in exactly one multiplication, and each product is then added into a running sum. That is 6 multiplications and 4 additions here. In a real layer each output sums thousands of products, so there is one addition per multiplication and the count is 2 FLOPs per weight.

The backward pass starts from the gradient of the loss with respect to the layer's output, and it has two separate jobs. Here that gradient is $\partial L/\partial y = (1, -1)$.

**Gradient for the input, 2 more FLOPs per weight.** The earlier layers need to know how the loss changes with $x$, so the signal can keep flowing down. That is $W^\top$ times the output gradient:

$$
\frac{\partial L}{\partial x} = W^\top \frac{\partial L}{\partial y} = \begin{bmatrix} 1\cdot1 + 0\cdot(-1) \\ 0\cdot1 + 1\cdot(-1) \\ 2\cdot1 + 1\cdot(-1) \end{bmatrix} = \begin{bmatrix} 1 \\ -1 \\ 1 \end{bmatrix}
$$

This is a second matrix multiplication with the same 6 weights. Each weight again takes part in one multiplication and one addition.

**Gradient for the weights, 2 more FLOPs per weight.** The optimizer needs to know how the loss changes with each weight. Weight $W_{ij}$ links input $j$ to output $i$, so its gradient is the product of the two, $\partial L/\partial y_i \times x_j$:

$$
\frac{\partial L}{\partial W} = \frac{\partial L}{\partial y}\, x^\top = \begin{bmatrix} 1 & 2 & 3 \\ -1 & -2 & -3 \end{bmatrix}
$$

That is one multiplication per weight for this token. A batch holds millions of tokens, and each weight's gradient is the sum of its products over all of them, so every token adds one multiplication and one addition per weight.

Adding the three parts gives $2 + 2 + 2 = 6$ FLOPs per weight per token. The forward pass is a third of the work, and the backward pass is the other two thirds because it runs two multiplications of the same size as the forward one. Summed over every weight in the model, a token costs $6N$, and $D$ tokens cost $6ND$. For the story model that is $2N = 22.0$ MFLOPs forward and $4N = 44.1$ MFLOPs backward, 66.1 MFLOPs per token in all.

The rule is approximate, and its gaps are worth knowing:
- **The optimizer update is too rare to count.** AdamW does a few dozen operations per parameter, but once per step rather than once per token. Each update of the story model's training predicts about 5,700 real tokens, so the optimizer's share per token is a few thousandths of a FLOP per parameter, against 6 for the matrices.
- **Attention scores are left out.** Comparing queries with keys and averaging values has no weights, so $6N$ misses it. The attention deep dive earlier in this section puts it at 9.7 percent of the story model's forward pass at 512 tokens, and the share grows with context length, as [attention cost against the feed-forward network](/tutorials/llm-deep-dive/efficient-attention-mechanisms/#attention-cost) in LLM Deep Dive follows out to 128K tokens.
- **The embedding lookup does no arithmetic.** A lookup copies one row and multiplies nothing. The story model's table is counted once in $N$, and its one use as a matrix is the output head, so $2N$ charges it correctly. A model with separate input and output tables counts an input table in $N$ that costs no FLOPs. In Llama 2 7B that table holds 131 million parameters, about 2 percent of $N$, so $6N$ is a slight overcount there. Some scaling studies leave embeddings out of $N$ for this reason.
- **For a mixture of experts, $N$ is the active count.** Only the weights a token actually multiplies cost FLOPs, so a model that stores 46.7 billion parameters but routes each token through 12.9 billion trains at about $6 \times 12.9$ billion FLOPs per token. [Total and active parameters](/tutorials/llm-deep-dive/mixture-of-experts-at-scale/#total-and-active-parameters) in LLM Deep Dive works through that gap.
- **Recomputation is extra work that the count ignores.** Runs that save memory by redoing the forward pass spend about $8N$ per token, but [model FLOPs utilization](/tutorials/llm-fundamentals/pretraining-at-scale/#the-compute-budget) still credits only $6N$, because the extra $2N$ produces nothing new. LLM Deep Dive covers the trade in [activation memory and recomputation](/tutorials/llm-deep-dive/numerics-and-training-stability/#activation-recomputation) and the utilization that real clusters reach in [model FLOPs utilization and the step time budget](/tutorials/llm-deep-dive/distributed-training-and-parallelism/#model-flops-utilization).

At inference there is no backward pass, so generating or scoring a token costs about $2N$, a third of a training token.

</details>

FLOPs set the cost of training and of processing a long prompt, but generating one token at a time is usually limited by reading the weights from memory instead. The story model reads only 22.0 MB of bf16 weights for each generated token, while a 7-billion-parameter model reads about 13.5 GB, and [Inference](/tutorials/llm-fundamentals/inference-and-decoding/) works through what that read costs.

## Mixture of experts

In a dense feed-forward network, widening the layer adds weights and increases the arithmetic for each token. A **mixture of experts**, or [MoE](/tutorials/llm-deep-dive/mixture-of-experts-at-scale/#total-and-active-parameters), breaks that link by running only part of the feed-forward network (FFN) for each token, following [Shazeer et al.](https://arxiv.org/abs/1701.06538) and [Switch Transformer](https://arxiv.org/abs/2101.03961). Each MoE layer keeps $E$ separate FFNs, each called an **expert**, and a small learned $d \times E$ matrix called the **router** scores the experts for each token. **Top-k routing** keeps the $k$ highest-scoring experts, renormalizes their router probabilities $p_e$ to sum to 1, and returns the weighted sum of their outputs. Mixtral renormalizes this way, though some models skip that step. Attention, norms, and embeddings stay shared.

![Mixture of experts layer](/images/llm-fundamentals/15d-mixture-of-experts-layer.png)

For this token the router's probabilities are 0.61, 0.22, 0.14 and 0.03, and top-2 routing keeps the first two. Together they hold 0.83 of the probability. Dropping experts 3 and 4 discards the 0.17 the router gave them, and dividing the kept pair by their sum turns 0.61 and 0.22 into 0.731 and 0.269. The token then pays for two experts' arithmetic out of four, half the feed-forward cost of running all of them, while all four sit in memory. The choice is a hard cut. Expert 3 at 0.14 was not far behind expert 2 at 0.22, and a slightly different token vector could swap them and send the token through entirely different weights. Everything outside the experts stays as it was. The mixed output is added to the residual stream exactly as a dense feed-forward network's output would be, so attention, the norms and the blocks above need no change.

The router is the only new piece of arithmetic. Each of its $E$ columns acts like a learned direction, and a token's score for expert $e$ is the dot product of the token's normalized stream vector with column $e$, so tokens whose vectors point the same way tend to land on the same experts. A softmax turns the $E$ scores into probabilities, and those probabilities also weight the experts' outputs, which is how the router learns. When a chosen expert's weighted output lowers the loss, training raises that expert's score for similar tokens, and when it raises the loss, training lowers it. The experts that were not chosen get no gradient from this token at all.

The gain comes from giving different tokens different weights. A dense FFN serves every token with one set of weights. An MoE layer with $E$ experts holds $E$ times as many FFN parameters, while each token still multiplies only $k$ of them. With 8 experts the size of the dense FFN and top-2 routing, the layer stores 8 times the dense FFN's weights and does twice its arithmetic per token. Across the whole model the ratios are smaller, because attention, norms and embeddings stay shared, as the count at the end of this section shows. The name suggests experts on topics such as biology or law. The [Mixtral](https://arxiv.org/abs/2401.04088) authors looked for such a split and found little of it. ArXiv papers, biology abstracts and philosophy papers used the experts in very similar proportions, and the routing followed syntax more than subject, with indentation tokens in Python code always going to the same experts. The costs mirror the gain. Every expert must sit in memory even though most are idle for any one token, and routing only pays off if tokens spread across the experts, which the worked example below shows does not happen on its own.

Left alone this imbalance worsens, because a busier expert trains faster and attracts still more tokens, until a few experts take everything. A **load balancing loss** keeps the experts in use. It is an extra training penalty that grows when assignments are uneven, and Advanced Topics derives it along with the capacity limits that drop overflow tokens.

The payoff and the cost show up in two counts. **Total parameters** are every weight stored, which sets memory. **Active parameters** are the weights one token actually multiplies against, which sets FLOPs. A concrete case swaps each FFN in the [story model](/tutorials/llm-fundamentals/#story-model) for 8 SwiGLU experts of the same size, routed top-2. Each expert holds 1,179,648 parameters, and the router adds $384 \times 8 = 3{,}072$ per block. Total parameters become 60.58 million, which is 121.2 MB in bf16. Active parameters are 18.11 million, so each token costs about $2 \times 18.11 = 36.2$ MFLOPs forward. The model stores 5.5 times the dense model's weights for 1.6 times its arithmetic. Mixtral 8x7B from [Jiang et al.](https://arxiv.org/abs/2401.04088) has 46.7 billion total and 12.9 billion active. Modern LLM Architectures covers how much quality the extra storage actually buys, which is less than the storage ratio.

## Architecture families
The same blocks can be wired three ways, and the wiring decides what the model can be trained to do. Each family pairs an attention pattern with an objective, the prediction task whose error training minimizes. The original Transformer from [Attention Is All You Need](https://arxiv.org/abs/1706.03762) was built for machine translation and used two stacks. An encoder read the source sentence, and a decoder wrote the translation while attending to it. The families that followed either kept both stacks or kept only one of them. An **encoder-only** model lets every token see every other token. It trains with **masked language modeling**, hiding about 15% of tokens and predicting them. [BERT](https://arxiv.org/abs/1810.04805) is built this way. A decoder-only model uses a [causal mask](/tutorials/llm-fundamentals/attention-and-positional-information/#the-causal-mask) so each token sees only earlier ones. It trains with **causal language modeling**, predicting the next token at every position. GPT and Llama are built this way. An **encoder-decoder** model keeps the original design, as [T5](https://arxiv.org/abs/1910.10683) does. It reads a source with a bidirectional encoder and writes the output with a causal decoder that also uses **cross attention**, attention whose queries come from the output and whose keys and values come from the encoded source. T5 trains with **span corruption**, replacing random runs of tokens with placeholder markers and generating the missing runs. A **prefix LM**, or prefix language model, is a decoder-only model that reads its first part bidirectionally and generates the rest causally. That first part is called the prefix.

The objectives differ sharply in how much signal one sequence gives. In a 512-token sequence, masked modeling yields about $0.15 \times 512 \approx 77$ predictions, while causal modeling yields about 512, one per position. T5's span corruption with spans averaging 3 tokens yields the same 77 hidden tokens in about 26 spans. Decoder-only models came to dominate general-purpose large language models for four connected reasons. They extract a learning signal from every token. One objective serves every task through prompting, since any task can be written as text to continue. Generation streams naturally one token at a time while reusing stored results for earlier tokens. With a single stack there are fewer design choices to scale. [Wang et al.](https://arxiv.org/abs/2204.05832) found causal decoders best for zero-shot use after plain pretraining on raw text. Zero-shot means tasks given without examples. Encoder-decoders and other models that read their input bidirectionally and train with masked modeling did better after multitask fine-tuning, meaning further training on many labeled tasks. So the win is about the general-purpose use case rather than every task.

| Situation | Choice | Main qualification |
|---|---|---|
| General assistant, open-ended generation, prompting with a few examples | Dense decoder-only | Cost per token grows with every parameter |
| Embeddings, retrieval, or classification at low latency | Encoder-only | Cannot generate text |
| Fixed input mapped to a different output, such as translation or speech | Encoder-decoder | Two stacks to scale and serve |
| Quality per FLOP matters and memory across many graphics processors is available | Decoder-only mixture of experts | Memory follows total parameters and needs load balancing |
| One graphics processor or an edge device with tight memory | Small dense decoder-only | Lower ceiling on quality |

A fair comparison of a dense model and a mixture of experts starts with the workload both models will serve. The experiment fixes a training budget in FLOPs, trains both at that budget on the same data, and compares quality alongside serving cost per million tokens at the expected batch size. A good decision record writes the reversal condition down before the run, for instance that the dense model ships if serving memory or the communication between graphics processors holding different experts makes the mixture's cost per token higher at equal quality.
