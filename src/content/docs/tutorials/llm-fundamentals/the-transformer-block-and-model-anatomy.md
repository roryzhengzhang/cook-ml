The [reference Llama 2 model](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/#reference-llama-2-model) used across this series is 32 copies of the same unit stacked on top of each other, and almost everything about its size, cost and training behavior comes from that one unit, called a block. Each token travels up the stack as a list of numbers, and every block reads that list and adds a correction to it instead of rewriting it. Questions about model size, training cost and stability mostly come down to how the blocks are wired, which is a separate matter from what the model is trained to predict.

A network built from such blocks is a **transformer**. This chapter covers the **decoder-only** kind, which reads text left to right and predicts the next token. GPT, Llama, Qwen and Mistral are all built this way, so every block, count and cost below is for a decoder. The other two families are encoders and encoder-decoders. They appear only in the last section, which compares them.

Each block holds two parts, and both follow the same routine. Attention lets a token pull information from earlier tokens, and the **feed-forward network** transforms each token on its own. Each part reads a rescaled copy of the running list, computes something, and adds the result back. Once that routine is clear, the model's anatomy reduces to counting. Counting the matrices gives the parameters, doubling that gives the arithmetic per token, and swapping one part for several copies gives a mixture of experts.

![Residual stream](/images/llm-fundamentals/15d-residual-stream.png)

Because every block adds to the stream and nothing overwrites it, the 4,096 numbers that reach the output head are the token's embedding plus 64 corrections, two from each of the 32 blocks. That sum is what lets a model this deep train at all. The gradient of the loss passes back through each plus sign unchanged, so block 1 gets as direct a signal as block 32. If each block instead replaced its input with its output, the signal would be multiplied by 32 blocks' worth of factors on its way down, and it could shrink to almost nothing before it reached the bottom. The additive design also changes what a block has to learn. A block does not rebuild the token's representation from scratch. It only learns a small edit that improves the next-token prediction, and a block with nothing useful to add can output numbers near zero and leave the stream as it was.

The stream is also shared. Every block reads everything earlier blocks have written, so a feature that attention adds in block 5 is still there for the feed-forward network in block 20 to use. The sum has a cost too. With 64 additions, the numbers in the stream tend to grow with depth, and a sublayer tuned for small inputs would see much larger ones near the top. That is why each sublayer reads a normalized copy, while the stream itself stays unnormalized so the gradient path through it stays clean.

The sections follow the order in which these ideas depend on each other. The residual stream comes first, with the gradient argument worked out in numbers. Normalization follows, because where it sits in the block decides whether that clean gradient path survives. The feed-forward network and its gated SwiGLU version come next. Together they hold about two thirds of each block's parameters, so they set most of the model's size. With those pieces in hand, a full decoder block and the output head can be assembled and checked against the reference model's 6.74 billion parameters.

A finished model leaves two more questions open, namely what it costs and what else it could have been. Counting parameters and FLOPs per token answers the first. The second is answered by a mixture of experts and by a comparison of encoders, decoders and encoder-decoders. A mixture of experts grows the parameter count without growing the cost per token.

## The residual stream

Any deep stack has to answer one design question, which is whether each layer replaces its input or edits it. If every layer recomputes its output from scratch, errors compound with depth and information from the embedding and early layers can fade. A **residual connection** takes the editing route. It adds a layer's output to its input instead of replacing it. The **residual stream** is the running vector those additions build up, and each token has its own. It runs from the **embedding** to the final layer. The embedding is the learned starting vector looked up for the token, covered in [Tokenization](/tutorials/llm-fundamentals/tokenization-and-embeddings/). It was introduced for image networks by [ResNet](https://arxiv.org/abs/1512.03385) and is used in every transformer since the original [Transformer](https://arxiv.org/abs/1706.03762).

Each block contains two **sublayers**, attention and then the feed-forward network. Treating a whole block as one update for now, block $\ell$ changes the stream by $x_{\ell} = x_{\ell-1} + F_\ell(x_{\ell-1})$, where $x_{\ell-1}$ is the stream entering, $F_\ell$ is what block $\ell$ computes from it, and $x_\ell$ is the stream leaving. The [decoder block](#the-decoder-block) section shows that a block actually makes this addition twice, once per sublayer. Unrolling the sum over all $L$ blocks gives $x_L = x_0 + F_1 + F_2 + \dots + F_L$. Each $F_\ell$ is evaluated on the stream it read, so the final vector is literally the embedding plus every contribution.

The editing route changes what a block has to learn. In a stack that replaces its input, a block with nothing useful to add must still pass everything it received through its own weights, and a freshly initialized block with random weights scrambles that information instead. In a residual stack the same block only has to output something close to zero, and the stream flows past it unchanged. A new model therefore starts close to a short path from the embedding straight to the output head, and each block learns a correction on top of what the blocks below it already wrote. The same identity path carries the training signal back down to the first block without passing through the blocks above it, and the end of this section puts a number on how much that matters for a deep stack.

The addition itself is almost free. Each sublayer adds 4,096 numbers into the stream, so the 64 sublayers of the [reference Llama 2 model](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/#reference-llama-2-model) spend 262,144 additions per token, about 0.002% of the 13.5 GFLOPs that the [FLOPs per token](#flops-per-token) section counts for a forward pass. The real constraint is on shape. A sum needs two vectors of the same length, so every sublayer must read a vector of width $d$ and write one back, and the stream keeps the same 4,096 numbers from the embedding to the last block. Anything a block wants to leave for later blocks has to fit into those numbers, alongside everything every other block has written.

Step 4 is a simplified case of the property that keeps training possible at depth. Block 3's addition was held fixed there, so the final vector moved by exactly block 2's write. In a real model the later blocks would react to the change as well, but the direct route from any block's write to the output still carries it through one for one. The loss is a single number measuring how wrong the model's predictions are. A **gradient** is the signal saying how much the loss would change if a parameter moved, and training sends it backward from the output through every layer. In a plain stack each layer multiplies the gradient by its own local slope, so 32 layers that each scale it by 0.5 shrink it to $0.5^{32} \approx 2.3 \times 10^{-10}$, which is the **vanishing gradient** problem. With residual connections the derivative of $x_L$ with respect to any $x_\ell$ always contains a term equal to 1 from the identity path, so block 1 receives the top-level gradient undiminished plus whatever the blocks above add to it. Interpretability work often reads the stream as a shared workspace that attention moves information into and the feed-forward network writes facts into, a view developed in Anthropic's [transformer circuits framework](https://transformer-circuits.pub/2021/framework/index.html).

## Layer normalization and RMSNorm

Adding contributions block after block lets the stream's numbers drift in size, and a sublayer that sees inputs ten times larger than the ones it learned on will behave differently. **Normalization** is a rescaling step that prevents this. It takes a vector and returns a version with a standard size, so the next layer always sees inputs on a predictable scale. **Layer normalization**, or LayerNorm, comes from [Ba et al.](https://arxiv.org/abs/1607.06450) and works within one token's vector. It subtracts the mean of the coordinates, divides by their standard deviation, then applies a learned scale and shift:

$$
\operatorname{LayerNorm}(x) = g \odot \frac{x - \mu}{\sqrt{\sigma^2 + \epsilon}} + b.
$$

Here $\mu$ is the average of the $d$ coordinates, $\sigma$ is their standard deviation, $\epsilon$ is a tiny constant such as $10^{-5}$ that keeps the denominator above zero, and $\odot$ multiplies coordinate by coordinate. The **gain** $g$ is a learned scale per coordinate and the offset $b$ is a learned shift per coordinate, which together let the model undo the standardization where that helps.

In plain terms, LayerNorm keeps the pattern of a vector and discards its overall level and spread. The pattern is which coordinates are high and which are low relative to each other. A token vector whose numbers sit around 100 and one whose numbers sit around 0.01 come out on the same footing before the gain and offset are applied. Both end up with average 0 and spread 1. It works on one token's vector at a time and never looks at other tokens or other sequences in the batch, so a token gets the same result in a large training batch as it does alone during generation.

**RMSNorm** comes from [Zhang and Sennrich](https://arxiv.org/abs/1910.07467). It skips the mean subtraction and the offset and divides by the root mean square $\operatorname{RMS}(x)$ instead. That is the square root of the average squared coordinate $x_i$. RMSNorm then multiplies by the same learned gain $g$:

$$
\operatorname{RMSNorm}(x) = g \odot \frac{x}{\operatorname{RMS}(x)}, \qquad \operatorname{RMS}(x) = \sqrt{\tfrac{1}{d}\textstyle\sum_i x_i^2 + \epsilon}.
$$

Dividing by the root mean square sets the typical size of a coordinate to 1 and leaves the vector's direction alone. With gain 1, every token leaves RMSNorm with a root mean square of 1, which for $d = 4{,}096$ means a vector of length $\sqrt{4{,}096} = 64$. The useful property follows directly. Scaling the input by any positive factor scales $\operatorname{RMS}(x)$ by the same factor, so $\operatorname{RMSNorm}(10x) = \operatorname{RMSNorm}(x)$ apart from the tiny $\epsilon$. A sublayer behind the norm therefore sees the same input whether the stream entering it has grown to several times its starting size over the blocks below or has not grown at all. The price is that the sublayer can no longer tell how large the stream was. Only the direction reaches it, and the learned gain rescales each coordinate by a fixed amount that is the same for every token.

The two outputs disagree most on coordinate 1. Its input value of 1 is positive but below the vector's mean of 2, so LayerNorm turns it into $-0.447$, while RMSNorm keeps it positive at $0.333$. LayerNorm judges every coordinate against the vector's own average, and RMSNorm judges it against zero. The RMSNorm output therefore keeps a mean of 0.67, the input mean of 2 divided by the root mean square of 3, so a shift shared by all coordinates still reaches the next layer. The two denominators are closely linked. The squared root mean square equals the variance plus the squared mean, here $9 = 5 + 4$, so for a vector whose mean is already near zero the two methods give almost the same output.

RMSNorm saves the mean computation and the $d$ offset numbers, and the paper reports 7% to 64% lower running time across its test models with comparable quality. The paper's argument is that the rescaling carries the stabilizing benefit, while recentering adds little. Llama, Mistral, and most recent decoders use it. In the [reference Llama 2 model](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/#reference-llama-2-model) each RMSNorm holds 4,096 gain numbers. There are two per block plus one final, which is 266,240 parameters in total.

## Pre-norm and post-norm
Once a block has a normalization step, the remaining question is where to put it, either on the way into each sublayer or after the addition. **Post-norm** was used in the original Transformer. It normalizes after the addition, $x_\ell = \operatorname{Norm}(x_{\ell-1} + F_\ell(x_{\ell-1}))$. **Pre-norm** has been used from GPT-2 onward. It normalizes only the copy the sublayer reads and leaves the stream itself untouched, $x_\ell = x_{\ell-1} + F_\ell(\operatorname{Norm}(x_{\ell-1}))$. In both, $x_{\ell-1}$ is the stream entering, $F_\ell$ is the sublayer's computation, and Norm is LayerNorm or RMSNorm.

The difference is what happens to the identity path from the [residual stream](#the-residual-stream) section. In post-norm every normalization sits on that path, so a gradient travelling from the top to block 1 passes through 64 rescalings. [Xiong et al.](https://arxiv.org/abs/2002.04745) showed that at the start of training the gradients near the output are much larger than those near the input. Post-norm stacks therefore need **warmup**, a schedule that starts the step size near zero and raises it over the first few thousand steps. Deep post-norm stacks still diverge easily. Pre-norm keeps the identity path free of any operation, so the 1 from the [residual stream](#the-residual-stream) section reaches every block. Deep stacks then train stably without the long [warmup](/tutorials/llm-fundamentals/pretraining-at-scale/#learning-rate-schedules) post-norm needs, though large runs still use a short one. Pre-norm has its own cost. The stream is never rescaled, so it grows. If the embedding has a root mean square of 1 and each of 32 blocks adds a contribution of size 1 that is roughly unrelated to the others, the squared sizes add and the final stream has size about $\sqrt{1 + 32} \approx 5.7$. A late block's write then changes the stream's direction by about one part in 5.7. That is one reason late layers in pre-norm models often contribute less, and it is why pre-norm models add a final normalization before the output head. Some recipes add extra norms or rescale the residual branches to recover late-layer influence, and those are refinements on a pre-norm base.

## The feed-forward network

Attention mixes information across tokens, but something also has to compute on what each token has gathered. The feed-forward network, or FFN, does that computation. It is a small two-layer network applied to each token's vector separately, with the same weights for every position. It widens the vector, applies a nonlinear function to each number, and narrows it back:

$$
\operatorname{FFN}(x) = \phi(x W_1)\, W_2.
$$

Here $x$ is the normalized stream for one token as a row of $d$ numbers, $W_1$ is a $d \times d_{\text{ff}}$ matrix that widens it, $\phi$ is the **activation function** applied to every number separately, and $W_2$ is a $d_{\text{ff}} \times d$ matrix that narrows it back. The **hidden width** $d_{\text{ff}}$ is the number of hidden units, classically $4d$. A matrix of shape $d \times d_{\text{ff}}$ holds $d \cdot d_{\text{ff}}$ parameters, so the classic FFN holds $2 \cdot d \cdot 4d = 8d^2$. At $d = 4{,}096$ that is 134,217,728, twice the $4d^2$ of attention. Two thirds of a block's parameters therefore sit in the part that never looks at another token.

The activation is what makes the network more than one matrix, because two matrices in a row with nothing between them collapse into a single matrix. The rectified linear unit, or **ReLU**, returns the larger of its input and zero. The Gaussian error linear unit, or **GELU**, comes from [Hendrycks and Gimpel](https://arxiv.org/abs/1606.08415). It returns $u\,\Phi(u)$ for an input $u$, where $\Phi(u)$ is the probability that a standard normal value falls below $u$. So it behaves like ReLU for large inputs and lets small negative inputs through as small negative outputs. GPT-2 and BERT use GELU.

## SwiGLU
A plain activation decides how much of each hidden unit passes based only on that unit's own value. A gate lets a second learned signal make that decision instead. That signal is computed from the same input. [Dauphin et al.](https://arxiv.org/abs/1612.08083) introduced the **gated linear unit**, which computes two projections of the input and multiplies them, one acting as the gate and the other as the value. The sigmoid linear unit, or **SiLU**, is $\operatorname{SiLU}(u) = u \cdot \frac{1}{1 + e^{-u}}$, a smooth curve close to GELU. **SwiGLU** uses SiLU on the gate branch, as proposed by [Shazeer](https://arxiv.org/abs/2002.05202):

$$
\operatorname{FFN}_{\text{SwiGLU}}(x) = \big(\operatorname{SiLU}(x W_{\text{gate}}) \odot x W_{\text{up}}\big)\, W_{\text{down}}.
$$

Here $W_{\text{gate}}$ and $W_{\text{up}}$ are both $d \times d_{\text{ff}}$ and produce the gate and the value, $\odot$ multiplies them coordinate by coordinate, and $W_{\text{down}}$ is $d_{\text{ff}} \times d$ and narrows the result back to width $d$. For a token whose gate pre-activations are $(2, -1)$ and whose values are $(3, 4)$, SiLU gives $2 \times 0.881 = 1.762$ and $-1 \times 0.269 = -0.269$, so the gated hidden vector is $(1.762 \times 3, -0.269 \times 4) = (5.285, -1.076)$. The first unit passes its value scaled up by 1.76, while the second shrinks its value to about a quarter and flips its sign, and the gate learned to make each call from the input.

Three matrices instead of two would raise the feed-forward network's (FFN's) parameters by half at the same hidden width, so the width is cut to keep the count near the classic $8d^2$. Setting $3 \cdot d \cdot d_{\text{ff}} = 8d^2$ gives $d_{\text{ff}} = \tfrac{8}{3}d$, which is the source of the $\tfrac{2}{3} \times 4d$ rule. For $d = 4{,}096$ that is $10{,}922.7$, and Llama rounds up to the next multiple of 256 so the matrices split evenly across hardware tiles, giving $43 \times 256 = 11{,}008$. The SwiGLU FFN then holds $3 \times 4{,}096 \times 11{,}008 = 135{,}266{,}304$ parameters, 0.8% above $8d^2 = 134{,}217{,}728$. Shazeer's experiments found the gated variants beat ReLU and GELU at matched parameters and compute, and PaLM, Llama, and Mistral all adopted SwiGLU. The paper offers no theory for why, so the usual explanation that multiplicative gates let a unit switch on context is a plausible reading rather than a proof.

## The decoder block

The sections from [residual stream](#the-residual-stream) to [SwiGLU](#swiglu) supply every part of a block, so assembling one is mostly a matter of putting them in the right order. A **decoder block** is the repeating unit of a text generator. It is a pre-norm attention sublayer followed by a pre-norm SwiGLU sublayer, each wrapped in a residual connection. For the attention sublayer it is enough here to know that multi-head attention splits the width into $h$ heads of width $d_h$, and each head scores every earlier token, turns the scores into weights that sum to 1, and returns a weighted average of their information. [Attention](/tutorials/llm-fundamentals/attention-and-positional-information/) develops the causal mask that makes it look only backward, along with positional information. One block then computes

$$
a = x + \operatorname{Attn}(\operatorname{RMSNorm}_1(x)), \qquad x' = a + \operatorname{FFN}_{\text{SwiGLU}}(\operatorname{RMSNorm}_2(a)).
$$

Here $x$ is the stream entering the block, $a$ is the stream after the attention sublayer has added its output, and $x'$ is the stream leaving. Each RMSNorm has its own gain. The [reference Llama 2 model](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/#reference-llama-2-model) stacks 32 identical copies, and each has its own weights. The input and output of every block are vectors of $d = 4{,}096$ numbers per token.

![Decoder block](/images/llm-fundamentals/15d-decoder-block.png)

Each block gives a token one chance to collect information from earlier tokens and then one chance to compute on what it collected. Attention is the only sublayer that looks at other tokens, so a stack without it would process each word in isolation, however deep. The feed-forward network reads the stream $a$ after attention has already added to it, so it works on what the token has just gathered from its context. The two jobs come at very different prices. Attention's four $d \times d$ matrices hold 67.1 million parameters per block and the SwiGLU network holds 135.3 million, so the part that never looks at another token makes up two thirds of the block. The [parameter counting](#parameter-counting) section counts both exactly. Both sublayers branch off the identity path, which is also called the residual path. Each adds its result back at a plus sign, so a sublayer that outputs zeros leaves the stream as it entered. Attention splits the 4,096 numbers into 32 heads of width 128 instead of widening them, so every edge of the block carries the same 4,096 numbers. That fixed width is what lets blocks be stacked, removed or inspected one at a time. Llama 2 uses exactly this block. Modern LLM Architectures gives the full list of later variants, such as [grouped-query attention](/tutorials/llm-deep-dive/efficient-attention-mechanisms/#grouped-query-attention) and different position schemes.

## The output head

After the last block, the model has one 4,096-number vector per position and needs a probability for every possible next token. The **output head** is one matrix $W_{\text{out}}$ of shape $d \times V$ that turns the final normalized vector into one score per vocabulary entry. Each score is a **logit**, an unnormalized number where higher means more likely. **Softmax** then exponentiates every logit and divides by the total, producing probabilities that are positive and sum to 1:

$$
z = \operatorname{RMSNorm}(x_L)\, W_{\text{out}}, \qquad P(\text{token } j) = \frac{e^{z_j}}{\sum_{i=1}^{V} e^{z_i}}.
$$

Here $x_L$ is the stream after the last block, $z$ is the row of $V$ logits, $z_j$ is the logit for token $j$, and the sum runs over the whole vocabulary of $V = 32{,}000$ tokens. A toy case has a three-token vocabulary of "cat", "dog", and "the", a final normalized vector $(1, 2)$, and output columns $(0, 1)$, $(0.6, 0.2)$, and $(0.1, 0)$. The logits are $0 + 2 = 2.0$, $0.6 + 0.4 = 1.0$, and $0.1$. Exponentials are 7.389, 2.718, and 1.105, which sum to 11.212, so the probabilities are 0.659, 0.242, and 0.099. If the true next token is "cat", the training loss for this position is $-\ln 0.659 = 0.417$, and [Language Modeling](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/) develops that cross-entropy loss and the softmax in full.

**Weight tying** reuses the embedding table as the output matrix, since both map between tokens and $d$-number vectors. It saves $V \times d$ parameters, which is 131,072,000 in the [reference Llama 2 model](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/#reference-llama-2-model). That is only 1.9% of the model, and Llama 2 keeps them separate. GPT-2 small has $V = 50{,}257$ and $d = 768$. There the same table is 38.6 million of about 124 million parameters, roughly 31%. That is why small models usually tie. The head's arithmetic is $2 \times 4{,}096 \times 32{,}000 = 262$ million operations per token, under 2% of the forward pass computed in the [FLOPs per token](#flops-per-token) section.

## Parameter counting

Counting parameters is bookkeeping over matrix shapes. A matrix with 4,096 rows and 11,008 columns holds 45,088,768 numbers, the product of the two. The model's total is the sum over every matrix and every normalization gain. The [reference Llama 2 model](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/#reference-llama-2-model) has $L = 32$ blocks, width $d = 4{,}096$, vocabulary $V = 32{,}000$, and SwiGLU hidden width $d_{\text{ff}} = 11{,}008$. Its parameters count as follows.

1. The input embedding has one row per vocabulary entry, giving $32{,}000 \times 4{,}096 = 131{,}072{,}000$.
2. Attention in one block has four $d \times d$ matrices for queries, keys, values, and output, giving $4 \times 4{,}096^2 = 67{,}108{,}864$.
3. The SwiGLU FFN in one block has three matrices of $d \times d_{\text{ff}}$, giving $3 \times 4{,}096 \times 11{,}008 = 135{,}266{,}304$.
4. The two RMSNorm gains in one block give $2 \times 4{,}096 = 8{,}192$. One block totals $202{,}383{,}360$.
5. All 32 blocks come to $32 \times 202{,}383{,}360 = 6{,}476{,}267{,}520$, the final RMSNorm adds 4,096, and the untied output head adds another 131,072,000.
6. Add the four parts:

   $$
   131{,}072{,}000 + 6{,}476{,}267{,}520 + 4{,}096 + 131{,}072{,}000 = 6{,}738{,}415{,}616.
   $$

   That is about 6.74 billion. The weights are stored in [bf16](/tutorials/llm-fundamentals/pretraining-at-scale/#mixed-precision), a 16-bit number format with 2 bytes per number. They take 13.48 GB, or 12.55 GiB in binary gigabytes of $2^{30}$ bytes.

![Parameter breakdown](/images/llm-fundamentals/15d-parameter-breakdown.png)

A quick estimate drops embeddings and norms and uses $4d^2$ for attention plus $8d^2$ for the feed-forward network (FFN), giving $N \approx 12 L d^2$. For the reference model that is $12 \times 32 \times 4{,}096^2 = 6{,}442{,}450{,}944$, about 4.4% below the exact count. Of that 296 million gap, 262 million is the two embedding tables, 33.6 million is SwiGLU's rounding from 10,922.7 to 11,008, and the norms add the last 0.27 million. The estimate works well for large models and badly for small ones, where embeddings are a big share. The GPT-2 small example in the [output head](#the-output-head) section showed this. Two common changes break the $4d^2$ attention term. In grouped-query attention, groups of query heads share one key head and one value head. With 8 such groups, the key and value matrices shrink to $d \times 1{,}024$ each. A mixture of experts multiplies the FFN term, as the [mixture of experts](#mixture-of-experts) section shows.

## FLOPs per token

Parameter count says how much memory the weights need, and a separate count says how much arithmetic each token costs. A **FLOP**, or floating-point operation, is one addition or multiplication on a decimal number. Multiplying a token's vector by a $d \times d$ matrix takes $d^2$ multiplications and about $d^2$ additions, so every weight is used for about 2 FLOPs per token. The **forward pass** computes the output from the input. It therefore costs about $2N$ FLOPs per token, where $N$ is the parameter count. For the [reference Llama 2 model](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/#reference-llama-2-model) that is $2 \times 6.74 \times 10^9 = 13.5$ GFLOPs, where one GFLOP is a billion FLOPs.

The $2N$ rule leaves out attention's own arithmetic, which has no weights. A token at position $t$ compares its query with $t$ keys and averages $t$ values, about $4td$ FLOPs per block across all heads. The **context length** $n$ is the number of tokens the model reads at once. Averaged over a causal sequence of that length, this adds about $2Lnd$ per token. At $n = 4{,}096$ that is $2 \times 32 \times 4{,}096 \times 4{,}096 = 1.07$ GFLOPs, 7.4% of the forward pass. The two terms are equal when $n = N/(Ld) \approx 51{,}400$ tokens, so for this shape the weights dominate until contexts get long, and attention then grows linearly per token while the weight term stays fixed.

![Flops versus context](/images/llm-fundamentals/15d-flops-versus-context.png)

</details>

The **backward pass** computes gradients and costs about twice the forward pass. For each matrix multiplication it needs two more of the same size, one giving the gradient for the layer's input so the signal can continue to earlier layers and one giving the gradient for the weights so they can be updated. Training per token is therefore $2N + 4N = 6N$, which is 40.4 GFLOPs per token for the reference model. Over a training run of $D$ tokens this becomes the $6ND$ rule. For 2 trillion tokens that is $8.09 \times 10^{22}$ FLOPs, which [Pretraining](/tutorials/llm-fundamentals/pretraining-at-scale/) turns into days on graphics processors. Some runs save memory by recomputing intermediate results during the backward pass instead of storing them. That adds roughly one more forward pass, bringing the total to about $8N$, so real runs often count more.

Almost every parameter in the model is a weight inside a matrix multiplication, so one small layer shows where the count comes from. Take a layer with 6 weights that turns a 3-number input into a 2-number output, $y = Wx$:

$$
W = \begin{bmatrix} 1 & 0 & 2 \\ 0 & 1 & 1 \end{bmatrix}, \quad x = \begin{bmatrix} 1 \\ 2 \\ 3 \end{bmatrix}
$$

**Forward pass, 2 FLOPs per weight.** Each output is a dot product, $y_1 = 1\cdot1 + 0\cdot2 + 2\cdot3 = 7$ and $y_2 = 0\cdot1 + 1\cdot2 + 1\cdot3 = 5$. Every weight is used in exactly one multiplication, and each product is then added into a running sum. That is 6 multiplications and 4 additions here. In a real layer each output sums thousands of products, so there is one addition per multiplication and the count is 2 FLOPs per weight.

The backward pass starts from the gradient of the loss with respect to the layer's output, and it has two separate jobs. Here that gradient is $\partial L/\partial y = (1, -1)$.

**Gradient for the input, 2 more FLOPs per weight.** The earlier layers need to know how the loss changes with $x$, so the signal can keep flowing down. That is $W^\top$ times the output gradient:

$$
\frac{\partial L}{\partial x} = W^\top \frac{\partial L}{\partial y} = \begin{bmatrix} 1\cdot1 + 0\cdot(-1) \\ 0\cdot1 + 1\cdot(-1) \\ 2\cdot1 + 1\cdot(-1) \end{bmatrix} = \begin{bmatrix} 1 \\ -1 \\ 1 \end{bmatrix}
$$

This is a second matrix multiplication with the same 6 weights. Each weight again takes part in one multiplication and one addition.

**Gradient for the weights, 2 more FLOPs per weight.** The optimizer needs to know how the loss changes with each weight. Weight $W_{ij}$ links input $j$ to output $i$, so its gradient is the product of the two, $\partial L/\partial y_i \times x_j$:

$$
\frac{\partial L}{\partial W} = \frac{\partial L}{\partial y}\, x^\top = \begin{bmatrix} 1 & 2 & 3 \\ -1 & -2 & -3 \end{bmatrix}
$$

That is one multiplication per weight for this token. A batch holds millions of tokens, and each weight's gradient is the sum of its products over all of them, so every token adds one multiplication and one addition per weight.

Adding the three parts gives $2 + 2 + 2 = 6$ FLOPs per weight per token. The forward pass is a third of the work, and the backward pass is the other two thirds because it runs two multiplications of the same size as the forward one. Summed over every weight in the model, a token costs $6N$, and $D$ tokens cost $6ND$. For the reference model that is $2N = 13.5$ GFLOPs forward and $4N = 27.0$ GFLOPs backward, 40.4 GFLOPs per token in all.

The rule is approximate, and its gaps are worth knowing:
- **The optimizer update is too rare to count.** AdamW does a few dozen operations per parameter, but once per step rather than once per token. With about 4.2 million tokens per step, its share per token is a few millionths of a FLOP per parameter.
- **Attention scores are left out.** Comparing queries with keys and averaging values has no weights, so $6N$ misses it. The attention deep dive earlier in this section puts it at 7.4 percent of the forward pass at 4,096 tokens, and the share grows with context length, as [attention cost against the feed-forward network](/tutorials/llm-deep-dive/efficient-attention-mechanisms/#attention-cost) in LLM Deep Dive follows out to 128K tokens.
- **The input embedding does no arithmetic.** A lookup copies one row and multiplies nothing. Its 131 million parameters are about 2 percent of $N$, so they make $6N$ a slight overcount. Some scaling studies leave embeddings out of $N$ for this reason.
- **For a mixture of experts, $N$ is the active count.** Only the weights a token actually multiplies cost FLOPs, so a model that stores 46.7 billion parameters but routes each token through 12.9 billion trains at about $6 \times 12.9$ billion FLOPs per token. [Total and active parameters](/tutorials/llm-deep-dive/mixture-of-experts-at-scale/#total-and-active-parameters) in LLM Deep Dive works through that gap.
- **Recomputation is extra work that the count ignores.** Runs that save memory by redoing the forward pass spend about $8N$ per token, but [model FLOPs utilization](/tutorials/llm-fundamentals/pretraining-at-scale/#the-compute-budget) still credits only $6N$, because the extra $2N$ produces nothing new. LLM Deep Dive covers the trade in [activation memory and recomputation](/tutorials/llm-deep-dive/numerics-and-training-stability/#activation-recomputation) and the utilization that real clusters reach in [model FLOPs utilization and the step time budget](/tutorials/llm-deep-dive/distributed-training-and-parallelism/#model-flops-utilization).

At inference there is no backward pass, so generating or scoring a token costs about $2N$, a third of a training token.

</details>

FLOPs set the cost of training and of processing a long prompt, but generating one token at a time is usually limited by reading the 13.48 GB of weights from memory instead, which [Inference](/tutorials/llm-fundamentals/inference-and-decoding/) works through.

## Mixture of experts

A dense model runs every parameter for every token, so making it know more also makes every token cost more. A **mixture of experts**, or [MoE](/tutorials/llm-deep-dive/mixture-of-experts-at-scale/#total-and-active-parameters), breaks that link by running only part of the feed-forward network (FFN) for each token, following [Shazeer et al.](https://arxiv.org/abs/1701.06538) and [Switch Transformer](https://arxiv.org/abs/2101.03961). Each MoE layer keeps $E$ separate FFNs, each called an **expert**, and a small learned $d \times E$ matrix called the **router** scores the experts for each token. **Top-k routing** keeps the $k$ highest-scoring experts, renormalizes their router probabilities $p_e$ to sum to 1, and returns the weighted sum of their outputs. Mixtral renormalizes this way, though some models skip that step. Attention, norms, and embeddings stay shared.

![Mixture of experts layer](/images/llm-fundamentals/15d-mixture-of-experts-layer.png)

For this token the router's probabilities are 0.61, 0.22, 0.14 and 0.03, and top-2 routing keeps the first two. Together they hold 0.83 of the probability. Dropping experts 3 and 4 discards the 0.17 the router gave them, and dividing the kept pair by their sum turns 0.61 and 0.22 into 0.731 and 0.269. The token then pays for two experts' arithmetic out of four, half the feed-forward cost of running all of them, while all four sit in memory. The choice is a hard cut. Expert 3 at 0.14 was not far behind expert 2 at 0.22, and a slightly different token vector could swap them and send the token through entirely different weights. Everything outside the experts stays as it was. The mixed output is added to the residual stream exactly as a dense feed-forward network's output would be, so attention, the norms and the blocks above need no change.

The router is the only new piece of arithmetic. Each of its $E$ columns acts like a learned direction, and a token's score for expert $e$ is the dot product of the token's normalized stream vector with column $e$, so tokens whose vectors point the same way tend to land on the same experts. A softmax turns the $E$ scores into probabilities, and those probabilities also weight the experts' outputs, which is how the router learns. When a chosen expert's weighted output lowers the loss, training raises that expert's score for similar tokens, and when it raises the loss, training lowers it. The experts that were not chosen get no gradient from this token at all.

The gain comes from giving different tokens different weights. A dense FFN serves every token with one set of weights. An MoE layer with $E$ experts holds $E$ times as many FFN parameters, while each token still multiplies only $k$ of them. With 8 experts the size of the dense FFN and top-2 routing, the layer stores 8 times the dense FFN's weights and does twice its arithmetic per token. Across the whole model the ratios are smaller, because attention, norms and embeddings stay shared, as the count at the end of this section shows. The name suggests experts on topics such as biology or law. The [Mixtral](https://arxiv.org/abs/2401.04088) authors looked for such a split and found little of it. ArXiv papers, biology abstracts and philosophy papers used the experts in very similar proportions, and the routing followed syntax more than subject, with indentation tokens in Python code always going to the same experts. The costs mirror the gain. Every expert must sit in memory even though most are idle for any one token, and routing only pays off if tokens spread across the experts, which the worked example below shows does not happen on its own.

Left alone this imbalance worsens, because a busier expert trains faster and attracts still more tokens, until a few experts take everything. A **load balancing loss** keeps the experts in use. It is an extra training penalty that grows when assignments are uneven, and Advanced Topics derives it along with the capacity limits that drop overflow tokens.

The payoff and the cost show up in two counts. **Total parameters** are every weight stored, which sets memory. **Active parameters** are the weights one token actually multiplies against, which sets FLOPs. A concrete case swaps the [reference Llama 2 model](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/#reference-llama-2-model)'s FFN for 8 SwiGLU experts of the same size, routed top-2. Each expert holds 135,266,304 parameters, and the router adds $4{,}096 \times 8 = 32{,}768$ per block. Total parameters become 37.04 billion, which is 74.1 GB in bf16. Active parameters are 11.07 billion, so each token costs about $2 \times 11.07 = 22.1$ GFLOPs forward. The model stores 5.5 times the dense model's weights for 1.6 times its arithmetic. Mixtral 8x7B from [Jiang et al.](https://arxiv.org/abs/2401.04088) has 46.7 billion total and 12.9 billion active. Modern LLM Architectures covers how much quality the extra storage actually buys, which is less than the storage ratio.

## Architecture families
The same blocks can be wired three ways, and the wiring decides what the model can be trained to do. Each family pairs an attention pattern with an objective, the prediction task whose error training minimizes. The original Transformer from [Attention Is All You Need](https://arxiv.org/abs/1706.03762) was built for machine translation and used two stacks. An encoder read the source sentence, and a decoder wrote the translation while attending to it. The families that followed either kept both stacks or kept only one of them. An **encoder-only** model lets every token see every other token. It trains with **masked language modeling**, hiding about 15% of tokens and predicting them. [BERT](https://arxiv.org/abs/1810.04805) is built this way. A decoder-only model uses a [causal mask](/tutorials/llm-fundamentals/attention-and-positional-information/#the-causal-mask) so each token sees only earlier ones. It trains with **causal language modeling**, predicting the next token at every position. GPT and Llama are built this way. An **encoder-decoder** model keeps the original design, as [T5](https://arxiv.org/abs/1910.10683) does. It reads a source with a bidirectional encoder and writes the output with a causal decoder that also uses **cross attention**, attention whose queries come from the output and whose keys and values come from the encoded source. T5 trains with **span corruption**, replacing random runs of tokens with placeholder markers and generating the missing runs. A **prefix LM**, or prefix language model, is a decoder-only model that reads its first part bidirectionally and generates the rest causally. That first part is called the prefix.

The objectives differ sharply in how much signal one sequence gives. In a 512-token sequence, masked modeling yields about $0.15 \times 512 \approx 77$ predictions, while causal modeling yields about 512, one per position. T5's span corruption with spans averaging 3 tokens yields the same 77 hidden tokens in about 26 spans. Decoder-only models came to dominate general-purpose large language models for four connected reasons. They extract a learning signal from every token. One objective serves every task through prompting, since any task can be written as text to continue. Generation streams naturally one token at a time while reusing stored results for earlier tokens. With a single stack there are fewer design choices to scale. [Wang et al.](https://arxiv.org/abs/2204.05832) found causal decoders best for zero-shot use after plain pretraining on raw text. Zero-shot means tasks given without examples. Encoder-decoders and other models that read their input bidirectionally and train with masked modeling did better after multitask fine-tuning, meaning further training on many labeled tasks. So the win is about the general-purpose use case rather than every task.

| Situation | Choice | Main qualification |
|---|---|---|
| General assistant, open-ended generation, prompting with a few examples | Dense decoder-only | Cost per token grows with every parameter |
| Embeddings, retrieval, or classification at low latency | Encoder-only | Cannot generate text |
| Fixed input mapped to a different output, such as translation or speech | Encoder-decoder | Two stacks to scale and serve |
| Quality per FLOP matters and memory across many graphics processors is available | Decoder-only mixture of experts | Memory follows total parameters and needs load balancing |
| One graphics processor or an edge device with tight memory | Small dense decoder-only | Lower ceiling on quality |

At staff level the choice between a dense model and a mixture of experts gets decided by an experiment with a stated exit. The experiment fixes a training budget in FLOPs, trains both at that budget on the same data, and compares quality alongside serving cost per million tokens at the expected batch size. A good decision record writes the reversal condition down before the run, for instance that the dense model ships if serving memory or the communication between graphics processors holding different experts makes the mixture's cost per token higher at equal quality.
