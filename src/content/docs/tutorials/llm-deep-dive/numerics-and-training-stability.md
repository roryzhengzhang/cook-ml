In bf16, 256 plus 1 is 256. The format keeps 8 significant bits, so between 256 and 512 it can only store even numbers, and 257 rounds back to 256. No error is raised and no warning appears. The [reference 7B model](/tutorials/llm-deep-dive/#scale-reference-models) takes about 477,000 optimizer steps, and each step performs about $1.7 \times 10^{17}$ multiplications and additions, every one rounded to some format. A large run spreads that arithmetic over thousands of GPUs, and at that scale some piece of hardware stops working every few hours.

**Numerics** is the study of what those roundings do to a computation. It asks which values a number format can hold, how much error each operation adds, and where the error piles up. **Training stability** is the separate question of whether the loss keeps falling smoothly or jumps, stalls and diverges. Some failures are pure numerics, such as a gradient too small for fp16 that becomes exactly zero. Others start as growth inside the model, such as attention scores that keep getting larger, and the number format only decides how soon that growth turns into a visible spike. The numerics side starts from one comparison, between the values each format can hold and the values each part of a training run produces.

![Format ranges](/images/llm-deep-dive/16d-format-ranges.png)

Two properties of a format decide where it can be used. The exponent bits set its range, and the mantissa bits set its precision. bf16 keeps fp32's 8 exponent bits and gives up mantissa, so every band of training values fits inside it, from single-weight gradients near $10^{-10}$ to rare activation outliers near $10^{3}$. fp16 makes the opposite trade. Its smallest value is $6 \times 10^{-8}$, so the smallest gradients round to exactly zero, which is the problem loss scaling solves. Range is not the only limit. An AdamW update late in the schedule can be 0.15% of its weight, as the [rounding error](#rounding-error) section works out, and bf16 drops any change below about 0.2% of a number even when both numbers sit well inside its range. That is why master weights stay in fp32. The FP8 formats run short of range itself. E4M3 holds full precision only from 0.0156 to 448, about 15 powers of two, while activations alone span six powers of ten, about 20 powers of two. No fixed placement covers that spread, so a tensor stored in FP8 is first multiplied by a scale factor that slides its values into the window.

The sections climb from single numbers to a whole cluster, and each level rests on the one below. The first group works on single values. It lays out the bits, then measures the error that long sums and weight updates collect, which decides where a run still needs fp32. Loss scaling and FP8 scaling follow from the range gaps above, and the 4-bit formats carry the same block-scaling idea further. Activation recomputation comes next as the other lever on memory, trading extra arithmetic for space instead of bits. The middle sections turn from rounding to the model's own dynamics. Attention and output logits can grow until softmax saturates, and the precision limits of the first group decide how soon that growth turns into a spike. Gradient clipping, the small constants in denominators, warmup and the Muon optimizer all control the size of each update, and hyperparameter transfer asks how those settings should change as the model gets wider or the batch grows. The last sections leave the model for the cluster, where hardware failures stop a synchronous run every few hours and checkpoints are sized against that rate. A closing table ties the earlier sections to the loss spikes they produce, so a spike can be traced back to its cause.

## Floating point formats
A floating point number is scientific notation in base two, and its format decides how far apart neighbouring values are at every size. [bf16](/tutorials/llm-fundamentals/pretraining-at-scale/#mixed-precision) and fp16 were introduced as bit counts in Fundamentals. Here the layout is used to compute exactly what each format stores. A value is built from three fields:

$$
x = (-1)^{s} \times 2^{\,E - b} \times \left(1 + \frac{f}{2^{m}}\right)
$$

Here $s$ is the sign bit, $E$ is the stored exponent read as an unsigned integer, $f$ is the stored mantissa read as an integer, and $m$ is the number of mantissa bits. The **exponent bias** $b$ is a fixed offset that lets an unsigned field hold negative powers, so bf16 with $b = 127$ stores $2^0$ as $E = 127$. Within one power of two, from $2^e$ up to $2^{e+1}$, the format holds $2^m$ evenly spaced values, so the gap between neighbours is $2^{e-m}$. The gap just above 1 is $2^{-m}$. It is called **machine epsilon**, and it measures relative precision. A value can be off by up to half a gap, a relative error of $2^{-m-1}$.

The exponent field $E = 0$ is reserved for **subnormal numbers**. These drop the leading 1 and spread $2^m$ values evenly between zero and the smallest normal number. They extend the range downward at the cost of significant bits (the lighter bars in the opening figure). Results are rounded with **round to nearest even**. A value goes to the closer grid point, and an exact tie goes to the neighbour whose mantissa ends in 0, so ties do not all push the same way.

| Format | Sign, exponent, mantissa bits | Bias | Largest value | Smallest normal | Smallest subnormal | Gap above 1 |
|---|---|---|---|---|---|---|
| fp32 | 1, 8, 23 | 127 | $3.4\times10^{38}$ | $1.2\times10^{-38}$ | $1.4\times10^{-45}$ | $1.2\times10^{-7}$ |
| bf16 | 1, 8, 7 | 127 | $3.4\times10^{38}$ | $1.2\times10^{-38}$ | $9.2\times10^{-41}$ | 0.0078 |
| fp16 | 1, 5, 10 | 15 | 65,504 | $6.1\times10^{-5}$ | $6.0\times10^{-8}$ | 0.00098 |
| FP8 E5M2 | 1, 5, 2 | 15 | 57,344 | $6.1\times10^{-5}$ | $1.5\times10^{-5}$ | 0.25 |
| FP8 E4M3 | 1, 4, 3 | 7 | 448 | 0.0156 | 0.00195 | 0.125 |
| FP4 E2M1 | 1, 2, 1 | 1 | 6 | 1 | 0.5 | 0.5 |

The two 8-bit formats split their bits differently, as standardized in [FP8 Formats for Deep Learning](https://arxiv.org/abs/2209.05433). **FP8 E4M3** keeps an extra mantissa bit for precision, and **FP8 E5M2** keeps fp16's exponent range. The 4-bit E2M1 format can hold only zero and plus or minus 0.5, 1, 1.5, 2, 3, 4 and 6, fifteen distinct values in all.

IEEE-style formats reserve the all-ones exponent for infinity and "not a number" (NaN). E5M2 follows that rule, so its top exponent field is 30, which means $2^{15}$. With the largest mantissa 1.75 it reaches $1.75 \times 2^{15} = 57{,}344$. E4M3 would keep too little range that way, so it has no infinity and reserves only the single pattern of all ones in both fields for NaN. Its top exponent then means $2^{15-7} = 2^8$ with mantissas up to 1.75, and $1.75 \times 256 = 448$. Conversions into E4M3 usually saturate, turning an overflow into 448 rather than NaN.

## Rounding error
A single rounding loses at most half a gap, but a long chain of additions can lose far more, because each partial sum is rounded before the next term arrives. **Swamping** is the case where a small term is added to a much larger total and vanishes because it is smaller than half the total's gap. Adding 0.01 a thousand times shows how far this goes. The true answer is 10, but a bf16 running sum stops at 4.0. From 4 upward the gap between bf16 numbers is 0.03125, so half the gap is 0.0156, and every further 0.01 rounds away.

The error is not random before the stall either. Between 1 and 2 the gap is 0.0078, and each 0.01 rounds down to one gap, so the sum lags the truth. Between 2 and 4 the gap is 0.0156, and each 0.01 rounds up to one gap, so the sum runs ahead. Within each stretch every rounding leans the same way, so the errors add up instead of cancelling. The stall point follows a simple rule. At the bottom of each power of two, half the gap is $2^{-8}$ of the total, so a bf16 sum of equal terms stops growing at the first power of two above 256 times the term. For 0.01 that is 4, since 2.56 lies between 2 and 4.

![Bf16 swamping](/images/llm-deep-dive/16d-bf16-swamping.png)

Matrix multiplication is exactly this kind of sum. One output of a 7B projection adds 4,096 products, and in bf16 the later products would be swamped by the partial sum. GPU tensor cores therefore take bf16 or FP8 inputs but keep the running sum in fp32 and round only the finished result. That is the dashed line in the figure. The same reasoning keeps every long reduction wide, including the softmax normalizer, the loss averaged over millions of tokens, the statistics inside [RMSNorm](/tutorials/llm-fundamentals/the-transformer-block-and-model-anatomy/#layer-normalization-and-rmsnorm), gradients summed over micro-batches, and in many stacks the sum of gradients across GPUs.

The weight update is the other place precision is lost, and it is why mixed precision keeps [master weights](/tutorials/llm-fundamentals/pretraining-at-scale/#optimizer-memory) in fp32. A bf16 number ignores any change smaller than half its gap. Half the gap is between $2^{-9}$ and $2^{-8}$ of the number's own size, roughly 0.2% to 0.4%. An AdamW step moves a weight by about the learning rate, so a weight of 0.02 at a late-schedule rate of $3 \times 10^{-5}$ changes by 0.15% and stays frozen if stored only in bf16. In fp32 the threshold is about $6 \times 10^{-8}$ of the weight's size, and the step registers.

Two cheaper alternatives drop the fp32 copy and keep the weights in bf16. **Stochastic rounding** rounds up or down at random with probabilities set by the distance to each neighbour, so the stored value is right on average. A weight of 1.0 receiving an update of 0.001 sits $0.001/0.0078125 = 12.8\%$ of the way to the next bf16 value, so it rounds up with probability 0.128, and after 100 such updates its expected value is 1.1 rather than a frozen 1.0. **Kahan summation** keeps a second bf16 number per weight that stores the part of each update lost to rounding and adds it back on the next step, so it saves 2 of the 4 bytes where stochastic rounding saves all 4. Large pretraining runs mostly still pay the 4 bytes for fp32 master weights, since sharding spreads that memory across GPUs ([Parallelism](/tutorials/llm-deep-dive/distributed-training-and-parallelism/)).

## Loss scaling
fp16 has three more mantissa bits than bf16 but stops at 65,504 at the top and $6 \times 10^{-8}$ at the bottom. The gradient of a single weight in a large model is often $10^{-8}$ or smaller, which is below that floor. In plain fp16 those gradients round to exactly zero, and their weights stop learning without any error. **Loss scaling** multiplies the loss by a factor $S$ before the backward pass. By the chain rule this multiplies every gradient by $S$ and lifts the small ones into range. Gradients are divided by $S$ in fp32 before the optimizer uses them.

Scaling works because multiplying every gradient by the same factor shifts the whole spread along a log scale without making it wider. fp16 covers about 40 powers of two, from its smallest subnormal $2^{-24}$ up to 65,504, which is just under $2^{16}$. The job of $S$ is to slide the gradients into that window. A spread from $2 \times 10^{-8}$ up to 1.2 is about 26 powers of two wide, so it fits with room to spare. Any $S$ from about 3,000 to 54,000 lifts the smallest gradient above fp16's smallest normal number and keeps the largest below 65,504. The smallest normal number is $6.1 \times 10^{-5}$, and above it a value keeps all ten mantissa bits. Too small an $S$ leaves the bottom of the spread in the subnormals or at zero, and too large an $S$ pushes the top past 65,504 to infinity. $S$ is often chosen as a power of two, such as 4,096 or 32,768. For normal values that stay within range, multiplying by a power of two changes the exponent without rounding the significand. As long as no value leaves the range, the scaled backward pass then rounds exactly as an unscaled one would, and dividing by $S$ recovers the same gradients with no added error.

A fixed $S$ is hard to choose, because the spread of gradients changes over the run, and one batch with an unusually large gradient moves the top of the spread up. **Dynamic loss scaling** extends the fixed scaling of [Micikevicius et al.](https://arxiv.org/abs/1710.03740) by adjusting $S$ automatically. It starts high, halves $S$ and skips the update whenever any gradient comes out as infinity or NaN, and doubles $S$ after a fixed number of clean steps to look for more headroom. PyTorch's default starts at $2^{16} = 65{,}536$, halves on overflow, and doubles after 2,000 clean steps.

## FP8 and microscaling
FP8 doubles the arithmetic rate of the tensor cores. Under this chapter's hardware assumption, an H100 SXM peaks at 1,979 TFLOP/s in FP8 against 989 in bf16, and FP8 activations stored for the backward pass take half the memory. The obstacle is the narrow window from the [floating point formats](#floating-point-formats) section. E4M3 holds 0.00195 to 448, while one tensor's values can span far more than that.

**Per-tensor scaling** fixes the window for each tensor separately. The **amax** is the largest absolute value in the tensor, and the scale is chosen so that the amax lands at the top of the format. Every value is multiplied by $448/\text{amax}$ before conversion to E4M3, and the matrix product is divided by the scales afterward. Finding the amax needs an extra pass over the tensor, so NVIDIA's [Transformer Engine](https://docs.nvidia.com/deeplearning/transformer-engine/examples/fp8_primer.html) introduced **delayed scaling**, which reuses the largest amax seen over recent steps. A scale computed from the current tensor would mean reading the whole tensor once to find its maximum and again to convert it, all before the matrix multiply can start. Delayed scaling converts with a scale already fixed from the amax history, records the current amax during the conversion, and adds it to the history for later steps. The price is a tensor that suddenly grows. If the history puts the amax at 10, the scale is $448/10 = 44.8$, and a new value of 20 scales to 896, past E4M3's top. A saturating conversion stores it as 448, so it comes back as 10 until the history catches up. That is half its true size. That recipe used E4M3 for weights and activations and the wider-range E5M2 for gradients.

One scale per tensor breaks down on outliers, and language model activations usually have a few channels hundreds of times larger than the rest. In this example, eight activations hold 0.020, −0.013, 0.007, 0.002, 0.031, −0.011, 0.004 and one outlier of 1,000. The per-tensor scale $448/1000 = 0.448$ pushes the small values into E4M3's subnormal range, where the step is 0.00195. After rounding and scaling back, 0.002 becomes 0. The value 0.007 becomes 0.0087, which is 25% high, and −0.011 becomes −0.0131, which is 19% off. Splitting the same eight values into two blocks of four with their own scales stores the first block within 2%, and only the block that holds the outlier still loses its small values.

**Fine-grained scaling** applies that block idea in production, and [DeepSeek-V3](https://arxiv.org/abs/2412.19437) documents a full recipe trained at 671B total parameters on 14.8 trillion tokens. Activations get one scale per tile of 1 by 128 values, which covers 128 channels of one token. Weights get one scale per block of 128 by 128. Scales are computed online from each tile's own maximum rather than delayed, and every tensor uses E4M3, since small blocks make E5M2's extra range unnecessary. The report also found that the H800's FP8 tensor cores keep only about 14 bits in their running sums. That is the swamping of the [rounding error](#rounding-error) section in hardware form, so partial sums are copied into fp32 registers every 128 products. With these changes the relative loss gap to a bf16 baseline stayed below 0.25%.

![Fp8 linear layer](/images/llm-deep-dive/16d-fp8-linear-layer.png)

The recipe follows one rule. FP8 goes where the arithmetic is, and wider formats go wherever values are summed or kept for long. Every linear layer runs three matrix multiplies. Fprop computes its output, Dgrad the gradient for its input and Wgrad the gradient for its weights. Each costs about $2N$ FLOPs per token, so together they make up the $6N$ of training, and running all three in FP8 moves almost all of training's arithmetic onto the faster FP8 path. The quantized activation is cached in FP8 for Wgrad and the quantized weight is reused by Dgrad, so each is converted once, and the stored activation takes half the memory it would in bf16.

Everything that accumulates stays wide. Products are summed in fp32, weight gradients are summed over micro-batches in fp32, and the master weights stay in fp32 because the [rounding error](#rounding-error) section showed that bf16 rounds away late-schedule updates. The AdamW moments can drop to bf16. A small relative error in a moment changes the step by a similarly small fraction, while the same error in a weight can be larger than the whole step. The parts left out of FP8 are cheap but sensitive. The embedding and the output head are a small share of the FLOPs, normalization statistics are long sums, the attention core runs a softmax over scores that the [logit growth](#logit-growth) section shows can grow large, and the MoE router makes a discrete choice that a small rounding error can flip to a different expert.

**Microscaling formats** build block scaling into the number format itself. The [OCP Microscaling specification](https://arxiv.org/abs/2310.10537) groups 32 values into a block that shares one 8-bit scale, stored as a pure power of two. MXFP8 uses E4M3 or E5M2 elements, and MXFP4 uses E2M1 elements, so each value costs $4 + 8/32 = 4.25$ bits. NVIDIA's **NVFP4** is supported in hardware on Blackwell GPUs. It uses smaller blocks of 16 values whose shared scale is an E4M3 number rather than a power of two, plus one fp32 scale per tensor. A value then costs $4 + 8/16 = 4.5$ bits, and the scale can fit the block more closely. Four-bit training has been shown at real scale. [NVIDIA trained a 12B model on 10 trillion tokens in NVFP4](https://arxiv.org/abs/2509.25149) with loss and downstream accuracy comparable to an FP8 baseline. In released models, [gpt-oss](https://arxiv.org/abs/2508.10925) ships its MoE expert weights in MXFP4 after post-training in that format. At 4.25 bits per parameter, this lets the 120B model fit on one 80 GB GPU. Quantizing a finished model for serving is a different problem, covered in [Serving Systems](/tutorials/llm-deep-dive/inference-systems-at-scale/).

## Activation recomputation
The backward pass needs intermediate results from the forward pass, and storing them can take more memory than the model's training state. A widely used published estimate comes from [Korthikanti et al.](https://arxiv.org/abs/2205.05198) of about 34 bytes per token per unit of width per layer. It is written $34\,sbh$ for $s$ tokens per sequence, $b$ sequences per micro-batch and width $h$. That count leaves out the attention score tables, which add $5\,as^2b$ bytes per layer for $a$ heads. They hold the softmax output, its dropout mask and the masked scores, each one number per pair of tokens per head.

For one 4,096-token sequence on the 7B, the first term is $34 \times 4{,}096 \times 4{,}096 = 0.57$ GB per layer, 18.3 GB over 32 layers. The score tables are $5 \times 32 \times 4{,}096^2 = 2.68$ GB per layer and 85.9 GB in total. Storing everything therefore takes 104.2 GB for a single sequence, more than an H100 holds before any weights. The constant 34 assumes a GPT-style layer with dropout, and a Llama-style layer without dropout and with SwiGLU comes out somewhat different, so these are teaching estimates.

![Activation memory](/images/llm-deep-dive/16d-activation-memory.png)

**Activation recomputation** discards intermediates in the forward pass and recomputes them during the backward pass. It is also called activation checkpointing, which is a different thing from the saved training checkpoints of the [fault tolerance](#fault-tolerance) section. Full recomputation keeps only each layer's input, which takes $2sbh = 33.5$ MB per layer or 1.07 GB in total. It reruns each layer's forward pass just before its backward pass, so only one layer's 0.57 GB is ever rebuilt at a time. Peak activation memory drops from 18.3 GB to about 1.6 GB. The cost is one extra forward pass. That adds $2N$ FLOPs per token on top of the $6N$ of training, so $8N/6N$ means 33% more arithmetic.

**Selective recomputation** recomputes only the attention core, the score tables and the weighted sum over values. Those tensors are 82% of the stored bytes but cheap to rebuild. Attention's own arithmetic is about $2Lsh = 1.07$ GFLOPs per token at this length against 40.4 GFLOPs for the rest of training, so the extra cost is about 2.5%. [FlashAttention](https://arxiv.org/abs/2205.14135) reaches the same point by design. It never writes the score tables to memory and recomputes them inside its backward kernel. Real runs combine these with sharding and offloading, which [Parallelism](/tutorials/llm-deep-dive/distributed-training-and-parallelism/) covers.

Recomputation also changes how efficiency is reported. [MFU](/tutorials/llm-fundamentals/pretraining-at-scale/#the-compute-budget) counts only the $6N$ FLOPs the model needs per token, while **hardware FLOPs utilization**, or HFU, counts what the GPU actually executes. A run at 40% MFU with full recomputation is at $40\% \times 8/6 = 53\%$ HFU, so HFU flatters a run that recomputes.

## Logit growth
Softmax turns scores into probabilities, and the same scores at nine times the size give a nearly one-hot result. A transformer has two softmaxes, the attention softmax in every layer and the output softmax over the vocabulary. Both are prone to this growth, and each has its own fix.

### Attention logits and QK-norm

An attention logit is a query-key dot product divided by $\sqrt{d_h}$, with the [square root scaling](/tutorials/llm-fundamentals/attention-and-positional-information/#square-root-scaling) that Fundamentals explained. Scaling fixes the size at initialization but not later. If training grows the projection matrices $W_Q$ and $W_K$, every logit grows with the product of their sizes. Logits of 2, 1 and 0 give attention weights 0.665, 0.245 and 0.090, with an entropy of 0.83 nats. If $W_Q$ and $W_K$ each grow threefold, the logits become 18, 9 and 0, and the weights become 0.99988, 0.00012 and 0.00000002, with an entropy of 0.001. This is **attention entropy collapse** ([Zhai et al.](https://arxiv.org/abs/2303.06296)). The slope of the winning weight with respect to its logit is $p(1-p)$. It falls from 0.223 to 0.00012, so the head can barely learn to spread its attention again. **Attention logit growth** of this kind destabilized an 8B-parameter vision transformer in [ViT-22B](https://arxiv.org/abs/2302.05442), and [Wortsman et al.](https://proceedings.iclr.cc/paper_files/paper/2024/hash/d848cb2c84f0bba7f1f73cf232734c40-Abstract-Conference.html) reproduced it in small language models by raising the learning rate.

**QK-norm** applies an RMSNorm with a learned gain to each head's query and key before the dot product. After normalization each vector has root mean square 1, so its length is $\sqrt{d_h} = 11.3$ for heads of width 128. The scaled logit can then be at most $11.3 \times 11.3 / 11.3 = 11.3$ times the two gains. Growth in $W_Q$ and $W_K$ no longer reaches the logits, and rotary position embedding keeps the bound, since a rotation keeps a vector's length. QK-norm is now standard in recent designs. [OLMo 2](https://arxiv.org/abs/2501.00656) uses it, [Qwen3](https://arxiv.org/abs/2505.09388) added it while removing the query, key and value biases of Qwen2, and the [Gemma 3 report](https://storage.googleapis.com/deepmind-media/gemma/Gemma3Report.pdf) says it replaced Gemma 2's soft-capping with QK-norm.

**Logit soft-capping** bounds logits smoothly instead, replacing each logit $z$ with $c \tanh(z/c)$. Small logits pass almost unchanged and large ones flatten toward $c$. [Gemma 2](https://storage.googleapis.com/deepmind-media/gemma/gemma-2-report.pdf) used $c = 50$ for attention logits and $c = 30$ for the final output logits, and with $c = 30$ a logit of 5 becomes 4.95, 20 becomes 17.48 and 60 becomes 28.92. **Output gating** changes what attention passes on rather than its logits. It multiplies each head's output by a sigmoid gate computed from the token's own input, and [Qiu et al.](https://arxiv.org/abs/2505.06708) report that it reduces extreme activations, tolerates larger learning rates and trains more stably. Norm placement matters too. OLMo 2 moved each RMSNorm from the sublayer's input to its output. This variant of the [pre-norm](/tutorials/llm-fundamentals/the-transformer-block-and-model-anatomy/#pre-norm-and-post-norm) layout stops one sublayer from writing a huge value into the residual stream. OLMo 2 reports that this reordering and QK-norm each did little alone but together reduced the growth and spikiness of gradient norms.

### Output logits and z-loss

The output softmax has a different weakness. Adding the same constant to every logit leaves the probabilities and the loss unchanged, so nothing in the cross entropy stops the logits drifting together, and [Wortsman et al.](https://proceedings.iclr.cc/paper_files/paper/2024/hash/d848cb2c84f0bba7f1f73cf232734c40-Abstract-Conference.html) call the resulting failure **output logit divergence**. Drift matters because of the [floating point formats](#floating-point-formats) section. In bf16 the gap between neighbouring numbers is 0.0156 near 2 but 4 near 1,000, so logits that drift far from zero lose the small differences that carry the prediction. The **z-loss** from [PaLM](https://arxiv.org/abs/2204.02311) adds a penalty on the log of the softmax normalizer $Z = \sum_i e^{z_i}$:

$$
\mathcal{L}_z = \alpha \,(\log Z)^2,
$$

where $z_i$ are the output logits and $\alpha = 10^{-4}$ in PaLM. The penalty is zero when $\log Z = 0$, which keeps the largest logit near zero. [Mixture of Experts](/tutorials/llm-deep-dive/mixture-of-experts-at-scale/) describes how MoE routers apply the same penalty to their scores.

## Gradient clipping
An unusually large gradient can make the optimizer take a step much larger than usual. [Gradient clipping](/tutorials/llm-fundamentals/pretraining-at-scale/#loss-spikes) limits that step by rescaling the gradient when its norm exceeds a threshold. The threshold is usually 1.0, and Llama 2 and DeepSeek-V3 both use 1.0. Its place in the step matters. The gradient is first summed across data-parallel GPUs, then divided by the loss scale if one is used, then measured. With sharded optimizers each GPU holds a slice, so the global norm needs one more all-reduce of a single number per GPU. Clipping comes last, just before the optimizer.

The clip rate is the fraction of steps on which clipping fires, and it is a cheap health signal. A healthy run clips occasionally, while a run that clips on most steps has a lower effective learning rate than its schedule says. A gradient norm that climbs over hundreds of steps often precedes a loss spike, so it warns earlier than the loss does, and some runs skip any update whose norm exceeds a multiple of its recent average.

Small constants in denominators cause a quieter set of problems. AdamW divides by $\sqrt{\hat v} + \epsilon$, and $\epsilon$ is meant only to prevent division by zero. Gradients with a root mean square of $10^{-9}$ are common in very large models. For such a weight $\sqrt{\hat v} \approx 10^{-9}$ and $\epsilon = 10^{-8}$ dominates the denominator, so the update is about $10^{-9}/1.1\times10^{-8} = 0.09$ of its intended size and Adam behaves like plain gradient descent for that weight. Wortsman et al. measured update sizes shrinking this way as models grew and found that shrinking $\epsilon$ to a much smaller value such as $10^{-15}$ restored them. Llama 2's $\epsilon = 10^{-5}$ damps any weight whose gradient root mean square is below about $10^{-5}$ in the same way.

Normalization layers have the same constant. RMSNorm divides by $\sqrt{\text{mean}(x^2) + \epsilon}$. For activations with a root mean square of 0.001, the mean square is $10^{-6}$, and $\epsilon = 10^{-5}$ makes the divisor $\sqrt{1.1 \times 10^{-5}} = 0.0033$ instead of 0.001, so the output is 0.30 of its intended size. Precision matters here too. In fp16, the square of 0.001 is $10^{-6}$, which is a subnormal with few significant bits. The square of 300 is 90,000, which overflows to infinity and turns the whole normalized vector into zeros. That is why normalization statistics are computed in fp32 even in FP8 recipes.

The embedding layer has its own failure. Each token's row of the embedding table receives a gradient only in batches that contain that token, and early in training these gradients can be large and erratic. [GLM-130B](https://arxiv.org/abs/2210.02414) multiplied the embedding layer's gradient by 0.1 to stop spikes it traced there, and [BLOOM](https://arxiv.org/abs/2211.05100) added a layer normalization right after the embedding for the same reason.

## Warmup and Muon
[Warmup](/tutorials/llm-fundamentals/pretraining-at-scale/#learning-rate-schedules) was justified in Fundamentals by Adam's first step, in which every weight moves by exactly the learning rate because $\hat v_1 = g_1^2$. The effect lasts longer than one step. For a weight whose gradient is mostly noise, the momentum $m$ averages random signs and settles at about $\sqrt{(1-\beta_1)/(1+\beta_1)} = 0.23$ of the gradient's typical size with $\beta_1 = 0.9$, while $\sqrt{\hat v}$ settles at the typical size itself. In steady state such a weight moves about 0.23 of the learning rate per step. In the first few steps, before $v$ has averaged many gradients, the ratio is close to 1, so noise-driven weights move about four times as far as they later will, all in directions set by a handful of batches.

The time $v$ needs to settle sets a natural warmup length. [Ma and Yarats](https://arxiv.org/abs/1910.04209) found that a linear warmup of $2/(1-\beta_2)$ steps works without tuning. That is 40 steps for $\beta_2 = 0.95$ and 2,000 for $\beta_2 = 0.999$, and [RAdam](https://arxiv.org/abs/1908.03265) builds a similar correction into the optimizer. Llama 2's 2,000-step warmup with $\beta_2 = 0.95$ is fifty times longer than that rule, so the rest of the reason is the early loss surface, which is sharply curved at initialization and flattens as the weights move away from their random start.

**Muon** replaces Adam's per-weight scaling with a step that treats each weight matrix as a whole ([Jordan et al.](https://kellerjordan.github.io/posts/muon/)). For every two-dimensional hidden matrix it keeps one momentum matrix $M$ and then orthogonalizes it. If $M = U\Sigma V^\top$ is its singular value decomposition, the update uses $UV^\top$, which sets every singular value to 1. A direction in which the gradients were small gets as large a step as the dominant direction. An exact decomposition is too slow, so Muon runs five steps of a **Newton-Schulz iteration**. The iteration first scales $X$ to unit size and then repeats the polynomial $X \leftarrow aX + b(XX^\top)X + c(XX^\top)^2X$ with $a = 3.4445$, $b = -4.7750$ and $c = 2.0315$. Each step is a few bf16 matrix multiplies. For a momentum matrix with singular values 3 and 0.1, scaling gives 0.9994 and 0.0333, and five steps give 0.70 and 1.13, so a direction thirty times weaker now gets a step of similar size. The coefficients trade exactness for speed, so the values land near 1 rather than on it.

Muon keeps one buffer instead of AdamW's two, so its training state is 12 bytes per parameter instead of 16. Embeddings, the output head and normalization gains still use AdamW. For the 7B that gives about 81.9 GB instead of 107.8 GB, and the Newton-Schulz products add roughly 0.4% to a 4-million-token step (teaching estimates, before sharding). Moonshot's [Muon is Scalable for LLM Training](https://arxiv.org/abs/2502.16982) added weight decay, rescaled each update so its root mean square matches AdamW's, and reported about twice the compute efficiency of AdamW in scaling experiments.

The same team then hit the attention logit growth of the [logit growth](#logit-growth) section at a larger scale. The [Kimi K2 report](https://arxiv.org/abs/2507.20534) found that a mid-scale Muon run reached maximum attention logits above 1,000, which tended to cause loss spikes. Its fix is called **QK-clip**. It tracks each head's largest pre-softmax logit $S_{\max}$ over the batch. After the optimizer step, it shrinks that head's query and key weights by $\sqrt{\tau / S_{\max}}$ each whenever $S_{\max}$ exceeds a threshold $\tau = 100$. A head whose largest logit reached 150 has both matrices multiplied by $\sqrt{100/150} = 0.816$, so its logits scale by 0.667 and the largest returns to 100. Muon combined with QK-clip is named **MuonClip**. It trained Kimi K2 on 15.5 trillion tokens with no loss spikes. Kimi K2 has about 1.04 trillion total and 32 billion active parameters. The maximum logits hit the cap of 100 early and fell back below it after about 30% of training.

## Hyperparameter transfer
Learning rates are tuned on small models because full-size sweeps are unaffordable. The usual setup is called **standard parameterization**, and under it the tuned value does not carry over. The best learning rate for hidden layers roughly halves each time the width doubles, because an update is built from the input it will be applied to.

In a small example, one row of a hidden matrix acts on an input whose $n$ coordinates are all 1. Adam's update moves each of the row's $n$ weights by about the learning rate $\eta$. Each moves in the direction that the input itself picked out, so all $n$ changes push the output the same way. With $n = 4$ and $\eta = 0.01$ the output moves by $4 \times 0.01 = 0.04$, and with $n = 8$ by 0.08. Random initial weights do not line up with the input, so their effect grows only as $\sqrt{n}$ and standard initialization corrects for that, but the aligned update grows as $n$. The same learning rate therefore makes a wider model take larger steps in function space, and past some width it diverges.

**muP** is the maximal update parameterization of [Yang et al.](https://arxiv.org/abs/2203.03466). It rescales each layer so that updates change activations by the same amount at every width. For Adam, the main rules are to scale hidden-layer learning rates by $1/n$ relative to a base width, so the width-8 row above gets $\eta = 0.005$ and moves the output by 0.04 again. The output logits are multiplied by $1/n$, attention logits are divided by $d_h$ rather than $\sqrt{d_h}$, and embedding learning rates stay fixed. The paper tuned hyperparameters on a 40-million-parameter proxy and transferred them to a 6.7B GPT-3 model. It beat the original GPT-3 6.7B at a tuning cost of 7% of its pretraining compute. [Cerebras-GPT](https://arxiv.org/abs/2304.03208) trained muP versions of its models to make their scaling more predictable.

![Mup learning rate transfer](/images/llm-deep-dive/16d-mup-learning-rate-transfer.png)

Under standard parameterization the best rate in the schematic falls from $2^{-7}$ at width 256 to $2^{-10}$ at width 2,048. That is the eightfold drop the $1/n$ argument above predicts for a model eight times wider, and it means a rate tuned on the narrow model puts the wide one far up the steep side of its curve. The curves also cross. At a large shared rate the widest model ends up worst, so comparing widths at one rate can even rank them backwards. Under muP the $1/n$ factor is built into each layer, so the best base rate stays in one place and the wider model is better at every rate. A sweep at width 256 is then enough, and each trial in it is cheap, since a hidden matrix of width 256 has $1/64$ the weights of one at width 2,048. muP covers width, so depth, batch size and training length still need their own rules or sweeps, and labs differ on how much of the recipe they adopt.

## Batch size and learning rate schedules

Averaging the gradient over more examples makes it less noisy. Once the batch is large enough that the noise is already small, making it larger barely helps. [McCandlish et al.](https://arxiv.org/abs/1812.06162) modeled this with the **gradient noise scale** $B_{\text{noise}}$, a batch size at which the noise in one gradient roughly equals the useful signal. Steps $S$ and training examples $E$ needed to reach a given loss then trade off as

$$
S = S_{\min}\left(1 + \frac{B_{\text{noise}}}{B}\right), \qquad E = E_{\min}\left(1 + \frac{B}{B_{\text{noise}}}\right),
$$

where $B$ is the batch size, $S_{\min}$ is the fewest steps possible with an unlimited batch and $E_{\min}$ the fewest examples possible with a tiny one. With $B_{\text{noise}} = 4$ million tokens, a batch of 1 million needs 5 times the minimum steps but only 1.25 times the minimum data. A batch of 4 million needs twice the minimum of each, and a batch of 16 million needs only 1.25 times the minimum steps but 5 times the minimum data. The **critical batch size** is the balance point near $B_{\text{noise}}$. Below it, doubling the batch nearly halves the number of steps, and above it, extra batch mostly wastes compute.

The simplest version is $B_{\text{noise}} = \operatorname{tr}(\Sigma)/\lVert G\rVert^2$, where $G$ is the true average gradient and $\Sigma$ is the covariance of single-example gradients. The trace $\operatorname{tr}(\Sigma)$ is then the total variance summed over parameters. A two-parameter case makes it concrete. If the average gradient is $(1, 0)$ and each example's gradient has variance 4 in each coordinate, then $\operatorname{tr}(\Sigma) = 8$ and $\lVert G\rVert^2 = 1$, so $B_{\text{noise}} = 8$ examples. A batch of 8 then has noise variance $8/8 = 1$, equal to the squared signal. Both can be estimated almost for free by comparing gradient norms at two batch sizes, such as one GPU's micro-batch and the full data-parallel batch. As the loss falls the signal shrinks faster than the noise, so $B_{\text{noise}}$ grows. [Kaplan et al.](https://arxiv.org/abs/2001.08361) fitted that growth as a power law in the loss.

</details>

Because the critical batch grows during training, large runs often grow the batch. GPT-3 raised its batch from 32 thousand tokens to the full size over the first 4 to 12 billion tokens, and DeepSeek-V3 raised its batch from 3,072 to 15,360 sequences over the first 469 billion tokens. The learning rate has to move with the batch. For Adam a square-root rule usually fits better than a linear one. Under it the rate doubles when the batch quadruples.

Schedules have moved toward the [warmup stable decay](/tutorials/llm-fundamentals/pretraining-at-scale/#learning-rate-schedules) shape. [Hägele et al.](https://arxiv.org/abs/2405.18392) found that a constant rate followed by a cooldown over the last 10% to 20% of training matches a tuned cosine schedule, and that branching cooldowns off one constant run gives finished checkpoints at many lengths. DeepSeek-V3 is a documented example. After 2,000 warmup steps it held $2.2\times10^{-4}$ until 10 trillion tokens, decayed along a cosine to $2.2\times10^{-5}$ over 4.3 trillion more, then held $2.2\times10^{-5}$ for 333 billion tokens and $7.3\times10^{-6}$ for the last 167 billion. The decay phase is also where most labs switch to their best data. MiniCPM and OLMo 2 describe this as the [mid-training](/tutorials/llm-fundamentals/pretraining-at-scale/#mid-training) or annealing stage.

**Checkpoint averaging** gets part of the benefit of decay without decaying, because at a high learning rate the weights bounce around the bottom of a valley. Take a one-weight loss $(\theta - 1)^2$ with the minimum at 1.0. Successive checkpoints might sit at 0.8 and 1.2, and each has loss $(0.2)^2 = 0.04$. Their average sits at 1.0 with loss 0. Averaging recent checkpoints cancels much of that bounce. This is the idea behind [stochastic weight averaging](https://arxiv.org/abs/1803.05407), and Hägele et al. found that averaging improves models along a constant-rate run. Llama 3 averaged checkpoints during its final annealing to produce the released base model. DeepSeek-V3 kept an exponential moving average of the weights in CPU memory to estimate what the model would score after decay, and it updated that average asynchronously after each step.

## Fault tolerance
A GPU fails rarely, but a run uses thousands of them, so the run as a whole fails often. The failure rate of a job grows in proportion to the number of GPUs it holds, so hardware that runs for years between problems on its own has a problem somewhere in a large cluster every few hours. The [Llama 3 report](https://arxiv.org/abs/2407.21783) gives the most detailed public numbers. In a 54-day snapshot of pretraining on up to 16,384 H100s it saw 466 job interruptions. Of these, 47 were planned and 419 unexpected, and the unexpected ones alone come to nearly eight a day. About 78% of the unexpected ones were confirmed or suspected hardware problems. GPU failures were the largest category at 58.7%, alongside host failures and **silent data corruption**. In silent data corruption, hardware returns wrong numbers without raising an error. Despite this the team reported more than 90% effective training time, and it handled all but three of the interruptions through automation without significant manual work. Effective training time is the share of elapsed time spent on useful training.

Every one of these failures stops the whole job, because training is synchronous. Each step ends in collectives such as the gradient all-reduce, which cannot finish until every GPU has sent its share. Under tensor and pipeline parallelism, each GPU holds the only copy of its slice of the weights and activations ([Parallelism](/tutorials/llm-deep-dive/distributed-training-and-parallelism/)). When one GPU stops, thousands of others wait inside a collective for data that never arrives, and the run cannot carry on without the missing slice. Each interruption therefore costs the work done since the last [checkpoint](/tutorials/llm-fundamentals/pretraining-at-scale/#loss-spikes) plus the time to restart.

The checkpoint has to hold everything that makes the step after a restart identical to the step that would have run without the failure. Most of its bytes are the fp32 master weights and Adam's two moments, 12 bytes per parameter. The bf16 working copy of the weights is left out, because rounding the master weights rebuilds it. A few small items matter just as much. The step count sets the learning rate in the schedule, the loss scale carries over in fp16 runs, the random number generator states fix dropout and any sampling, and the data loader's position says which batch comes next. Without that position the restarted run repeats data it has already seen or skips data it never saw. Writing a checkpoint pauses training, because the next step would change the weights while they are being written. The pause lasts as long as the write, so it grows with the model and shrinks with the bandwidth of the storage that every GPU writes to at the same moment.

How often to checkpoint is a trade between two kinds of waste. A checkpoint that pauses training for one minute, taken every 10 minutes, spends a tenth of the run writing. Taken once a day on a cluster that fails every few hours, it costs almost nothing to write, but each failure throws away half a day of work on average, since a failure is equally likely to land anywhere in the interval. The writing cost falls as the interval grows and the work lost per failure rises with it, so the total has a minimum in between. A faster checkpoint moves that minimum toward shorter intervals, which also cuts the work lost per failure.

**Asynchronous checkpointing** makes the checkpoint faster without faster storage, by splitting the write in two. Training pauses only while each GPU copies its shard of the state into the host's CPU memory. That copy is quick because the shard is a small fraction of the whole and it runs over the GPU's own link to its host. A background process then writes that frozen copy to storage while the GPU trains on. In [PyTorch's distributed checkpointing](https://pytorch.org/blog/reducing-checkpointing-times/), IBM's runs of a 7B model saw the pause per checkpoint fall from an average of 148.8 seconds to 6.3 seconds this way.

A training checkpoint's size and write speed set how often it can be taken, and the failure rate sets how often it should be.

Over the 11.8 days the 70B run takes at 40% MFU, that failure rate means about 11 or 12 interruptions, and each one has to be noticed before it can be fixed. A failed GPU rarely announces itself. More often the job hangs, with every other GPU waiting in a collective. NVLink is the link between GPUs inside one server. The Llama 3 team found that failures over NVLink often showed up as stalled operations with no clear error code. Their system therefore watches the communication library, times out any collective that stops making progress, and records which transfers between GPUs were still pending. Those pending transfers locate the GPU that stopped. A [straggler](/tutorials/llm-deep-dive/distributed-training-and-parallelism/#data-parallelism) raises no error at all and shows up only in per-GPU step times. Silent data corruption is the hardest case, since the job keeps running. The wrong numbers surface as a jump in the loss or the gradient norm, if they surface at all. Llama 3 traced 6 of its 419 unexpected interruptions to it.

Recovery restarts the whole job. The scheduler takes the faulty node out of the pool and swaps in a spare, every process is relaunched and rebuilds its communication groups, and each GPU reads its shard of the last complete checkpoint back from storage. The run then restores the step count, the random states and the data loader position. A loader that walks a fixed shuffled order from a saved seed needs only the number of batches already consumed to resume at the batch right after the checkpoint. A failure therefore costs half an interval of work on average plus the restart time, and the restart time is paid in full however short the interval is. Spare nodes kept ready and faster job startup shrink that second part, and reducing startup and checkpointing time is the first measure the Llama 3 team lists for raising its effective training time.

The asynchronous checkpointing of step 5 is now standard, and it comes with two conditions. Host memory has to hold a copy of each GPU's shard, and the background write has to finish before the next snapshot starts. At 10 GB/s the 827.7 GB write takes 83 seconds, well inside 7 minutes. Until a background write completes, the newest checkpoint is not yet safe on storage, so a failure during the write falls back to the one before it.

Writing a checkpoint every $\tau$ seconds of work spends $\delta$ seconds per interval, a fraction $\delta/\tau$. Failures arrive at rate $1/M$, and each one strikes at a uniformly random point of the current interval, so it loses $\tau/2$ of work on average, a fraction $\tau/(2M)$. The total $W(\tau) = \delta/\tau + \tau/(2M)$ has derivative $-\delta/\tau^2 + 1/(2M)$, which is zero at $\tau^\star = \sqrt{2\delta M}$. Substituting back gives $W(\tau^\star) = \sqrt{2\delta/M}$, here $\sqrt{2 \times 83/88{,}920} = 4.3\%$. Halving the checkpoint cost therefore cuts the waste only by a factor of $\sqrt{2}$. Daly refined the formula to account for failures during the write itself and for the restart time $R$. That gives roughly $\sqrt{2\delta(M+R)} - \delta$, which differs little when $\delta$ is small against $M$.

## Spike diagnosis
A loss spike looks the same whatever caused it, so diagnosis depends on signals logged before the spike. Those signals are the gradient norm per layer, the largest attention logit per head, $\log Z$ at the output, the loss scale or FP8 amax values, and the step time on every GPU. The table maps each pattern to its usual cause.

| Symptom | Likely cause | What to measure | Usual fix |
|---|---|---|---|
| Loss becomes NaN in the first few hundred steps | Learning rate too high for Adam's unsettled second moment, or fp16 overflow | Gradient norm and update size per step, loss scale history | Longer warmup, lower peak rate, bf16 instead of fp16 |
| One spike that recovers within a few hundred steps | A bad batch, such as long runs of one repeated token | Loss per batch and the data index at the spike | Skip the batch, roll back about 100 steps and skip a few hundred batches |
| Repeated spikes with the gradient norm climbing | Attention logit growth in a few heads | Largest attention logit per head over time | QK-norm, QK-clip, soft-capping or output gating, lower peak rate |
| Slow drift of $\log Z$ followed by divergence | Output logit divergence | Mean $\log Z$ and the largest output logit | z-loss near $10^{-4}$, final-logit soft-capping |
| fp16 run skips many steps | Loss scale too high for current gradients | Overflow count and scale history | Lower growth rate of the scale, or move to bf16 |
| FP8 run's loss pulls away from a bf16 baseline | Outliers crushed by coarse scaling, or narrow accumulation | Relative loss gap, amax per tensor, layers with the largest error | Smaller scaling blocks, fp32 accumulation, keep sensitive layers in bf16 |
| Loss flattens late while the rate is still nonzero | Updates rounded away or damped | Update-to-weight ratio, size of $\sqrt{\hat v}$ against $\epsilon$ | fp32 master weights, smaller Adam $\epsilon$ |
| Best learning rate changes when the model is widened | Standard parameterization | Learning rate sweeps at two widths | muP, or a fresh sweep at the target width |
| Steps slow down or the job stalls without a loss change | A failing GPU, straggling node or network fault | Step time per GPU, hardware error logs | Replace the node, restart from the last checkpoint |

Each row reads left to right as a hypothesis and its test. The symptom is what the loss curve or the job shows, the cause is the usual explanation for it, the measurement is the logged signal that confirms or rules that explanation out, and the fix is worth applying only once the measurement agrees. The first four rows are spikes and divergence that come from the learning rate, the data or the model's own logits. The next three are precision problems, which show up as skipped steps, a gap to a bf16 baseline or a loss that stops improving. The last two are not training dynamics at all, one a tuning setup and one the hardware. Two facts narrow the table quickly, when in the run the problem appears and whether it recurs at the same data position.

Most spikes in a well-configured run come from the data or from logit growth. A spike that recurs at the same data position points at the data, and one that recurs at random positions points at the model or the learning rate. Restarting from a checkpoint a few hundred steps before the spike and changing one thing at a time usually confirms the cause fastest.

A hypothetical case on the 70B run of the [fault tolerance](#fault-tolerance) section shows the table in use. Around step 120,000 the loss jumps from 1.9 to 2.6, recovers within 300 steps, and spikes again 900 steps later. The per-layer gradient norm had been climbing for about 2,000 steps before the first spike, and the two spikes fall at different data positions, which makes a bad batch unlikely and points at the third row. The first measurement is the largest attention logit per head. Most heads sit near 20, while three heads in late layers have climbed past 300, which confirms attention logit growth. QK-clip from the [warmup and Muon](#warmup-and-muon) section suits a run already in progress, because it only rescales existing query and key weights after each step, while QK-norm would add a normalization the weights were never trained with. The run restarts from a checkpoint saved before the climb began, and with asynchronous checkpoints about 200 steps apart one sits close to that point. With $\tau = 100$, a head at 300 has its query and key weights each multiplied by $\sqrt{100/300} = 0.577$, so its logits fall to a third and the largest returns to 100. Had both spikes landed at one data position and returned there after the rollback, the second row would apply instead, and skipping those batches would be the fix.
