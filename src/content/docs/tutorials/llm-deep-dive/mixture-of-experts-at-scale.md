The name Mixtral 8x7B suggests eight 7B models side by side, which would come to about 58 billion parameters. The model has 46.7 billion. Only the feed-forward network is copied eight times, while attention, the embeddings and the norms exist once. Even 46.7 billion overstates what any one token uses, because each token runs through 12.9 billion of them. The larger number decides how much memory the model needs and the smaller one decides how much arithmetic each token costs.

The [mixture of experts](/tutorials/llm-fundamentals/the-transformer-block-and-model-anatomy/#mixture-of-experts) basics are already in place. A router scores the experts, keeps the top two and mixes their outputs. The reference MoE is a model with Mixtral 8x7B's shape. This chapter follows it from that single routed token to thousands of tokens per step spread across many GPUs. There the gap between the two parameter counts turns into memory bills, idle GPUs and network traffic.

![Memory and compute](/images/llm-deep-dive/16e-memory-and-compute.png)

Memory and arithmetic come apart in an MoE because they follow different counts. Every weight has to be stored, so the reference MoE needs the same 93.41 GB as a dense model with all 46.7 billion parameters, more than one 80 GB H100 holds. Using six FLOPs per active parameter gives about 77.3 GFLOPs per training token for the weight operations. Attention, routing and communication affect the actual cost. That is 1.9 times the dense 7B's 40.4 GFLOPs and 3.6 times less than the dense 46.7B's 280.2. The factor of 3.6 is the ratio of total to active parameters, and it is what an MoE buys. At the compute cost of a 12.9B dense model it stores the parameters of a 46.7B one, and the [total and active parameters](#total-and-active-parameters) section shows that the extra stored parameters still buy quality, though less than their number suggests.

The memory bill does not shrink with sparsity. It is paid in full on the GPUs that hold the weights, and during training the optimizer state is eight times larger again. Balanced routing helps the arithmetic saving translate into lower wall-clock time. If most tokens went to the same two experts per layer, each token would still cost 12.9B parameters of arithmetic while the other experts sat in memory doing nothing, and the extra capacity would buy almost nothing.

The first two sections price the two parameter counts and open up the router, since every later problem starts from how it picks experts. Routing left to itself drifts toward a few favorite experts, so the middle of the chapter is about balance. It prices what imbalance costs in idle GPUs and unused experts, then compares three remedies. The auxiliary loss discourages imbalance through the gradient, the capacity limit caps it by dropping tokens, and the bias adjustment DeepSeek-V3 uses steers tokens without touching the loss. With balance in hand, a section on expert granularity asks how finely the expert capacity should be cut, with a table of current MoE designs. Smaller, more numerous experts send each token to more places once the experts leave a single GPU. That brings in the all-to-all exchange of expert parallelism, then the training instabilities that belong to routers, and upcycling a trained dense model into an MoE. The last two sections turn to serving, where every expert must stay in memory, and weigh when an MoE is worth its complexity.

## Total and active parameters

A mixture of experts stores many feed-forward networks and runs only a few of them for each token, so a single parameter count no longer describes it. Counting the reference MoE matrix by matrix shows where the parameters sit. Its 32 layers have width 4,096, 32 query heads and 8 key-value heads of width 128, and 8 [SwiGLU](/tutorials/llm-fundamentals/the-transformer-block-and-model-anatomy/#swiglu) experts per layer, of which each token uses 2.

1. Attention in one layer has two $4{,}096 \times 4{,}096$ matrices for queries and outputs and two $4{,}096 \times 1{,}024$ matrices for keys and values, which is 41,943,040 parameters.
2. One expert holds three matrices of $4{,}096 \times 14{,}336$, which is 176,160,768 parameters, and eight experts hold 1,409,286,144.
3. The router is a $4{,}096 \times 8$ matrix of 32,768 parameters, and the two norm gains add 8,192, so one layer holds 1,451,270,144.
4. Thirty-two layers hold 46,440,644,608. The embedding table and the output head add 131,072,000 each, and the final norm adds 4,096, for 46,702,792,704 in total.
5. A token uses only 2 experts per layer, so its count for one layer is

   $$
   41{,}943{,}040 + 2 \times 176{,}160{,}768 + 32{,}768 + 8{,}192 = 394{,}305{,}536.
   $$

   Over 32 layers plus the embeddings and the final norm that comes to 12,879,925,248 active parameters.

The experts hold 45.1 billion of the 46.7 billion parameters, 96.6% of the model. The **sparsity ratio** is total parameters divided by active parameters, which is $46.7/12.9 = 3.6$ here. Counting conventions differ slightly between reports. The count above includes the input embedding table as active, although a token only looks up one row of it. The gpt-oss model card leaves embeddings out of its active count.

Each count sets a different bill. Memory follows the total. The bf16 weights take $2 \times 46.7 = 93.41$ GB. Mixed-precision AdamW keeps 16 bytes per parameter, so the [optimizer state](/tutorials/llm-fundamentals/pretraining-at-scale/#optimizer-memory) alone is 747 GB, the memory of more than nine H100s before any activations. Arithmetic follows the active count. A forward pass costs $2 \times 12.88 = 25.8$ GFLOPs per token and training costs 77.3 GFLOPs per token. Over 2 trillion tokens that is $1.55 \times 10^{23}$ FLOPs, against $8.09 \times 10^{22}$ for the reference 7B and $5.60 \times 10^{23}$ for a dense model with all 46.7 billion parameters. The [compute budget](/tutorials/llm-fundamentals/pretraining-at-scale/#the-compute-budget) of the MoE therefore sits much closer to the small model.

The extra stored parameters still buy quality. The [Mixtral paper](https://arxiv.org/abs/2401.04088) reports that the model matches or beats Llama 2 70B on most of the benchmarks it evaluates, with about a fifth of the 70B's active parameters. The gain is smaller than the storage ratio suggests, because a token sees only two experts' worth of knowledge per layer.

## Top-k routing
The router turns one token vector into a choice of experts and a weight for each chosen expert. It multiplies the token vector $x$ by a $d \times E$ matrix $W_r$ to get one logit per expert. Here $d = 4{,}096$ is the model width and $E = 8$ is the number of experts. The Fundamentals example routed a token with logits $(2.0, 1.0, 0.5, -1.0)$. A second token with logits $u = (1.2, 0.9, 0.1, -0.6)$ over four experts shows the choices that section left open.

**Softmax gating** turns the logits into probabilities with a [softmax](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/#logits-and-softmax), here $(0.447, 0.331, 0.149, 0.074)$. Top-2 selection keeps experts 1 and 2 and renormalizes them to $0.447/0.778 = 0.574$ and $0.426$. A softmax over only the two kept logits gives the same pair, since $e^{1.2}/(e^{1.2} + e^{0.9}) = 0.574$. Mixtral and gpt-oss compute it that way. The two numbers are the **gate weights**. The layer returns $0.574$ times expert 1's output plus $0.426$ times expert 2's.

The gate weights are also the router's only connection to the training loss. The choice of top-k is a ranking, and a ranking has no gradient, so the loss reaches $W_r$ only through how the gate weights scale the expert outputs. That matters for top-1 routing. Renormalizing a single kept probability always gives 1, which would leave the router with no gradient at all. The [Switch Transformer](https://arxiv.org/abs/2101.03961) routes each token to one expert. It therefore multiplies the expert output by the unnormalized probability, which is 0.447 for this token. A router that grows more confident then gets a larger weight and a signal to learn from.

**Sigmoid gating** scores each expert on its own instead of making the experts share one unit of probability. Expert $i$ with logit $u_i$ gets the score $s_i = 1/(1 + e^{-u_i})$. For the same token the scores are $(0.769, 0.711, 0.525, 0.354)$, and normalizing the top two gives $0.519$ and $0.481$. [DeepSeek-V3](https://arxiv.org/abs/2412.19437) switched from softmax to sigmoid scores and normalizes over the selected experts, and Kimi K2 uses the same scoring. A common explanation is scale. With 256 experts a softmax hands each one $1/256 = 0.004$ on average, so raising one expert's probability drags down all the others, while a sigmoid score does not depend on how many experts exist.

**Noisy top-k gating** from [Shazeer et al.](https://arxiv.org/abs/1701.06538) adds random noise to the logits before selection. The noise is scaled per expert by a learned amount. With a noise scale of 0.5 and standard normal draws $(-0.4, 0.6, 0.2, -1.0)$, the logits become $(1.0, 1.2, 0.2, -1.1)$ and top-1 now picks expert 2. Expert 2 trails by 0.3, and the difference of two noise terms has a standard deviation of $0.5\sqrt{2} = 0.71$. This token therefore goes to expert 2 about $\Phi(-0.3/0.71) = 34\%$ of the time, where $\Phi$ is the standard normal probability of falling below a value. The noise makes the router explore, so an expert that currently loses close contests still receives some tokens and gradient. Most recent large models leave the noise out and rely on the balancing methods of the following sections.

## Load imbalance
A router trained only on the language modeling loss tends to concentrate tokens on a few experts. An expert that receives more tokens gets more gradient, improves faster on those tokens, and wins them more often next time. Taken to the limit this is **expert collapse**. A handful of experts handle almost every token while the rest receive no gradient and stay near their random initialization. A reference MoE that collapsed onto two experts per layer would compute like a 12.9B dense model while still storing $6 \times 32 \times 176{,}160{,}768 = 33.8$ billion parameters that do nothing.

Imbalance also wastes hardware long before collapse. An expert's **load** is the number of tokens routed to it in a batch. Take the batch that the [load balancing loss](#load-balancing-loss) section works through, eight tokens routed top-1 over four experts. Their loads are 4, 2, 1 and 1, with a mean of 2 and a maximum of 4. When each expert sits on its own GPU, the layer cannot move on until the busiest GPU finishes. The [expert parallelism](#expert-parallelism) section describes that layout. That GPU is a **straggler**. It works for 4 token-units of time while the others work for 2, 1 and 1, so the expert phase runs at $2/4 = 50\%$ of the speed of a balanced batch. The busiest expert also sets how much buffer memory every GPU must reserve. Balance is therefore both a quality problem and a systems problem. Unused experts waste capacity, and uneven experts waste time.

## Load balancing loss
The usual fix adds a small term to the training loss that grows when tokens are spread unevenly. The Switch Transformer form is

$$
\mathcal{L}_{\text{aux}} = \alpha \, E \sum_{i=1}^{E} f_i P_i.
$$

Here $f_i$ is the fraction of the batch's tokens sent to expert $i$, counted after top-k selection, and $P_i$ is the router probability for expert $i$ averaged over the batch. $E$ is the number of experts and $\alpha$ is a small weight, 0.01 in the Switch Transformer. If the probabilities matched the counts exactly, the sum would be $E\sum_i f_i^2$, which is 1 when every expert gets $1/E$ of the tokens and $E$ when one expert gets all of them. The **auxiliary loss** is called auxiliary because it serves balance rather than prediction.

Both factors are needed. The count $f_i$ measures the imbalance directly but has no gradient, because moving a probability slightly does not change which expert wins. The mean probability $P_i$ has a gradient but measures imbalance only loosely. In the product, the gradient with respect to $P_i$ is $\alpha E f_i$, so the router is pushed hardest to lower the probability of whichever expert is busiest.

The sum also has a plain reading. Because $f_i$ is the share of tokens sent to expert $i$, the sum $\sum_i f_i P_i$ equals the average of $P$ for the expert each token went to, taken over the batch's tokens. Multiplying by $E$ compares that average with the $1/E$ a uniform router would give. The loss is therefore high when tokens keep going to the experts the router already favors across the whole batch. That is the rich-get-richer loop of the [load imbalance](#load-imbalance) section written as a number. It is small in absolute terms. With $\alpha = 0.01$ and 8 experts it lies between 0.01 at perfect balance and 0.08 at full collapse. Next to a language modeling loss of about 2, it acts as a gentle, steady pull on the router probabilities.

The weight $\alpha$ is a compromise. Too small and the rich-get-richer loop wins and experts collapse. Too large and the balance gradient competes with the language modeling gradient and forces uniform routing even where the data would prefer some experts to be busier. For top-$k$ routing with $T$ tokens, $f_i$ counts the fraction of the $T \cdot k$ assignments, so the loss still equals 1 at perfect balance.

Where the counting happens matters as much as the formula. A micro-batch is the few sequences one GPU processes in one forward pass. Frameworks usually compute $f_i$ inside each micro-batch and average the losses. That is **micro-batch balancing**, and with only a few sequences per micro-batch it asks every sequence to be balanced on its own. Two micro-batches show the cost. A code sequence sends its tokens evenly to experts 1 and 2, and a prose sequence sends its tokens evenly to experts 3 and 4. Each micro-batch has $f = (0.5, 0.5, 0, 0)$ or $(0, 0, 0.5, 0.5)$, and with probabilities matching the counts each scores $4 \times (0.25 + 0.25) = 2.0$. Pooled together the fractions are 0.25 each and the loss is 1.0. **Global-batch load balancing** pools the counts across all micro-batches and data-parallel GPUs before computing the loss, which costs one extra exchange of $E$ numbers per step. [Qiu et al.](https://arxiv.org/abs/2501.11873) report better perplexity and clearer domain specialization from it, and [Qwen3](https://arxiv.org/abs/2505.09388) adopted it for its MoE models.

Shazeer et al. used two terms. An importance loss penalized the squared coefficient of variation of each expert's summed gate weights. The squared coefficient of variation is the variance divided by the squared mean. A load loss used a smooth estimate of how many tokens each expert would receive under the noisy gate. [GShard](https://arxiv.org/abs/2006.16668) introduced the product of a counted fraction and a mean gate value that the Switch Transformer simplified into the form above. DeepSeek-V3 keeps a sequence-wise version of the same product and does its real balancing with the bias method of the [bias-based balancing](#bias-based-balancing) section. Its $\alpha = 0.0001$ is small enough that the term only prevents extreme imbalance inside one sequence.

</details>

## Capacity factor
Uneven loads are also awkward for the kernels, which work best when every expert processes a buffer of fixed size. The **expert capacity** is that fixed number of slots per expert, set from the fair share:

$$
C = \left\lceil c \cdot \frac{T \cdot k}{E} \right\rceil.
$$

Here $T$ is the number of tokens in the batch, $k$ the experts per token, $E$ the number of experts, and the **capacity factor** $c$ the slack allowed above an even split. A token that arrives after its expert's slots are full is dropped. **Token dropping** means the token skips that expert, its expert output counts as zero, and the residual connection carries its vector to the next layer unchanged.

Fixed buffers come from how the work is laid out on the hardware. The Switch Transformer was built for TPUs, whose compiler needs every tensor shape fixed before training starts. Routing decides only at run time how many tokens each expert gets. The capacity turns that unknown load into a known buffer size. It also simplifies the all-to-all exchange of the [expert parallelism](#expert-parallelism) section, since every GPU then knows in advance how many vectors it sends to each other GPU. The formula reads as the fair share $Tk/E$ stretched by the slack $c$. With $c = 1$ the buffers allow no imbalance at all, and with $c = 2$ an expert can take twice its share before anything is dropped.

The capacity factor therefore trades two kinds of waste. A low $c$ costs quality, because overflow tokens lose a layer of expert computation. A high $c$ costs compute and memory, because every expert pays for its full buffer whether or not tokens fill it. A dropped token still passes through attention in the same layer and through every other layer, and under top-2 routing it can lose one of its two experts while keeping the other. The losses add up when drops are frequent, and the [Switch Transformer](https://arxiv.org/abs/2101.03961) found that keeping the drop rate low mattered for scaling sparse models. With its balancing loss the drop rate was typically under 1%, and its models performed better at the low capacity factors of 1.0 and 1.25 than at higher ones.

## Bias-based balancing
Any auxiliary loss changes the gradient the router receives, so the router learns a compromise between predicting well and balancing well. **Auxiliary-loss-free balancing** keeps the gradient purely about prediction and balances with a separate controller. It comes from [Wang et al.](https://arxiv.org/abs/2408.15664) and is used in DeepSeek-V3. Each expert gets an **expert bias** $b_i$ that is added to its score only when choosing the top-$k$, while the gate weight still comes from the unbiased score:

$$
\text{chosen}_t = \operatorname{top-}k_i\,(s_{t,i} + b_i), \qquad g_{t,i} = \frac{s_{t,i}}{\sum_{j \in \text{chosen}_t} s_{t,j}}.
$$

Here $s_{t,i}$ is token $t$'s score for expert $i$ and $g_{t,i}$ its gate weight. After every training step each bias moves by a fixed amount $\gamma$ against its expert's load. It goes down if the load $c_i$ was above the mean load $\bar c$, up if below and stays unchanged if equal.

$$
b_i \leftarrow b_i - \gamma \operatorname{sign}(c_i - \bar c)
$$

DeepSeek-V3 uses $\gamma = 0.001$ for its first 14.3 trillion training tokens and $\gamma = 0$ for the last 500 billion.

The bias changes which experts win without changing what a win is worth. A busy expert's bias falls step after step, so tokens that only narrowly preferred it start to land on their second choice, while tokens that strongly prefer it still go there. Because the gate weight uses the unbiased score, the expert outputs are mixed exactly as the router scored them, and the gradient that trains the router comes from the language modeling loss alone. The controller also uses only loads that are already known. Wang et al. update each bias from the previous batch's counts, because using the current sequence's loads would let later tokens influence where earlier ones go. That is the same leak that rules out expert choice routing for decoders.

The sign keeps each step at the same size $\gamma$ whether an expert was 1 token or 1,000 tokens over the mean, so no single batch can throw a bias far off. Wang et al. also tried moving each bias in proportion to its expert's overload. That balanced slightly better but did not lower perplexity, so they kept the sign. Against the auxiliary loss the controller improved both quantities they track. In a 1B-parameter MoE, averaged over layers, the busiest expert on the validation set held 72% more tokens than its fair share under the loss and 4% more under the bias, and validation perplexity fell from 9.56 to 9.50.

## Fine-grained and shared experts

The reference MoE splits its feed-forward capacity into 8 large experts, but the same parameters can be cut into more, smaller ones. **Fine-grained experts** were introduced with [DeepSeekMoE](https://arxiv.org/abs/2401.06066). They split each expert into $m$ narrower experts and route each token to $m$ times as many, which keeps both the total and the active parameter counts unchanged. Splitting each reference expert into 4 gives 32 experts of width 3,584, and top-8 routing uses $8 \times 3 \times 4{,}096 \times 3{,}584 = 352{,}321{,}536$ expert parameters per token, exactly the two coarse experts' worth.

What changes is the number of combinations. Choosing 2 of 8 experts allows 28 pairs, while choosing 8 of 32 allows 10,518,300 sets, so each token can draw on a much more specific mix of knowledge. **Expert granularity** is the width of an expert relative to the model width, and it has fallen accordingly. Mixtral's experts are 3.5 times the model width and DeepSeek-V3's are 0.29 times. A **shared expert** is an expert every token always uses. DeepSeekMoE argues that many routed experts would otherwise each relearn common knowledge such as frequent syntax. Keeping one of the 32 fine-grained experts as shared and routing to 7 of the other 31 leaves the active count unchanged and allows 2,629,575 routed sets.

![Fine grained and shared experts](/images/llm-deep-dive/16e-fine-grained-and-shared-experts.png)

Fine granularity has costs. Eight smaller matrix multiplications per token use the GPU less efficiently than two large ones unless they are grouped into one kernel. Each token is also sent to 8 places instead of 2, so the dispatch traffic of the [expert parallelism](#expert-parallelism) section grows fourfold at the same width. That is why fine-grained designs usually come with node-limited routing.

It found that at a fixed active count, raising sparsity kept lowering the loss, at the price of more complex infrastructure.

What the experts end up specializing in is less tidy than the name suggests. The Mixtral paper found no clear assignment of experts to topics such as biology or philosophy. Routing followed syntax more than subject, and consecutive tokens often went to the same expert. Models with many fine-grained experts show more topical structure. [OLMoE](https://arxiv.org/abs/2409.02060) reports experts that favor particular domains such as code or scientific text, and the global-batch balancing work above reports stronger domain specialization than micro-batch balancing gives.

## Expert parallelism
A model with 93 GB of experts cannot hold every expert on every GPU, and duplicating them would waste memory. **Expert parallelism** places different experts on different GPUs while the attention layers usually stay data-parallel, so every MoE layer must move each token to the GPUs holding its experts and bring the results back. The **dispatch** step sends token vectors to their experts and the **combine** step returns the expert outputs to the token's home GPU. Both are all-to-all collectives, in which every GPU sends a different piece of data to every other GPU. [Distributed Training and Parallelism](/tutorials/llm-deep-dive/distributed-training-and-parallelism/#collective-communication) describes them with the other collectives.

Splitting the experts this way divides the memory. With 8 GPUs and one expert per GPU in every layer, each GPU stores $32 \times 176{,}160{,}768 \times 2$ bytes of expert weights, which is 11.3 GB. It adds its own 3.2 GB copy of everything outside the experts, instead of holding all 93.4 GB. The price is that a token now crosses the network twice in every MoE layer. Attention runs on the token's home GPU, the router picks its experts, the dispatch carries the vector to them, the experts run, and the combine brings the outputs home before the next layer's attention can start. In the plain schedule both exchanges sit on the critical path, since no expert can start before its tokens arrive and no attention can start before the outputs return. Every GPU holds a different set of tokens for every destination, so each pair of GPUs swaps its own piece of data. That is what makes the exchange an all-to-all. How long it takes depends on how many tokens leave home and how many experts each token visits, and the receiving GPU with the most tokens sets the pace of the expert phase that follows.

Here only 3 of 8 tokens moved because the routing happened to favor home GPUs. With uniform routing over 4 GPUs, 3 in 4 tokens leave home, and with 8 GPUs 7 in 8 do. The balanced routing of the [bias-based balancing](#bias-based-balancing) section would also have given every GPU 2 tokens in step 4.

At reference scale the volume follows from the width. Top-2 routing sends each token's 8 KiB vector twice, so dispatch moves 16 KiB per token per layer and combine another 16 KiB. The backward pass runs both exchanges again in reverse, so training moves 64 KiB per token per layer, 2 MiB per token over 32 layers. A GPU holding 8,192 tokens with expert parallelism over 8 GPUs sends $8{,}192 \times 16 \text{ KiB} = 134$ MB per dispatch. Seven eighths of that leaves the GPU, which comes to 117 MB. Each expert then receives 16,384 assignments, and its forward pass on them costs

$$
16{,}384 \times 2 \times 176{,}160{,}768 = 5.77 \times 10^{12} \text{ FLOPs},
$$

about 5.8 ms at 989 TFLOP/s. The forward dispatch plus combine takes $2 \times 117 / 450 = 0.52$ ms over NVLink at about 450 GB/s per GPU, and 4.7 ms over InfiniBand at about 50 GB/s per GPU. Inside one node the exchange costs under a tenth of the expert time. Across nodes it costs about four fifths of it. DeepSeek-V3 uses fine-grained top-8 routing over 8 nodes and reports a ratio of computation to cross-node communication of roughly 1 to 1.

**Node-limited routing** caps how many nodes one token's experts may span. DeepSeek-V3 groups its 256 experts by node, picks the best 4 of 8 nodes for each token, and chooses the top 8 experts only within them. A token whose 8 experts would otherwise sit on 8 nodes then sends at most 4 copies over InfiniBand, and each receiving node forwards the vector to the right GPUs over NVLink. Specialized kernels do the rest. [DeepEP](https://github.com/deepseek-ai/DeepEP) is DeepSeek's open-source library. It provides high-throughput dispatch and combine kernels for training and prefill and low-latency kernels for decoding. It uses NVLink inside a node and RDMA across nodes, and it can dispatch in FP8 to halve the bytes. DeepSeek-V3 dedicates 20 of the H800's 132 streaming multiprocessors to communication so it runs alongside the matrix multiplications.

## Router z-loss
Large MoE models are known for training less stably than dense models of similar compute, and the router is a frequent cause. Its logits can drift upward during training. Large logits make the softmax saturate, so tiny changes flip which experts win, and they lose precision in [bf16](/tutorials/llm-fundamentals/pretraining-at-scale/#mixed-precision). A bf16 number keeps 8 significant bits, so between 16 and 32 neighbouring values are 0.125 apart. Logits of 24.0 and 24.06 round to the same value, which erases a 6% preference between two experts. Rounding can change any one $e^{z}$ by up to 6.4%. Near 100 the gap is 0.5 and the error reaches 28%.

![Bf16 router logit rounding](/images/llm-deep-dive/16e-bf16-router-logit-rounding.png)

The **router z-loss** from [ST-MoE](https://arxiv.org/abs/2202.08906) penalizes large logits directly:

$$
\mathcal{L}_z = \frac{1}{T} \sum_{t=1}^{T} \Big(\log \sum_{i=1}^{E} e^{u_{t,i}}\Big)^2.
$$

Here $u_{t,i}$ is token $t$'s router logit for expert $i$ and $T$ is the number of tokens. The inner log-sum-exp is close to the largest logit, so the loss is roughly the squared size of the winning logit. For the [top-k routing](#top-k-routing) section's logits $(1.2, 0.9, 0.1, -0.6)$ it is $2.006^2 = 4.02$, which the ST-MoE weight of 0.001 turns into 0.004. Multiplying the logits by 20 gives $(24, 18, 2, -12)$ and a z-loss of $24.002^2 = 576$. After weighting that is 0.58, which is large next to a language modeling loss of about 2. Its gradient with respect to each logit is $2z\,p_i$, so it pulls the largest logits down hardest. Here $z$ is the log-sum-exp and $p_i$ the softmax probability. The same idea applied to the output logits of the language model belongs to [Numerics and Stability](/tutorials/llm-deep-dive/numerics-and-training-stability/).

Several other fixes target the router specifically. The Switch Transformer computes the router in float32 while the rest of the layer stays in bf16. It called this choice **selective precision**. It also scales down the initial weights to keep early logits small. **Routing fluctuation** is when the same token keeps switching experts late in training. It means an expert's parameters are tuned for tokens it then stops receiving. Fine-tuning brings its own risk. ST-MoE found sparse models overfit small fine-tuning sets more easily than dense ones, and the Switch Transformer raised dropout inside the experts during [fine-tuning](/tutorials/llm-fundamentals/post-training-from-base-model-to-assistant/#supervised-fine-tuning) to compensate. Rolling back to a checkpoint and other general loss spike handling work for MoE runs as they do for dense ones.

## Upcycling
Training an MoE from scratch repeats work a dense model of the same width has already done. **Sparse upcycling** from [Komatsuzaki et al.](https://arxiv.org/abs/2212.05055) starts from a trained dense checkpoint, copies its feed-forward network into every expert, adds a freshly initialized router, and keeps training. Applied to the reference 7B with 8 experts and top-2 routing, it gives 37.04 billion total and 11.07 billion active parameters. The [Fundamentals example](/tutorials/llm-fundamentals/the-transformer-block-and-model-anatomy/#mixture-of-experts) applies the same change to the story model, giving 60.58 million total and 18.11 million active parameters.

At the first step the upcycled model computes exactly what the dense model did, provided the gates sum to 1. Let $F$ be the copied feed-forward network. With identical experts and renormalized top-2 weights such as 0.574 and 0.426, the layer returns $0.574\,F(x) + 0.426\,F(x) = F(x)$, so the loss does not jump. With Switch-style unnormalized top-1 weights the output would shrink to $0.447\,F(x)$ for the [top-k routing](#top-k-routing) section's token, and training would first have to recover from that. The experts start identical and drift apart only because the router sends them different tokens. That is why some variants add noise to the copies or give each expert a different slice of the dense network.

The paper reports that upcycled T5 language models and Vision Transformers beat their dense starting points with an extra budget of only about 50% of the original dense pretraining compute, and also beat MoE models trained from scratch on the full original budget. The saving comes from the starting point. Every expert begins with everything the dense feed-forward network learned, so the extra compute goes into specializing the experts and training the router instead of relearning the basics. Priced on the reference numbers, the dense 7B cost $8.09 \times 10^{22}$ FLOPs over its 2 trillion tokens. The upcycled model costs $6 \times 11.07 = 66.4$ GFLOPs per training token. Half of the dense budget then buys about 610 billion further tokens, under a third of the original run. The same budget of $8.09 \times 10^{22}$ FLOPs spent on a fresh MoE of this shape would cover only about 1.2 trillion tokens from random weights, which mirrors the comparison the paper's upcycled models won. Upcycling pays most when the dense checkpoint already exists, because its cost is then already spent.

The upcycled model still costs more to run than its parent. In the 7B example each token uses 11.07 billion parameters instead of 6.74 billion, which is 1.64 times the arithmetic. The weights take 5.5 times the memory.

## MoE inference
Any token might need any expert, so a server must keep all experts in fast memory even though each token uses a quarter of them. The reference MoE's 93.41 GB of bf16 weights need two H100s. [Quantizing](/tutorials/llm-fundamentals/inference-and-decoding/#quantization) the weights to FP8 halves them to 46.7 GB, which fits one GPU. That leaves 33.3 GB for the key-value cache, about 254,000 tokens at 128 KiB per token.

The bytes read per decode step depend on the batch. One sequence touches 2 experts per layer, so this model estimates 25.5 GB of weights read per step and a bandwidth cost close to that of a dense 12.9B model. Each extra sequence touches more experts. With top-2 of 8, an expert is missed by one token with probability $1 - 2/8 = 0.75$. If the selections are independent and uniform across sequences, a batch of $b$ sequences touches $8(1 - 0.75^b)$ experts per layer on average, which is 5.5 at $b = 4$ and 7.9 at $b = 16$. From about 16 sequences on, every step reads nearly all 93 GB while doing only 12.9B worth of arithmetic per token. Those are the same bytes a dense 46.7B model reads.

![Decode step time versus batch](/images/llm-deep-dive/16e-decode-step-time-versus-batch.png)

The [bandwidth bound](/tutorials/llm-fundamentals/inference-and-decoding/#memory-bandwidth-bound-decoding) lasts much longer than for a dense model. A dense model becomes compute bound near 295 sequences, where each weight read serves 295 tokens. An expert serves only the quarter of the batch routed to it, so the MoE needs about four times as many sequences before its arithmetic catches up with its memory reads. That is close to 1,070 in the idealized figure. Beyond that point it costs a dense 12.9B model's time per step, 3.6 times less than the dense 46.7B. An MoE therefore pays off at batch 1, where it reads only the active experts, and at very large batches. In between, this estimate puts it near the bandwidth cost of a dense model with the same total weights. Expert imbalance, kernel efficiency and interconnect traffic can move real timings away from the curve.

Large deployments reach that batch size with **wide expert parallelism**, which spreads the experts over so many GPUs that each holds only a few and receives tokens from the whole fleet. DeepSeek's [published serving setup](https://github.com/deepseek-ai/open-infra-index/blob/main/202502OpenSourceWeek/day_6_one_more_thing_deepseekV3R1_inference_system_overview.md) runs prefill with experts spread over 32 GPUs, with 9 routed experts and 1 shared expert per GPU. Decode runs over 144 GPUs, with 2 routed experts and 1 shared expert per GPU. It adds 32 **redundant experts**, which are extra copies of the busiest experts that relieve stragglers. It also separates the prefill and decode GPUs as described in [Serving Systems](/tutorials/llm-deep-dive/inference-systems-at-scale/). It reports about 14,800 output tokens per second per 8-GPU H800 node during decoding. As a teaching estimate, for each of DeepSeek-V3's 256 experts to see 295 tokens per step with top-8 routing, a decode step needs $295 \times 256/8 = 9{,}440$ tokens, about 66 sequences per GPU across 144 GPUs. An [SGLang deployment](https://lmsys.org/blog/2025-05-05-large-scale-ep/) built on DeepEP reproduced the approach on 96 H100s. DeepSeek-V3 also trains a multi-token prediction module, whose use as a draft model for speculative decoding is covered in [Serving Systems](/tutorials/llm-deep-dive/inference-systems-at-scale/).

At the other extreme, **expert offloading** keeps the experts in CPU memory and copies them to a small GPU on demand. One reference expert is 352 MB in bf16 and takes about 5.5 ms to copy over a PCIe link at 64 GB/s. A token that needed fresh copies of its 64 experts would wait 350 ms. [Eliseev and Mazur](https://arxiv.org/abs/2312.17238) keep recently used experts on the GPU, guess the next layer's experts by applying its router to the current hidden state, and quantize the experts to 2 or 3 bits. With 2-bit experts they report about 2 to 3 tokens per second for Mixtral at batch 1 on consumer GPUs and a free cloud notebook.

## Dense versus sparse models
An MoE trades memory, communication and engineering effort for lower compute per token, so the decision turns on which of those resources is scarce. The table maps common situations to a choice and the main reason.

| Situation | Choice | Reason |
|---|---|---|
| Pretraining at a fixed FLOP budget on many GPUs with fast links | Fine-grained MoE with a shared expert, dropless, bias or global-batch balancing | Most quality per training FLOP, and balancing keeps the experts useful |
| High-throughput serving with thousands of concurrent sequences | MoE with wide expert parallelism and redundant experts | Large aggregate batches make each expert compute bound |
| One GPU or an edge device | Dense model | Memory follows total parameters, and mid-sized batches read every expert |
| Batch-1 latency with spare GPU memory | MoE is acceptable | A single sequence reads only the active experts |
| Slow links between nodes | Coarser experts, node-limited routing, or a dense model | All-to-all traffic grows with the number of experts per token |
| Small team with frequent fine-tuning | Dense model | Fewer instabilities, no expert parallelism to operate, and less overfitting |
| A strong dense checkpoint and a limited budget | Upcycle into an MoE | About half the original pretraining compute buys a better model |

Each row names the resource that is scarce in that situation, and the choice follows from which of the MoE's bills that resource pays. Memory pays for the total parameters, the network pays for the all-to-all, and the team pays for router instabilities and for operating expert parallelism. The MoE saves arithmetic per token at every batch size, but it reads fewer bytes per step than a dense model of its total size only at small batches. When two rows apply at once, the scarcer resource decides. A team pretraining at a fixed FLOP budget on nodes joined by slow links follows the slow-links row before the pretraining row, because the [expert parallelism](#expert-parallelism) section showed that a cross-node exchange can cost four fifths of the expert time.

A worked diagnosis shows how a row is reached from measurements. A team serves the reference MoE on two H100s for an internal chat tool. In single-sequence tests a decode step reads the 25.5 GB of active weights, but with about 8 concurrent sequences in production the step time roughly triples. The first measurement is the number of experts each layer touches per decode step, which the routing decisions give directly. It averages 7.2 of 8, so a step reads about 84 GB while doing only active-parameter arithmetic. Those 84 GB are 90% of the whole model. This is the middle band of the [MoE inference](#moe-inference) section. The traffic is far from the roughly 1,070 sequences that would make the experts compute bound, so the deployment fits the one-GPU row better than the high-throughput row. The fix depends on the quality the tool needs. If a dense model of about 13B parameters is good enough, it reads about 26 GB per step, a third of the MoE's bytes. The Mixtral paper puts Mixtral-level quality near Llama 2 70B. If the tool needs that quality, the MoE still reads less than the roughly 140 GB of a dense 70B in bf16, and FP8 weights would cut its 84 GB to about 42 GB on a single GPU.

A sound comparison trains the dense and sparse candidates at the same FLOP budget on the same data, then compares quality together with serving cost per million tokens at the batch size the deployment will actually run. The decision record should name the reversal condition in advance, for example that the dense model ships if all-to-all time or resident memory makes the MoE's cost per token higher at equal quality. [Efficient Attention](/tutorials/llm-deep-dive/efficient-attention-mechanisms/) and [Long Context](/tutorials/llm-deep-dive/long-context-and-document-models/) cover whole-model choices beyond the feed-forward layer, such as attention variants and context length.
