Rank 16 [LoRA](/tutorials/llm-fundamentals/using-llms-in-applications/#low-rank-adaptation) on every attention and feed-forward matrix of the [reference 7B](/tutorials/llm-deep-dive/#scale-reference-models) trains 39,976,960 parameters, 0.59% of the model. The memory a training run needs does not fall to 0.59%. It falls from 107.8 GB to about 14 GB before activations, the activations stay where they were, and each token still costs the same 13.5 GFLOPs on the way forward. A share of trainable parameters describes one budget out of several, and the methods in this chapter differ mostly in which budget they cut.

Sharing is the thread that runs through all of them. A model can use one matrix at both its input and output ends, one block at every depth, one backbone for several tasks, or one frozen base under hundreds of small trained additions. Each kind of sharing cuts some of stored parameters, training state, activations, compute and serving memory, and none cuts all five. The figure puts four of those budgets side by side for ten fine-tuned variants of the 7B.

![Budgets for ten variants](/images/llm-deep-dive/16f-budgets-for-ten-variants.png)

LoRA cuts two of the four budgets and leaves the other two where full fine-tuning has them. Training memory falls from 107.8 GB to 14.12 GB, because gradients and AdamW state now exist only for the 40 million adapter parameters. Storage for ten tasks falls from 134.8 GB to 14.28 GB, because the ten tasks share one 13.48 GB base and each adds only an 80 MB file. That second saving grows with the number of tasks. A hundred tasks would need 1,348 GB as full copies and 21.47 GB as one base with adapters. Activations and forward compute barely move, 18.28 GB against 18.25 and 13.56 GFLOPs per token against 13.48. Every token still passes through all 32 frozen blocks, and the backward pass still runs back through them to reach the adapters in earlier layers. The small increases are the adapters' own work. On the way forward that is 2 FLOPs for each of the 40 million adapter parameters, 0.08 GFLOPs per token.

The training memory bar also shows where the next saving has to come from. Of LoRA's 14.12 GB, 13.48 GB is the frozen base, so even an adapter of zero size would save at most another 0.64 GB. Only storing the base in fewer bits brings that bar much lower. The activations bar needs a different tool again, such as gradient checkpointing, because no choice of which weights train changes what the forward pass has to save.

The chapter takes the levels of sharing in turn, starting inside one model. Reusing one block across depth cuts the stored model to 6.9% and leaves compute and activations untouched, which is the limit every later method inherits. Training one backbone on several tasks then shows what sharing trained weights costs, which is tasks whose gradients pull against each other. Freezing the base removes that conflict, because no two tasks then change the same weight, and the rest of the chapter works inside that design. Bottleneck adapters come first and show why an addition placed in series costs latency even when its arithmetic is tiny. Four sections on LoRA follow, covering its scale and initialization, which matrices to adapt and why low rank suffices, the full memory budget with merging, and its main variants. Prefix and prompt tuning train inputs to attention instead of weights. [QLoRA](/tutorials/llm-fundamentals/using-llms-in-applications/#quantized-adaptation) then stores the frozen base in four bits, since by that point the base is the largest term left in training memory. The closing sections serve many adapters on one base, fold several into one model by merging, and map situations to methods.

## Sharing levels
A pretrained model can be reused at four levels, and each level saves something different. The smallest is one matrix used twice inside a model. [Weight tying](/tutorials/llm-fundamentals/tokenization-and-embeddings/#weight-tying) does this for the embedding table and the output head, and in the reference 7B it would save 131,072,000 parameters, 1.9% of the model. The next level reuses whole blocks across depth, so one set of weights runs at many layers. Above that, one backbone serves several tasks, trained on all of them together. The broadest level freezes the pretrained model and shares it across many tasks, each of which trains only a small addition. That last family is called **parameter-efficient fine-tuning**, or PEFT. It adapts a model by training a small number of new or selected parameters while the rest stay fixed.

The embedding table also allows a second kind of saving beyond tying. [ALBERT](https://arxiv.org/abs/1909.11942) introduced **factorized embedding parameterization**. It stores each token as a short vector of width $e$ and projects it up to the model width with one shared $e \times d$ matrix. For the 7B with $e = 128$, the table becomes $32{,}000 \times 128 + 128 \times 4{,}096 = 4{,}620{,}288$ parameters instead of 131,072,000. The cost is expressiveness, since every token's input vector now lies in one 128-dimensional subspace of the 4,096-wide stream.

Five budgets recur through the chapter. **Stored parameters** are the weights kept on disk and in memory. **Training state** is what training keeps for each parameter it updates. In the [mixed-precision AdamW accounting](/tutorials/llm-fundamentals/pretraining-at-scale/#optimizer-memory), that is 2 bytes of gradient, 4 of master weight and 8 of moments, which with the 2-byte weight makes 16 bytes. Activations are the intermediate values saved for the backward pass, compute is the arithmetic per token, and **serving memory** is what a deployment keeps resident to answer requests for every task it supports. The table maps each level of sharing to those budgets.

| Level of sharing | Example | Stored parameters | Training state | Activations | Compute per token | Serving ten tasks |
|---|---|---|---|---|---|---|
| One matrix used twice | Weight tying, factorized embeddings | Falls by the shared matrix | Falls with it | Unchanged | Unchanged | Ten full models |
| One block across depth | ALBERT, Universal Transformer | Falls up to 32 times in the blocks | Falls with it | Unchanged | Unchanged | Ten smaller models |
| One backbone across tasks | Multi-task training | One model for all tasks | One run for all tasks | Unchanged | Unchanged | One model |
| One frozen base across additions | Adapters, LoRA, prefix tuning | Base plus small additions | Additions only | Nearly unchanged | Unchanged or slightly higher | One base plus ten small files |
| Frozen base in four bits | QLoRA | Base about 3.5 times smaller | Additions only | Nearly unchanged | Higher, from expanding weights | Depends on the serving format |

The table uses the same activation allowance across these configurations to isolate the cost of sharing weights. The exact tensors retained for backward depend on what is trained and how the run is implemented. Activation memory is cut by other means, such as [gradient checkpointing](/tutorials/llm-fundamentals/using-llms-in-applications/#quantized-adaptation) or the splitting across GPUs in [Parallelism](/tutorials/llm-deep-dive/distributed-training-and-parallelism/).

## Cross-layer sharing

Each of the 7B's 32 blocks has its own 202,383,360 weights, and nothing in the forward pass requires that. **Cross-layer parameter sharing** uses one set of block weights at every depth, so the stored model holds one block instead of 32. ALBERT shares all of its layers this way, and its paper reports 18 million parameters for ALBERT-large against 334 million for BERT-large of the same shape. The **Universal Transformer** of [Dehghani et al.](https://arxiv.org/abs/1807.03819) frames the same idea as a loop, in which one block is applied again and again and **adaptive computation time** lets each position stop after its own number of applications.

Reusing a block does not reuse its work, because each application reads a different input. A toy block $f(h) = 2h + 1$ doubles its input and adds one, and it has two weights. Applied three times to $h_0 = 1$ it gives 3, then 7, then 15. Three independent blocks would hold six weights, while the shared one holds two, yet both versions perform three multiplications and three additions, since the second application has to work on 3 and the third on 7. The saved activations are the same too, since the backward pass needs 1, 3 and 7 to compute gradients whichever version produced them.

What sharing does change is the gradient. The shared multiplier $w = 2$ receives the sum of what each application would have received alone. That is 7 from the third, $2 \times 3 = 6$ from the second and $2 \times 2 \times 1 = 4$ from the first, so the derivative of the final 15 with respect to $w$ is 17. One weight has to serve three depths at once, which is why shared models often need more width to match unshared ones.

![Cross layer sharing](/images/llm-deep-dive/16f-cross-layer-sharing.png)

Reusing one block shrinks what is stored and leaves the work alone. Sharing the 7B's blocks would leave $2 \times 131{,}072{,}000 + 202{,}383{,}360 + 4{,}096 = 464{,}531{,}456$ stored parameters, 6.9% of the model. Training state would fall in proportion, from 107.8 GB to 7.4 GB. Compute stays at about 13.5 GFLOPs per token and activations at about 18 GB per 4,096-token sequence, because every token still passes through 32 block applications. ALBERT shows the price. Its configuration that beat BERT-large needed a width of 4,096 and trained more slowly despite fewer parameters. Full sharing is therefore rare in large language models, where compute sets the cost. It survives where memory binds. [MobileLLM](https://arxiv.org/abs/2402.14905) runs each block twice in a row in sub-billion-parameter models built for phones.

## Multi-task learning
One backbone can learn several tasks at once if every batch mixes examples from all of them. **Multi-task learning** trains shared weights on a combined loss,

$$
\mathcal{L} = \sum_i \lambda_i \mathcal{L}_i,
$$

where $\mathcal{L}_i$ is the loss of task $i$ and $\lambda_i$ is the weight it gets. The weights are only half of the control. The **sampling mixture** sets how often each task's examples enter a batch, and it usually matters more, because a task seen nine times as often moves the shared weights nine times as often. With 900,000 examples of one task and 100,000 of another, sampling in proportion to size gives a 90 to 10 mix. **Mixing temperature** samples task $i$ in proportion to $n_i^{1/T}$, where $n_i$ is its example count and $T$ is the temperature. [T5](https://arxiv.org/abs/1910.10683) used this scheme. At $T = 2$ the weights are $\sqrt{900{,}000} = 948.7$ and $\sqrt{100{,}000} = 316.2$, a 75 to 25 mix. As $T$ grows the mix approaches 50 to 50.

Sharing helps when tasks have common structure and hurts when they do not. **Negative transfer** is the case where training a task alongside others leaves it worse than training it alone. One local cause is **gradient conflict**, where two tasks' gradients point more than 90 degrees apart. Their dot product is then negative, and a step that lowers one loss raises the other, at least to first order. **PCGrad** removes the conflict before adding the gradients. Its name is short for projecting conflicting gradients, and it comes from [Gradient Surgery for Multi-Task Learning](https://arxiv.org/abs/2001.06782). Whenever task $i$'s gradient $g_i$ has a negative dot product with task $j$'s gradient $g_j$, it subtracts the part of $g_i$ that points along $g_j$:

$$
g_i' = g_i - \frac{g_i \cdot g_j}{\lVert g_j \rVert^2}\, g_j \quad \text{when } g_i \cdot g_j < 0.
$$

Here $g_i \cdot g_j$ is the dot product, $\lVert g_j \rVert^2$ is the squared length of $g_j$, and the fraction is how many copies of $g_j$ the gradient $g_i$ contains. After the subtraction $g_i'$ is at right angles to $g_j$, so following it no longer moves task $j$'s loss either way.

PCGrad needs one gradient per task before it can project. For the full 7B, each extra task costs a backward pass and 13.48 GB of bf16 gradient, so PCGrad suits small trainable sets better than full fine-tuning of large models. Cheaper causes of conflict come first. These are labels that disagree between tasks, a loss summed over tokens for one task and averaged for another, or a mixture that starves the small task. A frozen base with one small module per task avoids the problem for the trained parameters, since no two tasks then share a weight that training changes. The rest of the chapter builds on that idea.

## Bottleneck adapters

The first parameter-efficient methods inserted small new layers into a frozen network. [Houlsby et al.](https://arxiv.org/abs/1902.00751) introduced the **bottleneck adapter**. It squeezes the hidden vector down to a few numbers, applies a nonlinearity, expands back to full width, and adds the result to its input:

$$
y = x + U\, \sigma(D x).
$$

Here $x$ and $y$ are vectors of width $d = 4{,}096$, $D$ is an $m \times d$ matrix that projects down to the bottleneck width $m$, $\sigma$ is an activation function, and $U$ is a $d \times m$ matrix that projects back up. Starting $U$ near zero makes the adapter start as the identity, so training begins at the pretrained model.

At $m = 64$ one adapter holds $2 \times 4{,}096 \times 64 = 524{,}288$ weights plus $64 + 4{,}096$ biases, 528,448 in all. Houlsby placed two per block, one after the attention sublayer and one after the feed-forward sublayer. In the 7B that makes $2 \times 32 \times 528{,}448 = 33{,}820{,}672$ trainable parameters, 0.50% of the model. Keeping only the adapter after the feed-forward sublayer halves that to 16,910,336. This variant is usually called the Pfeiffer placement, after [AdapterFusion](https://arxiv.org/abs/2005.00247).

![Adapter insertion points](/images/llm-deep-dive/16f-adapter-insertion-points.png)

Where an addition attaches decides what it costs at inference. A bottleneck adapter sits in series, between a sublayer and its addition to the residual stream, so its output is the input to everything after it. That placement is its main cost. Because of the nonlinearity $\sigma$, the adapter cannot be folded into any frozen weight, so every token at every layer waits for extra small operations. The bytes are small, 67.6 MB against 13.48 GB of base weights. But decoding at batch size 1 is a long chain of small operations, and 192 more per token show up as latency. The LoRA paper measured about 20% to 30% extra latency from adapter layers on GPT-2 medium at batch size 1.

The arithmetic is as small as the bytes. Each adapter multiplies by $D$ and then by $U$, which takes about $2 \times 528{,}448 \approx 1.06$ million FLOPs per token. The 64 adapters therefore add 67.6 million FLOPs to the 13.5 billion of the forward pass, 0.5% more. The 192 extra operations are those 64 adapters with three steps each, the down projection, the activation and the up projection. Each step needs the result of the one before, and each is far too small to fill the GPU, so at batch size 1 its time goes mostly to the fixed cost of launching and finishing it. That is how 0.5% more arithmetic becomes 20% to 30% more time. Larger batches give every small operation more work to spread that fixed cost over, and the same LoRA measurement found the overhead down to 2% to 3% at batch size 32 with 512-token sequences. The series placement is therefore mainly a cost for online serving, where requests often run one at a time.

LoRA attaches in parallel instead. Its branch reads the same input as a frozen matrix and adds to that matrix's output, with nothing nonlinear in between, so $Wx + \tfrac{\alpha}{r} BAx$ equals $(W + \tfrac{\alpha}{r} BA)x$. After training the branch can therefore be folded into $W$, which leaves a model of the original shape with no extra operations per token, as the [LoRA memory budget and merging](#lora-memory-budget-and-merging) section shows. Prefix and prompt tuning attach at a third kind of place, the inputs attention reads. They add positions rather than operations, so their cost shows up in the cache rather than in the chain of kernels, as the [prefix and prompt tuning](#prefix-and-prompt-tuning) section shows.

## LoRA scale and initialization

LoRA computes $h = W x + \tfrac{\alpha}{r} B A x$ with $W$ frozen, and Fundamentals worked one rank-one layer by hand. The starting values of $A$ and $B$ and the scale $\alpha / r$ are two choices made before training starts, and they decide how that layer learns.

The [story-model LoRA lab](/tutorials/llm-fundamentals/notebook/#lora) attaches an adapter to the first block’s query projection. Its first factor starts with small random entries and its second starts at zero, so the adapter initially adds zero. After three updates, the lab checks that the second factor has changed and the original projection is still identical.

The usual initialization draws $A$ at random and sets $B$ to zero, so the adapted model starts identical to the base. In the Hugging Face PEFT library, the entries of $A$ have size about $1/\sqrt{d_{\text{in}}}$. The gradient for $A$ is proportional to $B$, so on the first step only $B$ moves, and both factors train from the second step on. Zero for both would freeze them forever, since each factor's gradient contains the other. Random values for both would start from a perturbed model that early training has to undo.

The scale exists so that changing the rank does not change how fast the model moves. The **LoRA scale** is the factor $\alpha / r$ in front of $BA$, where $\alpha$ is a constant fixed once and $r$ is the rank. Without it, a rank 64 adapter would change the model's outputs about eight times faster than a rank 8 adapter at the same learning rate, and every change of rank would need a new learning rate search.

<summary><span class="cm-collapse-icon" aria-hidden="true"><svg viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round"><path d="M15 14c.2-1 .7-1.7 1.5-2.5 1-.9 1.5-2.2 1.5-3.5A6 6 0 0 0 6 8c0 1 .2 2.2 1.5 3.5.7.7 1.3 1.5 1.5 2.5"/><path d="M9 18h6"/><path d="M10 22h4"/></svg></span><span class="cm-collapse-text"><span class="cm-collapse-kicker">Deep dive</span><span class="cm-collapse-title">Why the first update grows with rank</span></span><span class="cm-collapse-hint" aria-hidden="true"></span></summary>

As the two-step example in [the AdamW section](/tutorials/llm-fundamentals/pretraining-at-scale/#adamw) showed, AdamW’s first update is close to $\eta$ in magnitude when the gradient is large compared with $\epsilon$. For entries of $B$ in that regime, the first step from zero gives them magnitude about $\eta$ and a sign that opposes the gradient. Output $i$ of the adapter then changes by

$$
\Delta y_i = \frac{\alpha}{r} \sum_{k=1}^{r} \Delta B_{ik}\, (A x)_k,
$$

a sum of $r$ terms, one per rank direction. Here $(A x)_k$ is the $k$-th number the down projection produces. On the first step every term's sign is chosen from the same gradient, so the terms line up and the sum has size about $r \eta \bar a$, where $\bar a$ is the typical size of $(A x)_k$. With $\eta = 10^{-4}$, $\bar a = 0.5$ and no scale, rank 8 moves the output by 0.0004 and rank 64 by 0.0032, eight times as much. With the scale $\alpha / r$ and $\alpha = 16$, rank 8 gives $2 \times 0.0004 = 0.0008$ and rank 64 gives $0.25 \times 0.0032 = 0.0008$. The factor $r$ cancels, and the first update is $\alpha \eta \bar a$ at every rank.

</details>

![Lora scaling versus rank](/images/llm-deep-dive/16f-lora-scaling-versus-rank.png)

The cancellation depends on the $r$ terms sharing one sign, which holds only on the first step. Later in training the terms point different ways, and in a simple teaching model with mixed signs their sum grows like $\sqrt{r}$ instead of $r$. Then $\alpha / r$ over-corrects. The update shrinks like $1/\sqrt{r}$, so a rank 256 adapter moves the output four times less than a rank 16 adapter, since $\sqrt{256/16} = 4$. **Rank-stabilized LoRA**, or [rsLoRA](https://arxiv.org/abs/2312.03732), analyzes activations and gradients as rank grows and derives that the scale should be $\alpha / \sqrt{r}$. It reports that plain LoRA's $\alpha / r$ makes large ranks learn so slowly that raising the rank brings little gain. With $\alpha = 16$, going from rank 16 to rank 256 cuts the scale 16-fold under $\alpha / r$ and only 4-fold under $\alpha / \sqrt{r}$. Neither rule keeps both kinds of update flat. In the same teaching model, $\alpha / \sqrt{r}$ makes the first update of a rank 256 adapter four times that of a rank 16 adapter, so its steady later steps come with a larger first step. The difference matters only at large ranks. At the common ranks of 8 to 64 either rule works once the learning rate is tuned.

The learning rate sits well above full fine-tuning's. Thinking Machines' [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/) swept 14 Llama and Qwen models. It found the best LoRA learning rate about 10 times the best full fine-tuning rate, for supervised fine-tuning and reinforcement learning alike. That rate was also nearly independent of rank, changing by less than a factor of 2 between rank 4 and rank 512. That rank independence is the $\alpha / r$ scale at work, and the study found no better initialization than the PEFT defaults.

## Target matrices and intrinsic rank

LoRA could adapt seven matrices in each block of the 7B. Four are the attention projections $W_Q$, $W_K$, $W_V$ and $W_O$, and three are the gate, up and down matrices of the [SwiGLU](/tutorials/llm-fundamentals/the-transformer-block-and-model-anatomy/#swiglu) feed-forward network. The chosen set is called the **target modules**. The original [LoRA paper](https://arxiv.org/abs/2106.09685) adapted only attention. On GPT-3 under a fixed budget, it found that $W_Q$ and $W_V$ together beat $W_Q$ alone at a higher rank. Later work moved the default to every matrix. [QLoRA](https://arxiv.org/abs/2305.14314) reported that all linear layers were needed to match full fine-tuning, and LoRA Without Regret found the feed-forward matrices matter most. On Llama 3.1 8B, attention-only LoRA at rank 256 (0.25 billion parameters) did worse than feed-forward-only LoRA at rank 128 (0.24 billion), so placement matters more than count. On the 7B, attention-only adapters at rank 38 cost the same 40 million parameters as all seven matrices at rank 16. The second spends two thirds of them in the feed-forward network, where two thirds of the weights sit.

Mixture of experts models raise the count, because each expert is its own feed-forward network and gets its own adapter. On the reference MoE, rank 16 on all 8 experts and attention comes to 240,123,904 parameters, six times the dense 7B's adapter. LoRA Without Regret gave each expert the total rank divided by the number of active experts, which for top-2 routing means rank 8 and 126,877,696 parameters. Routing itself belongs to [Mixture of Experts](/tutorials/llm-deep-dive/mixture-of-experts-at-scale/).

A rank of 16 out of 4,096 possible directions works because the change fine-tuning makes is close to low rank. A 4 by 4 update shows what that means in numbers:

$$
\Delta W = \begin{bmatrix} 1.0 & 2.0 & 0.0 & 1.1 \\ 2.0 & 4.1 & 0.0 & 2.0 \\ 0.5 & 1.0 & 0.1 & 0.5 \\ 1.0 & 2.0 & 0.0 & 0.9 \end{bmatrix}
$$

Every row is nearly a multiple of $(1, 2, 0, 1)$. An update's singular values are its lengths along its independent directions. This one's are 6.19, 0.131, 0.098 and 0.025, so the best rank-one approximation keeps $6.19^2 / (6.19^2 + 0.131^2 + 0.098^2 + 0.025^2) = 99.93\%$ of the update's squared size. A rank-one adapter loses almost nothing here, while a rank-one adapter on a matrix with four equal singular values would lose three quarters.

Measured evidence agrees. The **intrinsic dimension** of a task is the smallest number of directions in parameter space that reach most of full training's quality. [Li et al.](https://arxiv.org/abs/1804.08838) measured it by training inside a random subspace. [Aghajanyan et al.](https://arxiv.org/abs/2012.13255) found RoBERTa reaching 90% of full fine-tuning on a paraphrase task with only 200 parameters projected into the full space, and larger pretrained models having smaller intrinsic dimensions. The LoRA paper compared adapters trained at ranks 8 and 64 and found that their top few directions largely coincide, with the rest looking like noise.

The limit is capacity. LoRA Without Regret found LoRA matching full fine-tuning on small and medium instruction and reasoning datasets. LoRA fell behind once a dataset held more than the adapter could absorb, and it did so by learning less per step rather than by hitting a floor. It also found LoRA losing more than full fine-tuning at large batch sizes, at every rank. [LoRA Learns Less and Forgets Less](https://arxiv.org/abs/2405.09673) saw the same on large code and math corpora. There, full fine-tuning's weight changes had a rank 10 to 100 times higher than typical LoRA settings, and LoRA in return kept more of the base model's general ability.

Reinforcement learning sits at the other extreme. [Reinforcement learning with verifiable rewards](/tutorials/llm-fundamentals/post-training-from-base-model-to-assistant/#verifiable-rewards-and-grpo) gives about one bit of feedback per sampled answer, so 10,000 math problems with 32 samples each carry roughly 320,000 bits. LoRA Without Regret found LoRA matching full fine-tuning on such runs at ranks as low as 1. For the 7B, rank 1 on all seven matrices is $39{,}976{,}960 / 16 = 2{,}498{,}560$ parameters, several times more numbers than the run has bits to put into them.

## LoRA memory budget and merging

A LoRA run stores the frozen base, the adapter with its training state, the activations, and a small amount of workspace. Each term shrinks by a different amount, for a different reason. Gradients, master weights and AdamW moments exist only for parameters that train, so the 16 bytes per parameter of full fine-tuning now apply to the adapter alone. That budget falls in proportion to the 0.59% trainable share. The frozen base still sits in memory at its 2 bytes per weight, since every forward and backward pass reads it. It becomes the largest term. Activations depend on the layers the data passes through, not on which of them train, so they stay at full fine-tuning's size. The walkthrough below prices each one for the 7B with rank 16 adapters on all seven matrices of every block.

Step 5 also explains why LoRA steps are not much faster than full fine-tuning steps. The base weights still do their forward work, and the adapters add a small amount of computation. The backward pass still computes the gradient with respect to layer inputs while skipping gradients for the frozen weights. The $6N$ rule from the [compute budget](/tutorials/llm-fundamentals/pretraining-at-scale/#the-compute-budget) splits a full step on the 7B into about 13.5 GFLOPs per token forward, 13.5 for the gradients with respect to layer inputs and 13.5 for the gradients with respect to weights, 40.4 in all. LoRA drops the third share and keeps the other two, about 27 GFLOPs. The 40 million adapter parameters themselves add a few tenths of a GFLOP. LoRA Without Regret puts a LoRA step at a little over two thirds of a full fine-tuning step's arithmetic, which is that ratio. The estimate cuts training state by about sevenfold and model arithmetic by about a third. The wall-clock speedup depends on the kernels, activation handling and communication.

### Merging into the base

Adding $\tfrac{\alpha}{r} BA$ into $W$ gives a model with the original shape and no extra latency. The merge is one matrix product per adapted matrix. For one attention matrix, the rank 16 factors hold 131,072 numbers and expand into a full $4{,}096 \times 4{,}096$ update of 16.8 million entries. The whole 7B merge costs about 207 GFLOPs, the forward pass of about fifteen tokens. The result is again a 13.48 GB model, a full copy for that one task in place of the 80 MB file. Three details decide whether the merge is safe.

The first is rounding. A [bf16](/tutorials/llm-fundamentals/pretraining-at-scale/#mixed-precision) number keeps 8 significant bits. A typical weight of 0.02 lies between 0.015625 and 0.03125, and in that range neighboring values are $2^{-13} = 0.000122$ apart. Half that spacing is 0.000061. An update entry below it vanishes when added into such a weight, and an entry between 0.000061 and 0.000183 lands as exactly 0.000122. An entry of 0.00005 is lost, and one of 0.0001 is applied 22% too large. An unmerged adapter adds $BAx$ to the output, where such entries still count at their true size. A merged bf16 model is close to the unmerged one but not identical, so the evaluated version should be the served version.

The second is quantization. A 4-bit base cannot absorb an update without being quantized again, so a QLoRA adapter is usually merged into a bf16 copy of the base. The third is reversibility. A weight of exactly 0.03125 sits where the bf16 spacing doubles, 0.000244 above it and 0.000122 below it. Adding 0.0001 leaves it at 0.03125, since the update is under half the upper spacing. Subtracting 0.0001 afterwards rounds down to 0.031128, so the weight ends 0.000122 below where it started. Small errors like this scatter over billions of weights, and they are one reason a deployment that switches adapters keeps them unmerged.

## LoRA variants

The variants that stuck change how the update is parameterized, how it is scaled, or how fast each factor learns. The [LoRA scale and initialization](#lora-scale-and-initialization) section already covered the scaling change, rsLoRA. The other two are DoRA and LoRA+.

**DoRA** splits each row of a weight matrix into a length and a direction and trains them separately. The name stands for weight-decomposed low-rank adaptation, from [Liu et al.](https://arxiv.org/abs/2402.09353). The direction comes from the LoRA-updated matrix after each row is normalized, and a trained vector $m$ holds one length per row:

$$
W' = m \odot \frac{W + \tfrac{\alpha}{r} B A}{\lVert W + \tfrac{\alpha}{r} B A \rVert_{\text{row}}}.
$$

Here $\lVert \cdot \rVert_{\text{row}}$ divides each row by its own length, $\odot$ multiplies row $i$ by $m_i$, and $m$ starts at the row lengths of $W$, so training begins at the base model. For a row $(3, 4)$ of length 5 and a LoRA update of $(0.5, -0.5)$, plain LoRA gives $(3.5, 3.5)$, which turns the row by 8.1 degrees and also shrinks it to length 4.95. Under DoRA the same update sets only the direction, so the row becomes $(3.54, 3.54)$ with length still 5, and if training raises $m$ to 6 it becomes $(4.24, 4.24)$. The paper reports that full fine-tuning tends to change direction and length in opposite amounts while LoRA changes them together, and that DoRA's pattern looks more like full fine-tuning. The extra cost is 1,359,872 lengths for the 7B with all seven matrices plus the row norms at every step, and the trained result merges like LoRA.

**LoRA+** keeps the parameterization and gives $B$ a larger learning rate than $A$ by a fixed ratio. It comes from [Hayou et al.](https://arxiv.org/abs/2402.12354). Its argument comes from the shapes of the two factors. Once $B$ is nonzero, a step in $A$ changes the 16 numbers of $Ax$, and each of them is a sum over all 4,096 inputs. AdamW moves each entry by roughly the learning rate, so the effect of a step in $A$ grows with the model's width. A step in $B$ acts on those 16 numbers only, and its effect does not grow with width. A rate small enough to keep $A$'s steps stable therefore leaves $B$ moving slowly, a rate large enough for $B$ makes $A$'s steps too large, and the mismatch widens as models get wider. LoRA+ fixes the ratio of the two rates and tunes only one of them, so the search costs the same as plain LoRA's. The best ratio varied with model and task, around 16 for RoBERTa and 2 to 4 for Llama in the paper's own runs. The paper reports up to about twice the training speed and gains of 1 to 2 points at the same compute. Results vary by setup. Using tuned shared learning rates, LoRA Without Regret could not improve on the default of equal rates.

| Variant | What it changes | Extra cost | When it tends to help |
|---|---|---|---|
| rsLoRA | Scale $\alpha/\sqrt{r}$ instead of $\alpha/r$ | None | Ranks of 128 and above that otherwise learn too slowly |
| DoRA | Separate trained length per row, LoRA sets the direction | 1.36 million numbers for the 7B, row norms every step | Low ranks where LoRA trails full fine-tuning |
| LoRA+ | Learning rate of $B$ a fixed multiple of that of $A$, from about 2 to 16 | None | Faster convergence when the learning rate cannot be tuned per run |

All three keep LoRA's frozen base and its merge, and plain LoRA on every matrix with a tuned learning rate remains the usual starting point.

## Prefix and prompt tuning

Another family trains the input that attention sees instead of any weight. **Prompt tuning** learns a few vectors that sit in front of the text's token embeddings, as if they were tokens no tokenizer could produce. It comes from [Lester et al.](https://arxiv.org/abs/2104.08691). Twenty such vectors for the 7B are $20 \times 4{,}096 = 81{,}920$ parameters, a five-hundredth of a rank 16 adapter. The paper found the gap to full fine-tuning large for small models and closing as models grow, until it nearly vanished for T5 at 11 billion parameters. [Li and Liang](https://arxiv.org/abs/2101.00190) went deeper with **prefix tuning**. It learns a key and a value for each of $p$ extra positions in every layer's attention. The prefix has no query, so text tokens can attend to it but it never computes anything. With $p = 20$ the 7B gets $2 \times 20 \times 4{,}096 \times 32 = 5{,}242{,}880$ parameters, trained through a small auxiliary network because optimizing them directly was unstable.

![Prefix attention mask](/images/llm-deep-dive/16f-prefix-attention-mask.png)

A prefix gives every text token extra positions to read, and those positions compete with the text for the same attention weights. Each token can attend to all three prefix positions in addition to the earlier text that the [causal mask](/tutorials/llm-fundamentals/attention-and-positional-information/#the-causal-mask) already allows. Before, the first token "the" could only attend to itself. If its scores against the prefix positions are 1, 0 and 0 and against itself 1, softmax gives weights 0.366, 0.134, 0.134 and 0.366. The token's output keeps only 0.366 of its old value and draws the other 0.634 from the learned prefix values. [He et al.](https://arxiv.org/abs/2110.04366) showed that this holds in general. A head's output under prefix tuning is $(1 - \lambda)$ times its original output plus $\lambda$ times an attention output over the prefix alone, where $\lambda$ is the share of attention the prefix receives, 0.634 here.

The costs differ from LoRA's. Prefix positions occupy the [key value cache](/tutorials/llm-fundamentals/inference-and-decoding/#the-key-value-cache) like real tokens, and every decode step attends over them. On the 7B that is 20 positions at 0.5 MiB each, or 10 MiB per sequence. Prompt tuning also uses up 20 of the 4,096 context positions. Neither can be merged into weights, since they act on attention inputs rather than on a matrix. Their remaining advantage is size and isolation. A task is 164 KB for the 20 prompt vectors in bf16 or about 10 MB for the prefix. Requests for different tasks can share a batch with no special kernels, since each request simply carries its own extra positions. In current open-model practice LoRA has largely replaced both, because it matches full fine-tuning more reliably at the same parameter count.

## QLoRA
After LoRA, the frozen base is 13.48 of the 14.12 GB of training memory before activations. QLoRA stores it in four bits and trains bf16 adapters through it.

Training through a 4-bit base works because the base is only ever read. Its codes never change during the run. When a layer runs, it expands its blocks back to bf16 values and uses them for that one multiply. The backward pass expands the same blocks again to carry the gradient to the layer's input and from there to the adapters in earlier layers, and no gradient is ever formed for the codes themselves. The adapters therefore learn on top of the quantized base they will run with, and the base's rounding is part of the model they adapt from the first step. The [QLoRA paper](https://arxiv.org/abs/2305.14314) reports that this preserves full 16-bit fine-tuning performance while fitting a 65B model on a single 48 GB GPU. Three mechanisms make the plan work. NF4 keeps four bits accurate for weights, double quantization keeps the per-block scales from eating the savings, and paged optimizers keep a memory spike from crashing the run.

The format starts from **blockwise absmax quantization**. Weights are split into blocks of 64, each block's largest magnitude becomes its scale, dividing by the scale puts the block between $-1$ and $1$, and each value is stored as the 4-bit index of the nearest of 16 levels. NF4 picks those levels from quantiles of the normal distribution, because pretrained weights are close to normal. The quantiles are the points that cut the distribution into equal-probability pieces. Each level then serves roughly the same share of weights, and the levels crowd near zero. The construction uses 8 positive levels, 7 negative ones and an exact zero, scaled so the ends are $-1$ and $1$. The 16 levels are $-1$, $-0.696$, $-0.525$, $-0.395$, $-0.284$, $-0.185$, $-0.091$, $0$, $0.080$, $0.161$, $0.246$, $0.338$, $0.441$, $0.563$, $0.723$ and $1$.

Blocks keep one unusual weight from spoiling the rest. With a single scale for a whole matrix, one weight of 0.5 among typical weights of 0.02 would divide them all down to about 0.04. That is halfway between zero and the smallest positive level of 0.080, so most of the matrix would collapse onto the three codes nearest zero. With blocks of 64, that weight sets the scale for its own block only, and every other block keeps a scale that fits its own weights. The price is one 32-bit scale per block, which is 0.5 bits per weight at a block size of 64. The block size therefore trades accuracy inside each block against bits spent on scales.

**Double quantization** shrinks those 0.5 bits further by quantizing the scales themselves. The 32-bit scales are stored as 8-bit numbers, with one 32-bit scale for every 256 of them. That costs $8/64 + 32/(64 \times 256) = 0.127$ bits per weight and saves 0.373. On the 7B's 6,476,005,376 linear weights that saves 302 MB. The full QLoRA base is then 3.238 GB of 4-bit codes, 0.103 GB of scales, and 0.524 GB for the embedding table and output head. The common bitsandbytes setup keeps those two tables in bf16. With the half megabyte of norm gains the base comes to 3.87 GB. Quantizing every weight, the two tables included, would give 3.48 GB, and the difference is those two tables. With the 0.64 GB of adapter state and about 2 GB of checkpointed activations, a QLoRA run on the 7B needs about 6.5 GB. The arithmetic matters more at 70B. The reference 70B's linear weights at 4.127 bits plus bf16 embeddings come to 36.4 GB. Rank 16 adapters on all seven matrices add 207,093,760 parameters and 3.31 GB of state, so the run starts at 39.7 GB and fits on one 80 GB GPU. The bf16 base alone is 137.95 GB.

The third mechanism is **paged optimizers**. They keep the optimizer state in memory the GPU driver can move to CPU memory when the GPU runs short, so one unusually long sequence slows a step instead of crashing the run. Each page-out costs transfer time, so steady memory pressure still needs shorter sequences or more checkpointing.

QLoRA's price is speed. NF4 is a lookup table with no matching GPU arithmetic, so each layer expands its weights to bf16 before every matrix multiply, forward and backward. With gradient checkpointing that happens three times per layer per step. It happens once in the forward pass, once when the backward pass recomputes it, and once for the backward multiply itself. The expansion work is therefore paid on every one of the base's 6.5 billion linear weights each time. Newer low-bit formats avoid that step where hardware supports them, and [Numerics and Stability](/tutorials/llm-deep-dive/numerics-and-training-stability/) covers their numerics. A base stored in FP8 takes 6.74 GB for the 7B and runs its matrix multiplies directly in FP8 on an H100, at twice the bf16 peak. **MXFP4** stores blocks of 32 four-bit floating point values that share one 8-bit power-of-two scale, which comes to 4.25 bits per weight. Recent GPUs compute with it directly, though the H100 has no FP4 arithmetic and treats it as a storage format. OpenAI's [gpt-oss model card](https://cdn.openai.com/pdf/419b6906-9da6-406c-a19d-1bb078ac7637/oai_gpt-oss_model_card.pdf) reports its mixture of experts weights stored in MXFP4 at 4.25 bits per parameter, and NVIDIA's [fine-tuning guidance for gpt-oss](https://developer.nvidia.com/blog/fine-tuning-gpt-oss-for-accuracy-and-performance-with-quantization-aware-training/) upcasts those weights to bf16 for stable supervised fine-tuning before quantizing back. As with QLoRA's merge, a low-bit base is cheap to store and serve, but training changes usually happen at higher precision and are quantized again afterwards.

## Multi-adapter serving
Two requests can use different adapters while sharing the same base weights. **Multi-adapter serving** puts those requests in one batch and applies each adapter separately, so decoding reads the base weights once per step for both. At 80 MB each, the 66.5 GB left on an 80 GB GPU beside the 7B's weights would hold about 830 adapters and no cache at all, so a deployment with thousands of adapters keeps most in CPU memory and moves active ones in on demand.

[Punica](https://arxiv.org/abs/2310.18547) introduced the **SGMV** kernel, short for segmented gather matrix-vector multiplication. It computes every token's $B_i A_i x$ in one launch by gathering each token's own adapter. [S-LoRA](https://arxiv.org/abs/2311.03285) added **unified paging**, so adapters load and evict without fragmenting the cache. It keeps one paged GPU memory pool for adapter weights and cache entries, in the spirit of [PagedAttention](/tutorials/llm-fundamentals/inference-and-decoding/#continuous-batching-and-paged-attention). Current servers follow both. vLLM picks an adapter per request, runs [Punica-style kernels](https://docs.vllm.ai/en/latest/api/vllm/lora/punica_wrapper/index.html), and caps adapters per batch and the rank it reserves room for. Its [documentation](https://docs.vllm.ai/en/latest/features/lora.html) describes swapping adapter weights in place for asynchronous reinforcement learning, where the sampler keeps serving while the trainer publishes new versions. SGLang's [LoRA support](https://docs.sglang.io/advanced_features/lora.html) builds on S-LoRA and Punica, defaults to 8 adapter slots per batch, and evicts the least recently used adapter when the pool is full.

Step 6 is why multi-adapter serving is cheap on a [memory bandwidth bound](/tutorials/llm-fundamentals/inference-and-decoding/#memory-bandwidth-bound-decoding) decode. Each distinct adapter adds about 0.6% to the bytes. The remaining costs are practical. Room reserved for the largest rank is wasted on smaller adapters, an adapter loaded from CPU memory delays its first request, and every adapter is tied to the exact base it was trained on, so a base update invalidates all of them. How a scheduler fits these requests among everything else on the GPU is covered in [Serving Systems](/tutorials/llm-deep-dive/inference-systems-at-scale/).

Merging can also combine several fine-tuned models into one, with no adapters left to serve. A **task vector** is the difference between a fine-tuned model's weights $\theta_{\text{ft}}$ and the base's weights $\theta_0$, written $\tau = \theta_{\text{ft}} - \theta_0$. A LoRA adapter's $\tfrac{\alpha}{r} BA$ is a task vector restricted to rank $r$. **Task arithmetic** adds task vectors to the base, $\theta = \theta_0 + \lambda \sum_i \tau_i$, where $\lambda$ is one scaling factor tuned on held-out data. It comes from [Ilharco et al.](https://arxiv.org/abs/2212.04089) and can also subtract a task vector to remove a behavior. Adding them blindly lets them interfere. Take three task vectors over four parameters, $(0.5, -0.1, 0.3, 0)$, $(0.4, 0.2, -0.6, 0.05)$ and $(-0.1, 0.3, 0.4, -0.02)$. They average to $(0.267, 0.133, 0.033, 0.010)$, and the third parameter nearly cancels even though two of the three tasks moved it up by 0.3 or more.

**TIES-merging** from [Yadav et al.](https://arxiv.org/abs/2306.01708) resolves that in three steps. It trims each task vector to its largest entries. Keeping the top two of four gives $(0.5, 0, 0.3, 0)$, $(0.4, 0, -0.6, 0)$ and $(0, 0.3, 0.4, 0)$. It elects a sign for each parameter from the sum of the trimmed values. Here the sign is positive for the first three, since $0.3 - 0.6 + 0.4 = 0.1$ for the third. It then averages only the entries that agree with the elected sign, giving $(0.45, 0.3, 0.35, 0)$. The third parameter keeps a clear upward move of 0.35 instead of 0.033. **DARE** from [Yu et al.](https://arxiv.org/abs/2311.03099) drops a random fraction $p$ of each task vector's entries and multiplies the survivors by $1/(1-p)$ so the expected update stays the same. The paper reports that 90% or even 99% of the entries in fine-tuning deltas can be dropped this way without hurting the fine-tuned model, which leaves fewer overlapping entries to interfere when several are merged.

Merging is also routine inside post-training. [The Llama 3 paper](https://arxiv.org/abs/2407.21783) reports averaging models trained with different data versions or hyperparameters at each reward model, supervised fine-tuning and preference optimization stage. Merging two rank 16 adapters gives an update of rank up to 32. That update can no longer be stored as a single rank 16 adapter, so merged results are usually kept as full weights.

## Method selection

The right method follows from which budget binds and how many tasks share the base. [Domain Adaptation](/tutorials/llm-deep-dive/domain-adaptation-and-fine-tuning/) covers whether to fine-tune at all and how to run and judge a domain fine-tuning experiment. The table maps the situations covered here to a first choice and the qualification that comes with it.

| Situation | First choice | Main qualification |
|---|---|---|
| One task on the 7B, small or medium supervised set, one 80 GB GPU | LoRA at rank 16 on all seven matrices, learning rate about 10 times full fine-tuning's | Falls behind once the dataset holds more than the adapter can absorb |
| Base too large for bf16 training memory, such as the 70B on one GPU | QLoRA with NF4 and double quantization, or an FP8 base where supported | Slower steps, and the served format must be the one evaluated |
| Reinforcement learning fine-tuning with verifiable rewards | LoRA, even at low rank | The sampler must load each new adapter version promptly |
| Many tenants or tasks on one base | Unmerged adapters with multi-adapter batching | Adapter slots per batch, rank padding, and every adapter tied to one base version |
| One latency-critical task with a fixed adapter | Merge the adapter into a bf16 base | Switching tasks then means a separate deployment |
| Several tasks in one artifact without serving adapters | Merge task vectors with TIES or DARE | Each task needs its own check after merging |
| Several related tasks trained together | One backbone with a tuned mixing temperature, PCGrad if gradients conflict | PCGrad needs one gradient per task |
| Storage-bound model on a device | Cross-layer sharing or factorized embeddings | Compute and activations do not shrink |
| Large domain shift, such as a new language | Continued pretraining or full fine-tuning, then adapters per task | Full training state of 107.8 GB for the 7B |

Each row starts from what is fixed in the situation, such as the hardware, the number of tasks or the size of the shift. Its first choice is the method whose savings land on the budget that situation strains, which is one of the panels of the opening figure. The qualification is where that method tends to fail, so it is also the first thing worth measuring once the choice is running. Rows combine. A team serving 50 tenants from the 70B trains each adapter with QLoRA on one GPU and serves them unmerged. Those are the second and fourth rows. Both qualifications then apply. The adapters are judged on the base format the server actually runs, and all 50 are tied to that one quantized base version.

A short diagnosis shows the table in use. Take the first row's choice, a rank 16 LoRA run on the 7B. It trails a full fine-tuning baseline on held-out loss for a large instruction set. The first measurement is the learning rate, because the cheapest cause in this chapter is a LoRA run that reused full fine-tuning's rate, about ten times too low. If a sweep finds the best LoRA rate near ten times the full one and the gap remains, the second measurement is a rank sweep at that rate. A gap that shrinks as the rank rises means the adapter was short of capacity, which is the qualification in the first row. It points to a higher rank or to full fine-tuning for this dataset. Raising the rank is cheap to try. Rank 64 on all seven matrices is 159,907,840 parameters and 2.56 GB of training state, still small beside the 13.48 GB base. A gap that stays flat across ranks means the adapter's size was never the limit, and the batch size is the next suspect, since LoRA Without Regret found LoRA losing more than full fine-tuning at large batch sizes at every rank.

Two habits keep these choices reversible. Every adapter is stored with the exact base, tokenizer and quantization format it was trained against, so a base update is planned as a release of every dependent adapter. And each comparison between methods is made at matched learning-rate tuning, since LoRA run at full fine-tuning's learning rate looks much worse than LoRA run at its own.
