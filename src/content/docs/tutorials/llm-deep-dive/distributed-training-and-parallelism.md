One H100 and 2,048 H100s train the reference 70B model with exactly the same arithmetic, the $8.28 \times 10^{23}$ FLOPs that the [compute budget](/tutorials/llm-fundamentals/pretraining-at-scale/#the-compute-budget) gives for 2 trillion tokens. On one GPU at 40% utilization the run takes 66 years. On 2,048 it takes 11.8 days, provided every one of them keeps that 40%. Nothing about the hardware promises it, because the 2,048 GPUs now spend part of every step sending numbers to each other.

Memory is the other obstacle, and it applies before speed does. The 70B model has the Llama 2 70B shape, with 80 layers of width 8,192, 64 query heads sharing 8 key and value heads, and a SwiGLU width of 28,672. It holds 68,976,648,192 parameters. Its [training state](/tutorials/llm-fundamentals/pretraining-at-scale/#optimizer-memory) at 16 bytes per parameter is 1,103.6 GB, against 80 GB on one GPU. Every method in this chapter cuts the training computation along one axis, so that both the memory and the arithmetic per GPU shrink. Each method pays for its cut in communication.

![Memory and time walls](/images/llm-deep-dive/16c-memory-and-time-walls.png)

Three quarters of the training state is fp32 bookkeeping for the optimizer. The master weights and the two AdamW moments take 827.7 GB, while the bf16 weights that the forward pass actually multiplies with take 138 GB. Most of what has to be split is therefore state that only the optimizer step touches, which is why sharding the optimizer state is the first and cheapest saving later in the chapter. Activations come on top, 90 GB for one 4,096-token sequence. The two walls also differ in size. Memory alone would be satisfied by about 14 GPUs, but time needs far more. On 64 GPUs the run still takes 378 days, and 2,048 GPUs bring it to 11.8 days. Once 2,048 GPUs share the 1,103.6 GB, the state is about 0.54 GB per GPU if split evenly, so fitting stops being the hard part. The hard part is keeping the 40% while the GPUs exchange numbers. If communication pulls utilization down to 30%, the same run takes 15.8 days instead of 11.8.

The chapter first prices one training step, because its two kinds of memory respond to different cuts. The training state shrinks only when the parameters are split, while activations shrink when tokens or layers are split. Every cut is then paid for in messages between GPUs, so a short vocabulary of collective operations comes next, with the ring all-reduce worked by hand to show that its cost per GPU barely depends on the number of GPUs. With those prices in hand, the cuts come in the order they disturb the model. Copying the model and splitting the batch changes nothing inside it but stores the full state on every GPU, and sharding that state removes the repetition at the price of more traffic. When that traffic grows too large, the model itself is split, first each matrix inside a node where the links are fast, then the stack of layers into a pipeline across nodes, then a long sequence across GPUs. The last sections combine the cuts into one layout for 2,048 GPUs, compare it with the published layouts of Llama 3 and DeepSeek-V3, price a step second by second, and end with a table that maps slow or failing runs to their usual causes.

## Training memory
A training step needs two kinds of memory. **Training state** is everything that lives for the whole run. It holds the bf16 weights and gradients at 2 bytes each, plus the fp32 master weights and the two [AdamW](/tutorials/llm-fundamentals/pretraining-at-scale/#adamw) moments at 4 bytes each. For the 70B that is 137.95 GB of weights, 137.95 GB of gradients and 275.9 GB for each of the three fp32 tensors. That is 1,103.6 GB in all, enough to fill 13.8 GPUs before anything else is stored.

**Activation memory** is the second kind. It holds the intermediate results that the forward pass saves because the backward pass needs them again, and it grows with the number of tokens in flight rather than with the model size. A layer saves a tensor for one of two reasons. A matrix multiplication needs its input to compute the weight gradient, and a nonlinearity or normalization needs its input to compute its own slope. The table counts the numbers one 70B layer keeps per token in bf16. It assumes FlashAttention, so the attention scores are not stored ([Efficient Attention](/tutorials/llm-deep-dive/efficient-attention-mechanisms/) covers that kernel).

| Tensor kept for the backward pass | Numbers per token |
|---|---|
| Stream entering the attention RMSNorm | 8,192 |
| Normalized input to the query, key and value projections | 8,192 |
| Queries, keys and values after rotary embedding | 8,192 + 1,024 + 1,024 |
| Attention output, the input to the output projection | 8,192 |
| Stream entering the feed-forward RMSNorm | 8,192 |
| Normalized input to the gate and up projections | 8,192 |
| Gate and up outputs | 2 × 28,672 |
| Gated product, the input to the down projection | 28,672 |
| Total | 137,216 |

At 2 bytes each that is 274,432 bytes per token per layer, or 33.5 bytes per unit of width. That is close to the 34 that [Korthikanti et al.](https://arxiv.org/abs/2205.05198) derive for a GPT layer. One 4,096-token sequence therefore needs $274{,}432 \times 4{,}096 = 1.12$ GB per layer and 89.9 GB across 80 layers. Without FlashAttention each layer would also keep the softmax output, which is one 4,096 by 4,096 matrix per head. For 64 heads that is 524,288 bytes per token per layer, more than everything in the table combined.

The two terms behave differently, and that difference decides which cut fixes which problem. Training state is fixed by the parameter count, so only splitting the parameters across GPUs reduces it. Activations scale with the tokens a GPU processes at once and with the layers it holds, so splitting the batch, the sequence or the stack reduces them. Activation memory can also be cut without more GPUs by discarding activations in the forward pass and recomputing them in the backward pass. The section on [activation recomputation](/tutorials/llm-deep-dive/numerics-and-training-stability/#activation-recomputation) in Numerics and Stability explains how. Keeping only each layer's input brings the 89.9 GB down to $4{,}096 \times 8{,}192 \times 2 \times 80 = 5.37$ GB at the cost of a second forward pass.

## Collective communication
Every parallel method needs GPUs to exchange numbers, and almost all of that exchange uses five patterns. A **collective** is an operation that every GPU in a group calls at the same time. Each GPU contributes its own buffer, so the group behaves like one program. NVIDIA's NCCL and similar libraries implement them. Each GPU in the group has an index called its **rank**, here GPU 1 to GPU 4.

A choice of starting values makes every pattern readable at a glance. Four GPUs each hold a vector of four chunks, and GPU 1 holds $(1, 2, 3, 4)$, GPU 2 ten times that, GPU 3 a hundred times and GPU 4 a thousand times. The digits of a sum then show which GPUs contributed, and 1111 means all four did.

![Collective primitives](/images/llm-deep-dive/16c-collective-primitives.png)

**Broadcast** copies one GPU's vector to every GPU, which is how training starts from identical weights. **All-reduce** sums the vectors and leaves the full sum on every GPU, so all four end with $(1111, 2222, 3333, 4444)$. **Reduce-scatter** sums the vectors but leaves each GPU only its own chunk of the sum, so GPU 2 ends with 2222 alone. **All-gather** does the reverse of a scatter. Each GPU starts with one chunk and ends with all of them. **All-to-all** sends chunk $k$ of every GPU to GPU $k$, so GPU 2 ends with $(2, 20, 200, 2000)$, a transpose of the data. Mixture of experts training uses all-to-all to send tokens to the GPUs that hold their experts, which [Mixture of Experts](/tutorials/llm-deep-dive/mixture-of-experts-at-scale/) develops.

The names describe what happens to the data. To reduce is to combine many vectors into one by adding them, to scatter is to hand different pieces to different GPUs, and to gather is to collect pieces into one whole. A reduce-scatter therefore adds and then splits the result, and an all-gather collects every piece onto every GPU.

Two facts about these patterns come up in every later section. An all-reduce is a reduce-scatter followed by an all-gather. In the figure, the result of the reduce-scatter row is exactly the starting point of the all-gather row, and the all-gather ends where the all-reduce ends. The cost column gives the bytes each GPU sends for a vector of $S$ bytes on $p$ GPUs, and it follows from that. A reduce-scatter or an all-gather sends $(p-1)S/p$, and an all-reduce sends twice that, $2(p-1)S/p$.

The $(p-1)S/p$ figure is also a floor that no algorithm can beat. After a reduce-scatter, GPU $k$ holds the sum of chunk $k$, and that sum needs the other $p - 1$ GPUs' copies of the chunk, $S/p$ bytes each. On the four GPUs, GPU 2 cannot produce 2222 without receiving 2, 200 and 2000, three quarters of a vector. Every GPU must receive that much, and every byte received was sent by some GPU, so on average each GPU sends at least $(p-1)S/p$ as well. An all-gather is the mirror image, since each GPU must receive the $p - 1$ chunks it lacks. The next section shows an algorithm that meets this floor exactly.

## Ring all-reduce

The simplest way to sum gradients is to send everything to one GPU, add, and send the sum back. With 4 GPUs the collecting GPU receives three full vectors and sends three, and with 64 GPUs it receives 63, so its link becomes the bottleneck while every other link sits idle. The **ring all-reduce** arranges the GPUs in a circle, cuts the vector into $p$ chunks, and has every GPU send one chunk to its neighbor at every step, so all links are busy all the time. [Horovod](https://arxiv.org/abs/1802.05799) popularized it for deep learning.

The ring runs in two phases, which match the two halves of an all-reduce. In the first phase each chunk travels around the circle once. Every GPU it passes adds its own copy of that chunk before passing it on, so after $p - 1$ steps each GPU holds one chunk that carries the contributions of all $p$ GPUs. That phase is a reduce-scatter. In the second phase the finished chunks travel around once more, and each GPU they reach replaces its stale copy, so after another $p - 1$ steps every GPU holds every finished chunk. That phase is an all-gather.

![Ring all reduce paths](/images/llm-deep-dive/16c-ring-all-reduce-paths.png)

Each chunk's sum finishes on the GPU just before the one where it started. Chunk 1 leaves GPU 1 as 1, becomes 11 on GPU 2 and 111 on GPU 3, and reaches 1111 on GPU 4 after $p - 1 = 3$ hops. Each of the other chunks starts one GPU further along, so after three steps each GPU owns a different finished chunk, which is exactly the reduce-scatter result of the [collective communication](#collective-communication) section. Three more hops copy each finished chunk to the other three GPUs. Every step uses every link and waits until all four transfers have arrived, so the slowest link sets the time of every step. One degraded cable slows the whole all-reduce, not just the two GPUs at its ends, which is the straggler problem the [data parallelism](#data-parallelism) section returns to.

Cutting the vector into $p$ chunks is what keeps the work balanced. At every step each GPU sends a different chunk, so the ring moves $p$ chunks at once, and no GPU ever sends or receives more than $S/p$ bytes in one step. Each GPU therefore sends twice the floor of the [collective communication](#collective-communication) section in total, which is the least an all-reduce can cost since it contains both a reduce-scatter and an all-gather. The central scheme does far worse. For the 70B's 137.95 GB of bf16 gradients on 64 GPUs, the collecting GPU would receive $63 \times 137.95 = 8{,}691$ GB and send as much back. That takes about 174 s at 50 GB/s, while the ring needs about 5.4 s, as worked out below. The ratio is $p/2 = 32$, so the central scheme slows down in proportion to the number of GPUs and the ring does not.

Each phase takes $p - 1$ steps and each step moves $S/p$ bytes per GPU, so the total is

$$
\text{bytes sent per GPU} = 2 \cdot \frac{p-1}{p} \cdot S.
$$

Here $S$ is the size of the full vector in bytes and $p$ the number of GPUs, and for $p = 4$ the factor is $2 \times 3/4 = 1.5$. The factor approaches 2 as $p$ grows and never exceeds it, so the time spent moving bytes barely depends on how many GPUs share the sum. That is why the ring is called bandwidth optimal. For the 70B's 137.95 GB of bf16 gradients, 8 GPUs on NVLink send $2 \times 7/8 \times 137.95 = 241.4$ GB each, about 0.54 s at 450 GB/s. Over InfiniBand, 64 GPUs send 271.6 GB each, about 5.4 s at 50 GB/s. The ninefold gap between those times is almost entirely the link speed, not the GPU count.

The bandwidth formula leaves out a fixed cost per message. A common model writes the time of a collective as $\alpha \cdot k + B/\beta$, where $k$ is the number of sequential steps, $\alpha$ is the latency of one step, $B$ is the bytes each GPU sends and $\beta$ is the link bandwidth. A ring has $k = 2(p-1)$ steps. With a teaching estimate of $\alpha = 10$ microseconds across nodes, a ring over 2,048 GPUs spends $4{,}094 \times 10\ \mu\text{s} = 41$ ms on latency alone, while the bandwidth term for a 25 MB gradient bucket is about 1 ms. Small messages on large groups are therefore latency bound. NCCL then switches to tree algorithms or to hierarchical schemes. A tree's step count grows with $\log_2 p$, about 22 steps for 2,048 GPUs. A hierarchical scheme reduces inside each node over NVLink first and sends only one eighth of the data per GPU across nodes. Benchmarks report **bus bandwidth**, which is the measured $S/t$ multiplied by $2(p-1)/p$. With that scaling, a number close to the link speed means the collective is running as well as the hardware allows regardless of $p$.

## Data parallelism
The cheapest way to use many GPUs keeps the model whole and splits the data. In **data parallelism** every GPU holds a full copy of the model, runs forward and backward on its own slice of the batch, and then all-reduces the gradients so every copy applies the same update and stays identical. The **global batch** is the total set of sequences one optimizer step uses. A **micro-batch** is the slice one GPU processes in one forward and backward pass. Under **gradient accumulation**, the same GPU runs several micro-batches and adds their gradients before the all-reduce. The global batch therefore equals the micro-batch times the accumulation count times the number of copies.

The 7B reference model shows the timing. Its training state of 107.8 GB does not fit one GPU either, which the [ZeRO](#zero) section fixes without changing any traffic computed here. Its bf16 gradients are 13.48 GB, so a ring all-reduce across 64 GPUs over InfiniBand sends 26.5 GB per GPU and takes about 0.53 s. A micro-batch of 4 sequences of 4,096 tokens costs $16{,}384 \times 40.4$ GFLOPs $= 6.62 \times 10^{14}$ FLOPs, about 1.67 s at 40% utilization. The backward pass is about two thirds of that, 1.12 s. Run one after the other, the step takes 2.2 s and the network adds 32%.

**Bucketing** removes most of that. The backward pass produces gradients from the last layer to the first, so the gradients of layer 32 are final long before those of layer 1. PyTorch's DistributedDataParallel groups gradients into buckets of 25 MB by default. It starts each bucket's all-reduce as soon as the bucket is full, while backward keeps running on earlier layers. [Li et al.](https://arxiv.org/abs/2006.15704) describe the design. The 13.48 GB of gradients form about 539 buckets. Only the last one has nothing left to overlap with, and it takes about 1 ms to transfer. **Exposed communication** is the part of a transfer that no computation hides, and it is the part that costs time. Here the 0.53 s transfer fits inside the 1.12 s backward, so almost all of it is hidden. Buckets are a compromise. One bucket per tensor would pay the per-message latency hundreds of times, and one bucket for everything could not start until backward had finished.

![Data parallel replicas](/images/llm-deep-dive/16c-data-parallel-replicas.png)

Summing the four gradients gives exactly the gradient of the 16 sequences taken together, because the gradient of a sum of losses is the sum of their gradients. Data parallelism therefore computes the same update as one GPU working through the whole batch, only faster, and every copy that applies it stays identical without ever exchanging weights. Bucketing hides that sum only when the backward pass is long enough. The all-reduce always moves the same 13.48 GB, however many sequences each GPU processed, while the backward pass it hides behind grows with the micro-batch. With 4 sequences, 1.12 s of backward covers the 0.53 s transfer. With 1 sequence, backward takes about 0.28 s, so at least 0.25 s of the transfer is left exposed after it ends. Small micro-batches are where data parallelism stops scaling, and they get smaller as more GPUs share a fixed global batch.

Data parallelism has two limits that no overlap removes. The first is the batch. Llama 2 trained with a global batch of about 4 million tokens, which is 1,024 sequences of 4,096. So 2,048 GPUs could not each receive even one whole sequence, and larger batches stop improving the loss per token beyond a critical size. The second is that every GPU waits for the slowest one at every all-reduce. A **straggler** is a GPU that is consistently slower because of a faulty link, a hot chip or a busy host. It sets the step time for the whole job.

## ZeRO
Plain data parallelism stores the same 1,103.6 GB of training state on every GPU, and every copy computes the same update from the same averaged gradient. [ZeRO](https://arxiv.org/abs/1910.02054) removes that repetition in three stages. The name stands for Zero Redundancy Optimizer. Each GPU becomes the owner of a $1/p$ slice of the parameters and keeps only the state that slice needs. That slice is called its **shard**. Stage 1 shards the optimizer state, stage 2 also shards the gradients, and stage 3 also shards the bf16 weights.

| Layout on 64 GPUs | Bytes per GPU | 70B on 64 GPUs |
|---|---|---|
| Plain data parallelism | $16\Psi$ | 1,103.6 GB |
| ZeRO stage 1 | $4\Psi + 12\Psi/p$ | 288.8 GB |
| ZeRO stage 2 | $2\Psi + 14\Psi/p$ | 153.0 GB |
| ZeRO stage 3 | $16\Psi/p$ | 17.2 GB |

Here $\Psi$ is the parameter count of 68,976,648,192, and $p = 64$. Each row keeps at full size whatever its stage has not yet sharded. Stage 1 still stores the bf16 weights and gradients whole, which takes $4\Psi = 275.9$ GB. It divides only the 12 bytes of fp32 state, which adds 12.9 GB. Stage 2 also divides the gradients, leaving 137.95 GB of weights plus 15.1 GB of shards. Stage 3 divides all 16 bytes, $1{,}103.6/64 = 17.2$ GB. The full-size term outweighs the shards until the last stage, so only stage 3 fits the 70B on 80 GB GPUs. Stages 1 and 2 cost no extra traffic, because an all-reduce is already a reduce-scatter plus an all-gather. Stage 2 reduce-scatters the gradients so each owner receives the summed slice it updates, the owner steps its slice, and an all-gather returns the new weights. Stage 3 pays for its saving, because no GPU keeps the full weights between uses. Each layer's weights must be all-gathered before the forward pass and again before the backward pass, so the step moves the weights three times (two gathers and one reduce-scatter) instead of twice. That is 1.5 times the traffic of plain data parallelism.

On the 70B the "one borrowed weight" of step 3 is one 80th of the model, a full layer of 855,654,400 parameters or 1.71 GB in bf16. Real implementations prefetch the next layer while the current one computes, so about two layers totaling 3.4 GB sit gathered at once. That leaves room for activations, but not for the 89.9 GB of one full sequence. A pure ZeRO-3 run of the 70B therefore needs recomputation as well.

**Fully sharded data parallelism**, or FSDP, is PyTorch's implementation of stage 3, described in [Zhao et al.](https://arxiv.org/abs/2304.11277). Its first version flattened each wrapped block's weights into one long buffer and sharded that buffer. **FSDP2** instead shards every parameter tensor separately along its first dimension, which makes it easier to combine with tensor and pipeline parallelism. The [TorchTitan paper](https://arxiv.org/abs/2410.06511) reports about 7% lower memory than the first version on Llama 2 7B and uses FSDP2 as TorchTitan's default data-parallel layer. **Hybrid sharded data parallelism**, or HSDP, shards inside a group of GPUs and replicates across groups. With the 7B, sharding over the 8 GPUs of one node leaves $107.8/8 = 13.5$ GB per GPU, and only a plain gradient all-reduce crosses InfiniBand between nodes, so the gathers that block every layer stay on NVLink.

ZeRO alone does not scale to 2,048 GPUs for the 70B. With 4 million tokens per step, each GPU would get 2,048 tokens, which is half a sequence. That is $8.48 \times 10^{14}$ FLOPs or 2.14 s of work at 40% utilization. ZeRO-3 would still move the weights three times per step, $3 \times 2{,}047/2{,}048 \times 137.95 = 413.7$ GB per GPU, which takes 8.3 s over InfiniBand. Communication four times longer than the compute is a run that mostly waits, and the remaining sections split the model itself so that fewer GPUs share each copy.

## Tensor parallelism

Sharding still runs every layer whole on each GPU, one layer at a time. **Tensor parallelism** splits the matrices of each layer across GPUs so that each GPU computes part of every layer and stores only part of its weights. It comes from [Megatron-LM](https://arxiv.org/abs/1909.08053). The design question is how to split two matrix multiplications in a row so that the GPUs exchange as little as possible.

The answer is to split the first matrix by columns and the second by rows. A **column-parallel** layer gives each GPU some of the output columns, so each GPU computes some of the hidden units in full. A **row-parallel** layer gives each GPU the rows that match its hidden units, so each GPU produces a partial sum of every output number, and one all-reduce adds the partial sums.

The order matters because of the nonlinearity between the two matrices. A column split hands each GPU complete hidden units. Each one is the full dot product of the input with one column, so ReLU or SiLU can act on them without any knowledge of what the other GPUs hold. A row split of the first matrix would give each GPU a partial sum of every hidden unit, and a nonlinearity does not distribute over a sum. ReLU of $-2 + 1$ is 0, while ReLU of $-2$ plus ReLU of $1$ is 1. So the partial sums would have to be added before the ReLU, which costs an all-reduce in the middle of the pair. With the column split first, the second matrix finds its input already divided the way it needs. Each GPU holds exactly the hidden units that meet its own rows of the second matrix, multiplies them without communication, and only the final output needs a sum.

The backward pass mirrors the forward one. The gradient flowing back into the row-parallel layer's input splits along the same hidden units, so it stays local. In contrast, every GPU's columns of the first matrix contribute to the gradient of the shared input. That gradient is therefore a partial sum and needs its own all-reduce. Memory follows the split. With $t$ GPUs, each stores $1/t$ of both weight matrices and $1/t$ of the hidden activations. The input and output of the pair stay whole on every GPU, and the [sequence parallelism](#sequence-parallelism) section closes that gap. The price is one all-reduce of the layer's full output in each direction.

![Tensor parallel column and row split](/images/llm-deep-dive/16c-tensor-parallel-column-and-row-split.png)

What crosses between the GPUs is the output of the pair, never the hidden layer. In the example that is two numbers, while the four hidden units stay where they were computed. The same holds at full size. The 70B's feed-forward network has 28,672 hidden units per token but exchanges only the 8,192-number output, so the traffic depends on the model width and not on the hidden width. Doubling the hidden width would double each GPU's share of the arithmetic and the weights but add no communication. Every GPU still ends with the complete output, which lets the next layer start from the same input on every GPU.

The 70B's [SwiGLU](/tutorials/llm-fundamentals/the-transformer-block-and-model-anatomy/#swiglu) feed-forward network uses the same pattern with two column-parallel matrices. The gate and up projections are split by the same columns, so the coordinate-by-coordinate product of SiLU(gate) and up stays local. With 8 GPUs each holds 3,584 of the 28,672 columns. Attention splits by heads. The query, key and value projections are column-parallel, each GPU runs attention for its heads, and the output projection is row-parallel. With 8 GPUs each takes 8 of the 64 query heads and 1 of the 8 key and value heads, because [grouped-query attention](/tutorials/llm-fundamentals/attention-and-positional-information/#head-sharing) gives each group of 8 query heads one shared key and value head. Beyond 8 GPUs the key and value heads would have to be copied rather than split.

Each layer therefore needs one all-reduce after attention and one after the feed-forward network in the forward pass, and two more in the backward pass for the gradients of the layer inputs. These sit on the **critical path**. The next matrix multiplication cannot start until the sum arrives, so the GPU waits through each one unless a kernel overlaps them. For one 4,096-token sequence, each all-reduce carries the full activation of $4{,}096 \times 8{,}192 \times 2 = 67.1$ MB, and a ring over 8 GPUs sends 117.4 MB per GPU. Over 80 layers that is 320 all-reduces and 37.6 GB per sequence per step. That takes about 84 ms on NVLink and 752 ms on InfiniBand, against 214 ms of arithmetic per GPU at peak speed.

The ratio between communication and computation explains why the tensor-parallel group stays inside one node. Per token and per layer, each GPU's arithmetic shrinks as $1/t$ when $t$ GPUs share the layer, while the bytes each GPU sends approach $4 \times 2 \times 16{,}384 = 131{,}072$ because the ring factor $2(t-1)/t$ approaches 2. Here 16,384 is one token's 8,192-number activation in bf16 and 4 is the number of all-reduces per layer.

| Tensor-parallel size $t$ | Arithmetic per GPU at peak | All-reduces on NVLink | Ratio |
|---|---|---|---|
| 2 | 2.60 µs | 0.15 µs | 6% |
| 4 | 1.30 µs | 0.22 µs | 17% |
| 8 | 0.65 µs | 0.25 µs | 39% |
| 16 | 0.32 µs | 0.27 µs | 84% |

At $t = 8$ the collectives already cost 39% of the arithmetic time. At $t = 16$ the group would span two nodes, so the same bytes would cross InfiniBand at a ninth of the speed. Serving uses the same splits with a different balance of costs, which [Serving Systems](/tutorials/llm-deep-dive/inference-systems-at-scale/) covers.

## Sequence parallelism

Tensor parallelism splits the matrices but leaves some of the layer copied on every GPU. The RMSNorms and the residual additions act on the full 8,192-number stream of every token, and before sequence parallelism every GPU in the group computed and stored them in full. Of the 137,216 numbers per token per layer in the [training memory](#training-memory) section, the four stream-sized tensors around the two norms stay whole on every GPU. They hold 32,768 numbers, while the other 104,448 are divided by 8. Tensor parallelism alone therefore cuts the activations to $2 \times (32{,}768 + 104{,}448/8) = 91{,}648$ bytes per token per layer, a factor of 3 rather than 8.

Those four tensors stay whole because a column-parallel projection needs the complete normalized input of every token. Each GPU of the group therefore runs the same RMSNorm on all 4,096 tokens, adds the same residual and stores the same result, so the 8 GPUs hold 8 identical copies of 32,768 numbers per token per layer. That copy is the redundancy tensor parallelism leaves behind, and it makes up 32,768 of the 45,824 numbers each GPU keeps, about 72%.

**Sequence parallelism** splits those regions along the sequence instead. It also comes from [Korthikanti et al.](https://arxiv.org/abs/2205.05198). Normalization and residual additions treat each token separately, so each of the 8 GPUs can handle 512 of the 4,096 tokens there. The all-reduce after the row-parallel layer becomes a reduce-scatter that sums the partial outputs and leaves each GPU only its 512 tokens. The column-parallel layer that follows starts with an all-gather that collects all 4,096 tokens again. Since an all-reduce is exactly a reduce-scatter and an all-gather, the bytes moved do not change.

Each GPU now alternates between two slices of the same activations. Inside attention and the feed-forward network it holds all 4,096 tokens but only an eighth of the heads or hidden columns. Around the norms and residual additions it holds all 8,192 numbers of the stream but only 512 tokens. Both slices are one eighth of the full tensor, and the collectives at the boundaries convert one slice into the other.

![Tensor and sequence parallel layer](/images/llm-deep-dive/16c-tensor-and-sequence-parallel-layer.png)

Between the collectives, the residual stream stays split by tokens through all 80 blocks. A GPU's 512 tokens are gathered only to enter a projection and return to 512 tokens through the reduce-scatter that adds the partial outputs. The switches sit at the only places where a tensor has to change hands. Attention for a GPU's heads needs every token, so the gather comes before it, and the row-parallel output is a partial sum, so the reduce-scatter comes after. Nothing in between needs the other GPUs. With every tensor in the table now divided by 8, a layer keeps 34,304 bytes per token instead of 274,432, and one 4,096-token sequence needs 11.2 GB over 80 layers instead of 89.9 GB.

| Split of one 4,096-token sequence | Bytes per token per layer | All 80 layers |
|---|---|---|
| No split | 274,432 | 89.9 GB |
| Tensor parallel 8 | 91,648 | 30.0 GB |
| Tensor and sequence parallel 8 | 34,304 | 11.2 GB |

One tensor needs extra care. The all-gather gives each GPU the normalized input of all 4,096 tokens, and the backward pass needs that input again to compute the weight gradient of the projection that follows. Storing it whole would bring back two of the stream-sized copies. Korthikanti et al. store only each GPU's 512-token slice and repeat the all-gather in the backward pass, overlapped with the computation of the input gradient. The switches between slices move exactly the bytes of the four all-reduces they replace, 469.8 MB per GPU per layer for one sequence on 8 GPUs. The two repeated all-gathers add 117.4 MB that runs alongside arithmetic, so the step-time estimates of later sections count only the switches. The full eightfold cut in activation memory costs only extra traffic that mostly hides. That is why tensor and sequence parallelism are almost always turned on together.

## Pipeline parallelism

Tensor parallelism needs NVLink, and one node has only 8 GPUs. **Pipeline parallelism** splits the model across nodes along its depth instead. Each **stage** holds a run of consecutive layers, and the only data crossing between stages is the activation at the boundary going forward and its gradient coming back. For the 70B split into 4 stages of 20 layers, one 4,096-token micro-batch sends 67.1 MB forward per boundary, and with sequence parallelism each of the 8 GPUs in a stage sends only its 8.4 MB share. That is the least traffic of any cut, which is why the pipeline is the axis that crosses the slower InfiniBand links.

The cost is idle time. Stage 2 cannot start until stage 1 has finished a micro-batch, and stage 1 has nothing to do while the last backward passes drain back up. [GPipe](https://arxiv.org/abs/1811.06965) runs all forward passes of $m$ micro-batches and then all backward passes. Each stage is then busy for $m$ slots of each kind and idle for $p - 1$, where $p$ is the number of stages. The idle share of the step is called the **pipeline bubble**, and it is

$$
\text{bubble} = \frac{p-1}{m+p-1}.
$$

The numerator counts the slots a stage waits while the pipeline fills and drains, and the denominator counts all slots. With $p = 4$ and $m = 4$ the bubble is $3/7 = 42.9\%$, with $m = 8$ it is $3/11 = 27.3\%$, and with $m = 16$ it is $3/19 = 15.8\%$. More micro-batches shrink the bubble, but GPipe stores the activations of all $m$ micro-batches at once on stage 1, so a larger $m$ costs memory.

The **1F1B schedule** keeps the bubble and fixes the memory. Its name is short for one forward one backward, and it was introduced with [PipeDream](https://arxiv.org/abs/1806.03377). As soon as the last stage has the loss for a micro-batch it runs that micro-batch's backward pass, and from then on every stage alternates one forward with one backward. A micro-batch's activations are freed as soon as its backward pass has run, so stage 1 holds at most $p$ micro-batches instead of $m$.

## Context parallelism
Sequence parallelism splits only the normalization regions, so attention and the matrix multiplications still see the full sequence on every GPU of the tensor-parallel group. At 4,096 tokens that is affordable, and at 131,072 tokens it is not. One 131,072-token sequence of the 70B needs $34{,}304 \times 131{,}072 \times 80 = 360$ GB of activations even with tensor and sequence parallelism. **Context parallelism** splits the whole layer along the sequence, so each of $c$ GPUs holds the queries, keys, values and activations of $1/c$ of the tokens. With $c = 16$ the 360 GB becomes 22.5 GB per GPU. Long context training as a whole belongs to [Long Context](/tutorials/llm-deep-dive/long-context-and-document-models/), including position scaling and data.

Everything in a layer except attention treats tokens separately, so only attention needs data from other GPUs. A query on GPU 3 must see the keys and values of every earlier token, wherever they live. **Ring attention** passes key and value blocks around a ring of GPUs. It comes from [Liu et al.](https://arxiv.org/abs/2310.01889). At each step every GPU computes attention between its own queries and the block it currently holds, merges the result into a running softmax the way FlashAttention merges tiles, and passes the block on. After $c$ steps every query has seen every key. The transfer hides behind the arithmetic when blocks are large. With $c = 16$, each GPU holds 8,192 tokens, and one block of keys and values for the 70B's 8 key and value heads is $8{,}192 \times 2 \times 1{,}024 \times 2 = 33.6$ MB per layer. Sending it takes 0.67 ms over InfiniBand. One full block of attention arithmetic is $4 \times 8{,}192 \times 8{,}192 \times 8{,}192 = 2.2 \times 10^{12}$ FLOPs, which takes 2.2 ms even at peak speed.

The [causal mask](/tutorials/llm-fundamentals/attention-and-positional-information/#the-causal-mask) creates a load imbalance that the plain split ignores. If GPU 1 holds the first quarter of the sequence and GPU 4 the last, GPU 1's queries see almost no keys and GPU 4's see all of them.

![Context parallel balance](/images/llm-deep-dive/16c-context-parallel-balance.png)

With a contiguous split the four GPUs do 2, 6, 10 and 14 blocks of work, 32 in all. Each ring step waits for the busiest GPU, so the attention takes as long as 14 blocks, and the group does only $32 / (4 \times 14) = 57\%$ of the work it could. The imbalance follows from the mask. Query chunk $j$ meets $j - 1$ full blocks and one half block on the diagonal, so its work grows in a straight line with $j$. The fix cuts the sequence into $2c$ chunks and gives GPU $i$ chunks $i$ and $2c + 1 - i$, an early chunk paired with a late one. Their work adds to $(i - 0.5) + (2c + 0.5 - i) = 2c$, the same for every GPU, so all four do 8 blocks. The [Llama 3 paper](https://arxiv.org/abs/2407.21783) uses exactly this pairing. It also replaces the ring with a single all-gather of keys and values before attention. That leaves the transfer on the critical path but supports masks such as document masks more easily. Grouped-query attention keeps the cost small, because keys and values are an eighth the size of the queries. [DeepSpeed Ulysses](https://arxiv.org/abs/2309.14509) takes a third route. An all-to-all turns a split by tokens into a split by heads before attention and back afterwards, which caps the split at the number of attention heads.

## Parallel layout
The cuts combine because each one splits a different thing. Tensor and sequence parallelism split each layer, pipeline parallelism splits the stack, context parallelism splits long sequences and data parallelism splits the batch. A **parallel layout** assigns every GPU one position on each axis, and the product of the group sizes equals the GPU count. The order of the axes follows the network. The axis that communicates most often and on the critical path goes on the fastest links, so tensor parallelism sits inside a node on NVLink. The axis that can overlap its traffic with computation goes outermost, across the most network hops.

The 70B on 2,048 H100s works out as follows, with a global batch of 4,194,304 tokens, 1,024 sequences of 4,096.

1. Tensor and sequence parallel size 8, one node per group. Each GPU holds 1/8 of every layer it has, and the [tensor parallelism](#tensor-parallelism) section showed that size 8 keeps the collectives at 39% of arithmetic time on NVLink.
2. Pipeline parallel size 4 across nodes, with 20 layers per stage. One copy of the model now spans $8 \times 4 = 32$ GPUs, each holding $68.98 \times 10^9/32 = 2.16 \times 10^9$ parameters.
3. Data parallel size $2{,}048/32 = 64$ copies, with ZeRO stage 1 sharding the optimizer state across the 64. Each copy processes $1{,}024/64 = 16$ sequences per step as 16 micro-batches of one sequence, so the pipeline bubble is $3/19 = 15.8\%$.
4. Each GPU stores 4.31 GB of bf16 weights, 4.31 GB of gradients and an optimizer shard of $12 \times 2.16 \times 10^9/64 = 0.40$ GB. Activations are 2.81 GB per micro-batch on a 20-layer stage, and stage 1 holds 4 under 1F1B, 11.2 GB. The total is about 20 GB of 80, so this layout needs no recomputation.
5. In each step, each GPU's tensor-parallel collectives move 150 GB over NVLink, the pipeline sends 268 MB over InfiniBand, and the data-parallel gradient sync moves 8.5 GB over InfiniBand.

![Parallel layout 2048 gpus](/images/llm-deep-dive/16c-parallel-layout-2048-gpus.png)

Every GPU belongs to three groups at once. It shares each of its layers with the 7 other GPUs of its node, it passes activations to the next stage of its copy, and it averages gradients with the 63 GPUs in other copies that hold exactly the same slice of the model. The layout gives each group the links its traffic needs. The tensor-parallel collectives move 150 GB per GPU per step and sit on the critical path, so they stay on NVLink, where they take about 0.33 s. The same bytes over InfiniBand would take 3.0 s, longer than the whole step. The pipeline sends only 268 MB, about 5 ms over InfiniBand, so the slowest links carry it at almost no cost. The 8.5 GB gradient sync crosses InfiniBand too, but it happens once per step, takes about 0.17 s, and can overlap the backward pass.

Published runs follow the same logic at larger scale. The Llama 3 paper calls its version **4D parallelism**. It orders tensor, context, pipeline and data parallelism from innermost to outermost, with tensor parallelism inside 8-GPU servers on NVLink. Its data-parallel axis is FSDP that shards the optimizer state and gradients but keeps the gathered weights after the forward pass to avoid a second all-gather in the backward pass. Its reported configurations for the 405B model were as follows.

| GPUs | Tensor | Context | Pipeline | Data | Sequence length | Tokens per batch | BF16 MFU |
|---|---|---|---|---|---|---|---|
| 8,192 | 8 | 1 | 16 | 64 | 8,192 | 16M | 43% |
| 16,384 | 8 | 1 | 16 | 128 | 8,192 | 16M | 41% |
| 16,384 | 8 | 16 | 16 | 8 | 131,072 | 16M | 38% |

The paper attributes the drop from 43% to 41% to the smaller batch per data-parallel group when the GPU count doubled at a fixed 16M tokens. The long-context stage traded data-parallel copies for context parallel size 16, so the 131,072-token sequences fit while the tokens per batch stayed at 16M.

[DeepSeek-V3](https://arxiv.org/abs/2412.19437) shows a different set of choices for a mixture of experts model on 2,048 H800 GPUs. It uses 16-way pipeline parallelism, 64-way expert parallelism spanning 8 nodes and ZeRO-1 data parallelism, and no tensor parallelism at all, which the report says its memory savings made possible. Expert parallelism places different experts on different GPUs and moves tokens to them with all-to-all. It is the subject of [Mixture of Experts](/tutorials/llm-deep-dive/mixture-of-experts-at-scale/). The report states that this cross-node traffic made communication about as long as computation. Its **DualPipe** schedule feeds micro-batches from both ends of the pipeline at once and pairs a forward chunk with a backward chunk on the same GPU, so the all-to-all and pipeline transfers of one run during the arithmetic of the other. It also splits backward passes into input and weight parts in the zero-bubble style. Custom all-to-all kernels send each token over InfiniBand at most to 4 nodes and forward it inside each node over NVLink, using 20 of the GPU's streaming multiprocessors for communication.

## Model FLOPs utilization
A layout is judged by how much of the hardware's arithmetic ends up as training. [Model FLOPs utilization](/tutorials/llm-fundamentals/pretraining-at-scale/#the-compute-budget), or MFU, counts only the $6N$ FLOPs per token the model needs. [PaLM](https://arxiv.org/abs/2204.02311) introduced it for this purpose:

$$
\text{MFU} = \frac{6N \times \text{tokens per second}}{G \times F}.
$$

Here $N$ is the parameter count, $G$ the number of GPUs and $F$ the peak FLOPs per second of one GPU, 989 TFLOP/s for bf16 on an H100. **Hardware FLOPs utilization** also counts recomputed forward passes and so reads higher for the same run, which makes the convention part of any reported figure. For the 70B layout, each step processes 4,194,304 tokens. That is $6 \times 68.98 \times 10^9 \times 4{,}194{,}304 = 1.74 \times 10^{18}$ FLOPs, or 0.857 s per GPU at peak. A step that takes 2.14 s is therefore 40% MFU, and 476,837 steps of 2.14 s make the 11.8 days from the opening.

The table splits that 2.14 s into its parts. It is a teaching estimate built from the numbers in earlier sections, assuming matrix kernels reach 70% of peak and that no communication is overlapped with arithmetic. The tensor-parallel collectives and the 8.5 GB data-parallel sync both appear in full, the sync taking $8.5 / 50 = 0.17$ s on InfiniBand.

| Part of one step | Time | Share |
|---|---|---|
| Matrix arithmetic at 70% of peak | 1.224 s | 57% |
| Attention scores, not counted in $6N$ | 0.048 s | 2% |
| Tensor-parallel collectives on NVLink | 0.334 s | 16% |
| Pipeline bubble, 3/16 of the busy time | 0.301 s | 14% |
| Data-parallel gradient sync, exposed | 0.170 s | 8% |
| Optimizer step, launch gaps, stragglers | 0.065 s | 3% |
| Total | 2.142 s | 100% |

Read this way, the gap between 40% and 100% has named owners, and each has a known remedy. **Communication overlap** runs a transfer at the same time as independent arithmetic. DistributedDataParallel overlaps gradient buckets with backward, FSDP prefetches the next layer's weights, and Megatron-style kernels can overlap the all-gather of sequence parallelism with the first matrix multiplication of the next sublayer. Each of these turns exposed time into hidden time without moving fewer bytes. DualPipe goes further and builds the whole schedule around overlap.

Topology decides how much of the rest can be removed. Llama 3's cluster joined 3,072 GPUs per pod at full bisection bandwidth, so any half of the pod can talk to the other half at full speed. Pods were connected to each other with an oversubscription of 1 to 7, about a seventh of that bandwidth. The paper describes the scheduler and the parallel layout as aware of this so that traffic mostly stays inside a pod. An **NVLink domain** is the set of GPUs joined by NVLink, and its size sets how large the tensor-parallel group can be. NVIDIA's [GB200 NVL72](https://www.nvidia.com/en-us/data-center/gb200-nvl72/) joins 72 GPUs in one NVLink domain at 1.8 TB/s of bidirectional bandwidth per GPU, twice an H100's 900 GB/s. On such systems, tensor, context or expert groups larger than 8 can stay on NVLink, which shifts the layout arithmetic of the [parallel layout](#parallel-layout) section.

## Parallelism diagnosis
A slow or failing run usually shows one symptom first, and each symptom points at one axis. The table maps what is seen to what to measure and the usual fix.

Each row reads from left to right. The symptom is what shows up first, in an error message, a falling MFU or a step time that drifts. The measurement is the one number that separates that row's cause from others that look the same from outside, and the fix points back to the section that develops it. The first two rows are about memory and appear at or near the first step. The next five are about time. Their measurements correspond to lines of the step-time table in the [model FLOPs utilization](#model-flops-utilization) section, since a profiler trace splits a step into arithmetic, collectives, pipeline bubble and exposed sync in the same way. A slow step then comes down to finding which line grew. The last row concerns a single GPU, and only per-rank timings reveal it, because every rank waits at the same collective and so every rank reports the same slow step time.

| Symptom | What to measure | Usual cause | Usual fix |
|---|---|---|---|
| Out of memory before the first step | Training state per GPU against 80 GB | Weights, gradients and optimizer state replicated | Raise the ZeRO stage, or add tensor or pipeline parallelism |
| Out of memory that grows with sequence length | Activation bytes per token per layer | Activations of long sequences | Sequence parallelism, then context parallelism, then recomputation ([Numerics and Stability](/tutorials/llm-deep-dive/numerics-and-training-stability/)) |
| MFU falls as data-parallel GPUs are added | Exposed all-reduce time in a profiler trace | Gradient sync not hidden behind backward | Bucketing, larger micro-batches, hybrid sharding |
| GPUs idle at the start and end of every step | Idle time per pipeline stage | Pipeline bubble from too few micro-batches | More micro-batches, interleaved stages, zero-bubble schedules |
| One pipeline stage always finishes last | Time per stage | Embedding, output head or loss on one stage | Move layers off the first and last stages |
| Step time jumps when the tensor-parallel group grows past 8 | Collective time per layer | Tensor parallelism crossing InfiniBand | Keep tensor parallelism within an NVLink domain |
| Long-context steps slow and uneven across GPUs | Attention time per context-parallel rank | Causal imbalance with a contiguous split | Pair early and late chunks on each GPU |
| Whole job runs at the speed of one GPU | Per-rank step times | Straggler from a bad link or host | Benchmark collectives across nodes, replace the node |

The 70B layout of the [parallel layout](#parallel-layout) section gives a worked case. Suppose the layout changes from tensor parallel 8 and pipeline parallel 4 to tensor parallel 16 and pipeline parallel 2, in order to shrink the bubble. The step time then rises from 2.14 s to about 8.4 s. The symptom matches the sixth row, so the first measurement is the collective time per layer in a profiler trace. It shows that each tensor-parallel group now spans two nodes, so its all-reduces run at InfiniBand speed. Each GPU holds 40 layers and runs 16 micro-batches. Each of its 4 all-reduces per layer sends $2 \times 15/16 \times 67.1$ MB, which totals 322 GB per step. At 50 GB/s that is 6.4 s, against 0.334 s on NVLink before. The bubble fraction did fall from 3/16 to 1/16, but it is now a fraction of a much longer busy time, so the bubble itself grew from 0.30 s to 0.48 s. The fix is to return the tensor-parallel group to one node. If the bubble still needs to shrink, the interleaved schedule of the [pipeline parallelism](#pipeline-parallelism) section with two chunks per GPU halves it to about 0.15 s. The cost is paid in pipeline sends, which are the cheapest bytes in the layout.

The order of choices mirrors the sections. Data parallelism comes first because it costs the least, and ZeRO or FSDP is added when the training state no longer fits. Tensor and sequence parallelism follow once a layer's computation needs more than one GPU, and they are held inside the NVLink domain. Pipeline parallelism then carries the model across nodes, and context parallelism comes in only when sequences grow long. Expert parallelism enters for mixture of experts models. Each axis is sized as small as it can be, since every added axis brings its own collectives and its own share of the step time budget.
