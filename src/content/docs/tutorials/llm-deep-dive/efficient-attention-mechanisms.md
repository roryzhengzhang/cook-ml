Attention is called quadratic, yet at the length the [reference 7B model](/tutorials/llm-deep-dive/#scale-reference-models) was trained on, the label barely shows. At 4,096 tokens, comparing each token with the tokens before it costs about 8% of a layer's arithmetic, and the feed-forward network in the same layer costs eight times as much. At 32,768 tokens the two are about equal. At 131,072 tokens attention costs four times the feed-forward network.

Writing text runs into a different wall that the arithmetic never shows. Each new token reads every cached key and value from memory, and past about 25,700 tokens those reads outweigh reading all 13.48 GB of the model's weights. So "efficient attention" names two separate jobs. Training and prompt processing pay for a table of scores that grows with the square of the length. Generation pays for a cache that grows with the length and is read in full at every step.

![Attention cost against context](/images/llm-deep-dive/16a-attention-cost-against-context.png)

The two curves cross at similar lengths, but they measure different resources, arithmetic on the left and memory traffic on the right. A method that fixes one often leaves the other untouched. FlashAttention removes the score table's memory traffic and does nothing for the cache, and grouped-query attention shrinks the cache while every score is still computed.

The chapter first prices both costs, because the price decides which methods can help at all. Decode turns out to be limited by the bytes it reads and almost never by arithmetic, so the methods for it either shrink what each cached token stores or limit how many tokens are cached. The cache comes next, since it decides how many users fit on a GPU. Shared key and value heads lead that group, because almost every current model uses them, and they set the baseline that latent attention then beats by compressing each token's keys and values into one short vector. Sparse attention cuts the number of pairs instead. Fixed patterns show the saving and its price in reach, local and global layers show how current models buy that reach back with a few full layers, and learned selection lets the content decide which pairs to keep. FlashAttention and the online softmax inside it keep every pair and change only where the numbers live. That fixes the training memory taken by the stored score table and leaves the quadratic arithmetic as it was. The last group replaces the growing cache with a fixed-size state, through linear attention with gates and the delta rule, state space models such as Mamba, and hybrid stacks. A fixed state cannot keep every token exactly, and that limit is why the hybrids now in production keep some attention layers. A closing table maps each bottleneck to the methods that address it and to what current models actually choose.

## Attention cost
Each layer of the 7B does two kinds of arithmetic per token, and only one of them depends on how much text came before. The weight work is fixed. The four attention projections cost $2 \times 4d^2 = 134$ million FLOPs per token in the forward pass, and the SwiGLU [feed-forward network](/tutorials/llm-fundamentals/the-transformer-block-and-model-anatomy/#the-feed-forward-network) costs $2 \times 3\,d\,d_{\text{ff}} = 271$ million, where $d = 4{,}096$ is the width and $d_{\text{ff}} = 11{,}008$ is the feed-forward width. The other kind is attention proper. The token's query is compared with every earlier key, and the weights average every earlier value.

A four-token example shows how to average that second cost over a sequence. Under the causal mask, token 1 reads 1 key, token 2 reads 2, token 3 reads 3 and token 4 reads 4, so the sequence holds 10 pairs and a token reads $10/4 = 2.5 = (n+1)/2$ keys on average. A token at position $t$ costs $2td$ FLOPs for its scores and another $2td$ for the weighted sum of values. Both counts are summed over all heads, since the heads split the width $d$. Averaging $4td$ over a sequence of length $n$ gives

$$
\text{attention FLOPs per token per layer} \approx 4d \cdot \frac{n+1}{2} \approx 2nd.
$$

The weight work per token never changes, while the attention work per token grows with how much text precedes the token. Setting $2nd$ equal to the feed-forward cost $6\,d\,d_{\text{ff}}$ gives $n = 3\,d_{\text{ff}} = 33{,}024$ tokens. Against all the weight work in the layer, projections included, the crossover is 49,408 tokens, which matches the deep dive in [FLOPs per token](/tutorials/llm-fundamentals/the-transformer-block-and-model-anatomy/#flops-per-token).

| Context $n$ | Attention, GFLOPs per token per layer | Feed-forward | Attention share of the layer |
|---|---|---|---|
| 4,096 | 0.034 | 0.271 | 7.7% |
| 32,768 | 0.268 | 0.271 | 39.9% |
| 131,072 | 1.074 | 0.271 | 72.6% |

These counts assume a kernel that skips the masked half of the table. A kernel that computes the full $n \times n$ table and then masks it does $4nd$, twice as much. Training multiplies every row by about three for the backward pass, so the shares stay roughly the same.

The table of scores also has a memory cost, and it grows faster than the arithmetic share suggests. One layer's scores for 32 heads in bf16 take $32 \times n^2 \times 2$ bytes. For the reference 7B that is 1 GiB at 4,096 tokens and 64 GiB at 32,768. The [quadratic cost section](/tutorials/llm-fundamentals/attention-and-positional-information/#quadratic-cost-and-the-key-value-cache) of Fundamentals counted the same table for the story model, where it is only 3 MiB per layer at 512 tokens. A plain training implementation keeps each layer's softmax probabilities for the backward pass, so a single 4,096-token sequence holds 32 GiB of them across 32 layers, more than twice the weights. That stored table is what first limits training length, not the arithmetic.

## Prefill and decode bottlenecks
Prefill and decode run the same attention formula on very different shapes, so they hit different limits. The useful measure is [arithmetic intensity](/tutorials/llm-fundamentals/inference-and-decoding/#memory-bandwidth-bound-decoding), the FLOPs done per byte moved from memory. An H100 turns compute bound near 295 FLOPs per byte. That number is the ratio of its two speeds, 989 TFLOP/s of bf16 arithmetic over 3.35 TB/s of memory bandwidth. A kernel that does fewer than 295 FLOPs for each byte it reads leaves the arithmetic units waiting on memory, and one that does more keeps memory waiting on the arithmetic units. The point where the two balance is called the ridge.

In [prefill](/tutorials/llm-fundamentals/inference-and-decoding/#prefill-and-decode-phases) or training, all prompt queries can be processed together. The causal mask allows each query to see its own key and the earlier keys. For one head at 4,096 tokens, the allowed dot products take about 2.15 billion FLOPs. Reading the query and key arrays once in bf16 would move 2 MiB, which gives about 1,024 FLOPs per byte in this simplified calculation. Real kernels also move other data. The [trainable sparse attention](#trainable-sparse-attention) section shows how storing the full score table can make a naive implementation memory bound.

In decode, one new query per sequence meets a cache that is already sitting in memory. For each cached token, one layer reads a key and a value for 32 heads, which take $2 \times 32 \times 128 \times 2 = 16{,}384$ bytes. It does $4d = 16{,}384$ FLOPs on them. That is 1 FLOP per byte, about 300 times below the ridge. Batching does not raise it, because unlike the weights, every sequence has its own cache. Each of the 6.74 billion weights is read once per step as 2 bytes and used for 2 FLOPs by every sequence in the batch, so the weights sit at 1 FLOP per byte at batch 1 and at 16 FLOPs per byte at batch 16. A cached key belongs to one sequence and meets only that sequence's query, so its 1 FLOP per byte stays the same at any batch size.

![Prefill and decode attention shapes](/images/llm-deep-dive/16a-prefill-and-decode-attention-shapes.png)

So decode attention is priced in bytes. At batch 1 a step reads 13.48 GB of weights plus the cache, and dividing the total by 3.35 TB/s gives the step time. At 512 KiB per token, 4,096 tokens of cache add 2.15 GB, so a step reads 15.63 GB. That takes 4.7 ms at 4,096 tokens of context, 9.2 ms at 32,768 and 24.5 ms at 131,072, and at that last length the 64 GiB cache plus the weights no longer fit in one H100's 80 GB. Dividing the 13.48 GB of weights by the 524,288 bytes each token adds gives the 25,700 tokens of the opening, the length where the cache becomes the larger read. Batching brings that point much closer. At batch 16 and only 4,096 tokens, the 16 caches hold 34.4 GB against the same 13.48 GB of weights, so 72% of each step's bytes are cache. A server that batches to make good use of the weights therefore finds its step time set mostly by the cache, even at modest lengths. The methods for decode therefore come in two families. One cuts the bytes stored per cached token, which is what shared heads and latent attention do. The other caps how many tokens are cached at all, which is what sliding windows and recurrent states do.

## Grouped-query attention
[Grouped-query attention](/tutorials/llm-fundamentals/attention-and-positional-information/#head-sharing) lets several query heads read one shared key and value head. Sharing keys does not force sharing weights. With shared keys $k_1 = (1,0)$ and $k_2 = (0,1)$, a head with query $(2,0)$ scores them 2 and 0 and puts 0.881 of its weight on the first, while a head with query $(0,2)$ scores 0 and 2 and puts 0.881 on the second. The heads still look at different tokens. They just look through one shared set of keys.

The cache shrinks in proportion to the key value heads. For the 7B shape it is 512 KiB per token with 32 key value heads, 128 KiB with 8, 64 KiB with 4 and 16 KiB with 1, which is multi-query attention. The reference 70B has 64 query heads and would need 2.5 MiB per token as plain multi-head attention. Its 8 key value heads bring that to 320 KiB. Sharing also raises decode intensity. A key value head serving a group of $g$ query heads is read once and used $g$ times, so the 1 FLOP per byte of the [prefill and decode bottlenecks](#prefill-and-decode-bottlenecks) section becomes $g$ FLOPs per byte, 4 for the 7B with 8 groups and 8 for the 70B. The parameters shrink too. With 8 key value heads the key and value projections become $4{,}096 \times 1{,}024$, so attention drops from 67.1 million to 41.9 million parameters per layer, 805 million fewer across 32 layers.

![Grouped query head sharing](/images/llm-deep-dive/16a-grouped-query-head-sharing.png)

The cache follows the number of key value heads and ignores the number of query heads. In the 7B shape one token costs 16 KiB per layer with 32 key value heads, 4 KiB with 8 and 512 bytes with 1, while all 32 query heads keep their own projections in every case. Grouped-query attention is therefore a dial between multi-head attention, where each key value head serves one query head, and multi-query attention, where one serves them all. The savings along the dial shrink quickly. Going from 32 to 8 key value heads removes 384 KiB per token over 32 layers, and going on from 8 to 1 removes only another 112 KiB. The quality cost runs the other way. Each query head in a group still weights tokens its own way, as the two-key example showed, but the whole group matches against one shared set of keys. With 8 groups the model keeps eight different ways of describing tokens for matching, and with one group it keeps a single way. The first step buys most of the saving, and the last step buys little while giving up the most.

The [GQA paper](https://arxiv.org/abs/2305.13245) found that 8 key value heads come close to full multi-head quality at close to multi-query speed, while a single shared head loses some quality and trains less stably. It also showed an existing model does not need retraining from scratch. **Uptraining** builds each group's key and value projections as the mean of the heads it replaces, then continues pretraining for about 5% of the original compute. Under the mean, two heads with weights 0.4 and 0.2 in one position become 0.3. For the 7B trained on 2 trillion tokens, 5% is 100 billion tokens, about $4 \times 10^{21}$ FLOPs (teaching estimate).

Grouped-query attention is now the default in open models. [Llama 3](https://arxiv.org/abs/2407.21783) 8B uses 8 key value heads. Every dense [Qwen3](https://arxiv.org/abs/2505.09388) model uses 8 key value heads and its mixture of experts models use 4. [gpt-oss](https://arxiv.org/abs/2508.10925) pairs 64 query heads with 8 key value heads.

Three small additions to the attention layer have become common at the same time, all aimed at keeping attention scores and outputs in a healthy range. **QK-norm** applies RMSNorm to each head's queries and keys before the dot product, which caps how large a score can grow. Qwen3 introduced it in place of the bias on the query, key and value projections, and [Gemma 3](https://arxiv.org/abs/2503.19786) uses it instead of Gemma 2's soft-capping of scores. **Gated attention** multiplies each head's output by a sigmoid gate computed from the token. [Qiu and colleagues](https://arxiv.org/abs/2505.06708) found that this improves stability, tolerates larger learning rates and mitigates the attention sink. [Qwen3-Next](https://huggingface.co/Qwen/Qwen3-Next-80B-A3B-Instruct) uses gated attention layers. An **attention sink** is a position that soaks up weight a head does not need, often the first token. gpt-oss gives each head a learned sink instead, an extra logit in the softmax denominator. With scores 1 and 2 and a sink logit of 2, the weights become 0.155 and 0.422, and the remaining 0.422 goes to nothing at all. [Numerics and Stability](/tutorials/llm-deep-dive/numerics-and-training-stability/) covers why these help training stay stable.

## Multi-head latent attention

Grouped-query attention decides by hand which heads share keys and values. **Multi-head latent attention**, or MLA, learns a compression instead. It was introduced in [DeepSeek-V2](https://arxiv.org/abs/2405.04434). Each token stores one short **latent vector**, and every head rebuilds its own key and value from it when needed. A learned down-projection $W_{DKV}$ maps the token's hidden state $h_t$ of width 4,096 to the latent $c_t$ of width $d_c = 512$, and per-head up-projections rebuild keys and values:

$$
c_t = h_t W_{DKV}, \qquad k^C_{t,i} = c_t\, W_{UK,i}, \qquad v_{t,i} = c_t\, W_{UV,i}.
$$

Here $i$ numbers the head, $k^C_{t,i}$ is head $i$'s content key for token $t$ and $v_{t,i}$ its value, each 128 numbers wide. Only $c_t$ is cached. The heads' keys and values are highly correlated, so 512 learned numbers can carry most of what $2 \times 32 \times 128 = 8{,}192$ separate numbers carried.

[Rotary position embedding](/tutorials/llm-fundamentals/attention-and-positional-information/#rotary-position-embedding) breaks the simple version. RoPE rotates each key by an angle that depends on its position. That rotation would sit between the latent and the query, so the up-projection could no longer be merged into the query (the deep dive below shows why the merge matters). MLA therefore keeps position out of the latent and adds a **decoupled RoPE key** $k^R_t$, 64 numbers computed from $h_t$, rotated by position, and shared by all heads. Each head's query gets a matching 64-number part $q^R$. The score is the sum of the two matches, $q^C \cdot k^C + q^R \cdot k^R$. That sum is scaled by $1/\sqrt{128 + 64}$.

![Multi head latent attention](/images/llm-deep-dive/16a-multi-head-latent-attention.png)

The cache holds the input that keys and values are made from, not the keys and values themselves. Each head's content key and value is a fixed linear function of the latent, so storing the latent keeps everything the heads need. The saving is paid in arithmetic, because something has to turn the latent back into 32 keys and 32 values, and the deep dive below shows how that work moves to the query side. Position cannot pass through the shared latent, so it travels separately in the 64-number RoPE key. All 32 heads read that one key, so for position alone MLA works like multi-query attention, while each head still gets its own content key from the latent.

The cache per token per layer is the latent plus the RoPE key, $512 + 64 = 576$ numbers. DeepSeek-V2 reports a cache 93.3% smaller than its earlier 67B dense model and 5.76 times the maximum generation throughput. [DeepSeek-V3](https://arxiv.org/abs/2412.19437) and [Kimi K2](https://huggingface.co/moonshotai/Kimi-K2-Instruct) keep the same 512 and 64 widths over 61 layers, although Kimi K2 has 64 query heads to DeepSeek-V3's 128. The cache is identical for both, because it does not depend on the head count at all. MLA has costs. Rebuilding or absorbing the up-projections adds arithmetic per decode step, it needs dedicated kernels, and turning an existing multi-head model into an MLA model takes more than the mean-pooling that grouped-query uptraining uses.

Rebuilding 32 keys and 32 values from every cached latent at every step would undo much of the saving, and it is not needed. For head $i$ the content score against an earlier token $s$ is $q^C_i \cdot (c_s W_{UK,i})$, and matrix products can be regrouped:

$$
q^C_i \cdot \big(c_s W_{UK,i}\big) = \big(q^C_i W_{UK,i}^{\top}\big) \cdot c_s.
$$

So the query is mapped once into the 512-number latent space and compared with the cached latents directly. With single numbers, a query of 2, an up-projection of 3 and a latent of 0.5 give $(2 \times 3) \times 0.5 = 3$ either way. The value side works the same way, with $W_{UV,i}$ folded into the output projection. This **weight absorption** is why the RoPE key has to stay separate. A position-dependent rotation between $q$ and $c_s$ would change the merged matrix for every pair of positions.

After absorption, decode attention behaves like multi-query attention with one shared 576-number key and one shared 512-number value per token. Each cached token costs 1,152 bytes per layer to read, and each head spends $2 \times 576 + 2 \times 512 = 2{,}176$ FLOPs on it. With 32 heads that is about 60 FLOPs per byte, and with DeepSeek-V3's 128 heads about 242, close to the H100's ridge of 295. MLA thus shrinks the cache and also turns decode attention from a pure memory read into work that keeps the arithmetic units busy.

## Fixed sparse patterns

A token near the end of a long document might only need to read a few nearby tokens. **Sparse attention** computes scores for selected query and key pairs and treats the other pairs as masked. If each token reads a fixed number of keys, the work grows in proportion to the length instead of its square. On 16 tokens full causal attention computes $16 \times 17 / 2 = 136$ pairs. Each pattern below keeps only a band of them, so a token added at the end costs a fixed number of new pairs rather than one pair per earlier token.

![Sparse attention patterns](/images/llm-deep-dive/16a-sparse-attention-patterns.png)

**Sliding window attention** lets each token read itself and the $w - 1$ tokens before it, 58 pairs here with $w = 4$. **Dilated attention** reads the same number of tokens spaced further apart, so it covers a wider span with 52 pairs. Here it reads every second token. A **global token** is a position that every token reads, and that in an encoder may read every token in return. Adding token 1 as a global token to the window costs 70 pairs. [Longformer](https://arxiv.org/abs/2004.05150) combines all three, and [BigBird](https://arxiv.org/abs/2007.14062) adds random links on top. **Block-sparse attention** decides in blocks rather than single pairs. Here each block of 4 reads itself and the block before, for 88 pairs. The [Sparse Transformer](https://arxiv.org/abs/1904.10509) used strided block patterns of this kind.

At real scale the savings grow with length. A window of 4,096 on a 32,768-token sequence computes 126 million pairs per head per layer instead of 537 million, 4.3 times fewer. At 131,072 tokens it is 16 times fewer. The saving only appears if the kernel skips whole tiles of the score table. A dense kernel with a sparse mask still computes every masked pair. That is why kernels favor blocks that match the GPU's tile size. It is also why a dilated pattern is harder to make fast, since it scatters its reads.

A window also caps the cache, which no other fixed pattern does on its own. A layer that only ever reads the last 4,096 tokens needs to keep only those, so Mistral 7B stores its cache in a **rolling buffer cache** that overwrites the oldest entry. For the 7B shape with plain attention that caps the cache at 2 GiB per sequence however long the text runs. The price is reach. A global token at the start of a causal model cannot summarize text that has not been written yet. Two tokens outside each other's window can only exchange information through other tokens over several layers, which the [local and global layers](#local-and-global-layers) section traces.

Some inputs are grids rather than sequences, such as an image patch grid or a table of quarters by metrics. **Axial attention** attends along one axis at a time. It comes from the [Axial Transformer](https://arxiv.org/abs/1912.12180). Each cell first attends within its row, then within its column. On a 3 by 4 table, the row pass computes $3 \times 4^2 = 48$ pairs and the column pass $4 \times 3^2 = 36$, so 84 pairs instead of $12^2 = 144$. On a 64 by 64 grid it is 524,288 pairs instead of 16,777,216, 32 times fewer. Any cell can still reach any other in two passes. The path runs through the cell where the source's row meets the destination's column. So a fact at row 1, column 1 reaches row 3, column 4 by way of row 1, column 4. AlphaFold 2 uses row-wise and column-wise attention of this kind over its grid of aligned protein sequences. Language models rarely use it, because text has one natural axis and folding it into a grid adds an arbitrary second one. In a causal model, each pass must also be masked so that a path through an intermediate cell cannot carry later content back to an earlier one.

</details>

## Local and global layers

Information can travel further than a window, because each layer reads the outputs of the layer below. The **receptive field** of a token is the set of input positions that can influence its output after a given number of layers. With a window, it grows by $w - 1$ positions per layer. Current models shape it by mixing two kinds of layer. The **local layers** use a window, and the **global layers** use full causal attention.

The growth comes from stacking. In the first layer a token's output mixes only the $w$ tokens in its window. In the second layer it reads the outputs of the $w - 1$ tokens before it, and the earliest of those outputs already carries information from up to $w - 1$ positions further back. Each local layer therefore pushes the reach back by one more window, so $L$ local layers reach back $L(w - 1)$ positions, a reach that grows in a straight line with depth. A global layer breaks that line. It reads every earlier position directly, so whatever the local layers below it have gathered reaches every later token in one step, and the layers above it start from outputs that already draw on the whole context.

The two kinds of layer cost different amounts. Once the text is longer than the window, every token in a local layer reads a full window of $w$ keys, so the layer does about $4wd$ attention FLOPs per token and keeps only the last $w$ tokens in its cache. A global layer pays the $2nd$ of the [attention cost](#attention-cost) section and keeps all $n$ tokens. With $w = 1{,}024$ at 32,768 tokens, a local layer does one sixteenth of a global layer's attention arithmetic. A stack with one global layer in every $r + 1$ layers therefore stores $r$ windows plus one full context per group. At long context its cache and attention arithmetic approach $1/(r + 1)$ of an all-global stack. The design question is how few global layers still give enough long-range recall, and current models answer it differently.

The reach on paper overstates the reach that works, because each hop mixes the signal with everything else in the window again. [Mistral 7B](https://arxiv.org/abs/2310.06825) uses a window of 4,096 in every layer and quotes a theoretical span of about 131,000 tokens. Later models interleave instead. [Gemma 2](https://arxiv.org/abs/2408.00118) alternates local layers with a 4,096-token window and global layers spanning 8,192 tokens. Gemma 3 moves to five local layers per global layer and shrinks the window to 1,024 tokens. Its report puts the memory overhead from the cache at 32,768 tokens at 60% when every layer is global, and under 15% already with one global layer per three local ones and a 1,024-token window. For the 5 to 1 mix, per group of six layers the cache holds $5 \times 1{,}024 + 32{,}768$ token entries instead of $6 \times 32{,}768$, about 19% as many (teaching estimate). gpt-oss alternates layers with a band of only 128 tokens and fully dense layers, and adds the learned sinks of the [grouped-query attention](#grouped-query-attention) section.

[StreamingLLM](https://arxiv.org/abs/2309.17453) observed this as a sharp quality loss once the first tokens are evicted. A learned sink gives each head a permanent place to send that weight, whatever the window holds.

## Trainable sparse attention

A fixed pattern decides before training which pairs exist. **Trainable sparse attention** lets each query choose which earlier tokens to read. The selection step is itself learned, so the sparsity follows the content rather than the distance.

**Native Sparse Attention**, or NSA, runs three branches for every query. It comes from [DeepSeek researchers](https://arxiv.org/abs/2502.11089). One attends to compressed blocks, each a learned summary of a run of tokens. One attends to the few blocks that the compressed scores rate highest, at full detail. One is a sliding window over the most recent tokens. A small learned gate per branch weighs the three outputs. Each gate is computed from the token with a sigmoid. The branches split the reading into a coarse pass and a fine one. The compressed branch gives every query a cheap view of the whole past. Its scores decide which blocks the selected branch reads in full, so the expensive detail goes only where the coarse view found something relevant. Selection works on contiguous blocks of 64 tokens instead of single tokens because a GPU reads a contiguous block far faster than scattered positions and can feed it straight to the tensor cores. The [fixed sparse patterns](#fixed-sparse-patterns) section gave the same reason for block-sparse patterns. The paper's settings make the saving concrete. Compression blocks of 32 tokens are taken every 16 tokens. The selection picks 16 blocks of 64 tokens, always including the first block and the two most recent. The window covers 512 tokens. The last query of a 65,536-token sequence then reads $4{,}096 + 1{,}024 + 512 = 5{,}632$ entries instead of 65,536. The paper reports that NSA matches or beats full attention in quality, turns that ratio of reads into an expected decode speedup of 11.6 times, and measures speedups of up to 9.0 times in the forward pass and 6.0 times in the backward pass at that length.

**DeepSeek Sparse Attention**, or DSA, selects individual tokens. It was introduced in [DeepSeek-V3.2](https://arxiv.org/abs/2512.02556). A **lightning indexer** scores every earlier token for each query. It is a tiny attention-like scorer with few heads, a ReLU instead of a softmax and FP8 arithmetic. The main attention then reads only the top $k = 2{,}048$ tokens. In a toy version with 8 earlier tokens, indexer scores 0.1, 2.0, 0.3, 0.0, 1.5, 0.2, 0.0, 0.4 and $k = 2$, the query attends only to tokens 2 and 5 and its softmax runs over those two. The indexer is still quadratic, but its cost per pair is far below the main attention's, while the main attention drops from $O(n^2)$ to $O(nk)$. At 131,072 tokens a query reads 2,048 tokens instead of 65,536 on average, 32 times fewer pairs.

DSA is built on MLA in its shared-latent form, so each selected token costs one 1,152-byte latent entry per layer. At decode the selected entries take $2{,}048 \times 1{,}152$ bytes per layer. That is 2.25 MiB, against 144 MiB for all 131,072 latents. The indexer's own small keys come on top. The cache itself still holds every token, because a later query may select any of them, so DSA cuts reads and arithmetic rather than storage. DeepSeek trained it from DeepSeek-V3.1-Terminus rather than from scratch. A 1,000-step warm-up trained only the indexer, with dense attention kept and a loss pulling the indexer's scores toward the dense attention distribution. Then 15,000 steps over 943.7 billion tokens trained the whole model with selection switched on.

## FlashAttention
A GPU has two kinds of memory, and the naive attention kernel uses the wrong one. **High-bandwidth memory**, or HBM, is large and comparatively slow. **SRAM** is the small on-chip memory beside the arithmetic units. The [FlashAttention paper](https://arxiv.org/abs/2205.14135) describes an A100 with 40 to 80 GB of HBM at 1.5 to 2.0 TB/s, against 192 KB of SRAM in each of 108 multiprocessors at an estimated 19 TB/s.

A naive kernel writes the score table to HBM, reads it back for the softmax, writes the probabilities, and reads them again for the weighted sum. For one layer of the 7B at 4,096 tokens that moves $4 \times 1$ GiB, which takes 1.28 ms at the H100's 3.35 TB/s. The arithmetic on the full table is $4n^2d = 2.75 \times 10^{11}$ FLOPs, which takes 0.28 ms at 989 TFLOP/s. So naive attention spends more than four times as long moving the table as computing it, even though the [prefill and decode bottlenecks](#prefill-and-decode-bottlenecks) section showed the arithmetic itself is dense enough to be compute bound.

**FlashAttention** is an **IO-aware** algorithm, one designed around how many bytes cross between memory levels rather than how many FLOPs it does. Through **tiling**, it loads a block of queries into SRAM, streams blocks of keys and values past it, computes each tile of scores, folds it into a running result and discards it. **Kernel fusion** puts the scores, the softmax and the weighted sum in one GPU program, so the score table never reaches HBM. In a 4 by 4 example with 2 by 2 tiles there are four tiles. Under the causal mask the upper-right one holds only future keys and is skipped, the two diagonal ones are masked inside SRAM, and one is computed in full.

![Flashattention tiling](/images/llm-deep-dive/16a-flashattention-tiling.png)

The result is exact attention, not an approximation. The paper's measurement on GPT-2 medium shows the trade, with 1,024 tokens, 16 heads of width 64 and a batch of 64 on an A100. FlashAttention did slightly more arithmetic, 75.2 GFLOPs against 66.6. The extra comes from the backward pass, which recomputes scores instead of storing them. But it moved 4.4 GB to and from HBM instead of 40.3 GB and ran in 7.3 ms instead of 41.7. Memory changes even more. Instead of the probability table, the backward pass needs one 32-bit statistic per query row, the **log-sum-exp** of the row's scores. These take 512 KiB per layer at 4,096 tokens instead of 1 GiB. The arithmetic stays quadratic, so FlashAttention fixes the memory side of the training bottleneck and leaves the FLOP curve of the [attention cost](#attention-cost) section where it was.

[FlashAttention-2](https://arxiv.org/abs/2307.08691) kept the algorithm and reorganized the work. On GPUs, the arithmetic outside matrix multiplication runs on much slower units than the tensor cores. That arithmetic includes exponentials, rescaling and division. The second version cuts it by deferring the division to the very end of each row. It also splits work across the sequence as well as across batch and heads, and divides each tile among a thread block's warps so they do not have to exchange partial results. Together these roughly doubled speed over the first version.

[FlashAttention-3](https://arxiv.org/abs/2407.08608) targets the H100's Hopper features. A dedicated copy engine moves tiles while the tensor cores compute, and specialized warps take the two roles, so data movement overlaps arithmetic. The softmax of one tile is interleaved with the matrix multiply of the next, so the slow exponentials hide behind tensor-core work. For FP8 it adds block quantization and incoherent processing. Incoherent processing is a random rotation that spreads outliers before rounding. With both, it reports 2.6 times lower error than a baseline FP8 attention. The paper reports 1.5 to 2.0 times speedups on H100. It reaches close to 1.2 PFLOP/s in FP8 and up to 740 TFLOP/s in FP16, which is 75% of peak.

## Online softmax

Tiling raises one problem. Softmax divides each exponential by a sum over the whole row. For numerical safety it also subtracts the row's maximum first. A tile sees only part of the row. **Online softmax** keeps a small running state per query row and corrects it whenever a later tile changes the maximum. It comes from [Milakov and Gimelshein](https://arxiv.org/abs/1805.02867). The state is the largest score so far $m$, the sum of exponentials measured from it $\ell$, and the weighted sum of values measured from it $o$. For a new tile with scores $s_j$ and values $v_j$:

$$
m' = \max\!\big(m, \max_j s_j\big), \qquad \ell' = e^{m - m'}\,\ell + \sum_j e^{s_j - m'}, \qquad o' = e^{m - m'}\,o + \sum_j e^{s_j - m'}\,v_j.
$$

After the last tile the output is $o / \ell$. The factor $e^{m - m'}$ re-expresses everything stored so far relative to the new maximum. Old contributions are not forgotten, only restated in a new unit, and the final division cancels whichever unit was used.

<details class="cm-collapse" id="deriving-the-online-softmax-update">
<summary><span class="cm-collapse-icon" aria-hidden="true"><svg viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round"><path d="M15 14c.2-1 .7-1.7 1.5-2.5 1-.9 1.5-2.2 1.5-3.5A6 6 0 0 0 6 8c0 1 .2 2.2 1.5 3.5.7.7 1.3 1.5 1.5 2.5"/><path d="M9 18h6"/><path d="M10 22h4"/></svg></span><span class="cm-collapse-text"><span class="cm-collapse-kicker">Deep dive</span><span class="cm-collapse-title">Deriving the online softmax update</span></span><span class="cm-collapse-hint" aria-hidden="true"></span></summary>

For one query row with scores $s_1, \dots, s_n$ and values $v_1, \dots, v_n$, attention returns the softmax-weighted average of the values.

$$
y = \frac{\sum_{j} e^{s_j}\, v_j}{\sum_{j} e^{s_j}}
$$

Multiplying every exponential by the same factor $e^{-c}$ leaves $y$ unchanged, because the factor appears once in the numerator and once in the denominator and cancels. Any shift $c$ gives the same answer. Choosing $c$ as the largest score keeps every exponent at zero or below, so no term can overflow. That is why softmax kernels subtract the maximum.

After the first $k$ scores, the running state is defined with the largest score seen so far as the shift.

$$
m_k = \max_{j \le k} s_j, \qquad \ell_k = \sum_{j \le k} e^{s_j - m_k}, \qquad o_k = \sum_{j \le k} e^{s_j - m_k}\, v_j
$$

By the shift argument, $o_k / \ell_k$ is exactly the softmax output over the first $k$ scores. Nothing has been approximated.

A new tile arrives with scores $s_j$ for $j$ in a set $T$. The new maximum is $m' = \max(m_k, \max_{j \in T} s_j)$, and the new sum has to be measured from $m'$.

$$
\ell' = \sum_{j \le k} e^{s_j - m'} + \sum_{j \in T} e^{s_j - m'}
$$

The first sum covers scores that were already folded into $\ell_k$, and the individual scores are no longer stored. Splitting each exponent as $s_j - m' = (s_j - m_k) + (m_k - m')$ turns each old term into $e^{s_j - m_k}\, e^{m_k - m'}$. The second factor is the same for every old term, so it comes out of the sum, and what remains is $\ell_k$.

$$
\sum_{j \le k} e^{s_j - m'} = e^{m_k - m'} \sum_{j \le k} e^{s_j - m_k} = e^{m_k - m'}\, \ell_k
$$

The same step applies to $o$, since each of its terms is the same exponential multiplied by a fixed value $v_j$. These two results are the update rules above. Because $m' \ge m_k$, the factor $e^{m_k - m'}$ is at most 1, so rescaling only ever shrinks the stored numbers and cannot overflow.

The practice below checks this on numbers. Score 1 was stored in tile 1 as $e^{1-2} = 0.368$. Rescaling by $e^{2-4} = 0.1353$ turns it into $0.0498$, which is $e^{1-4}$. That is exactly what it would have been had the maximum of 4 been known from the start. Divided by the final sum of 1.5530, it gives the weight 0.032 that a softmax over all four scores assigns.

The derivation never used the fact that the new tile is fresh. Take two partial states $(m_a, \ell_a, o_a)$ and $(m_b, \ell_b, o_b)$ built from any two disjoint parts of the row. They merge the same way.

$$
m = \max(m_a, m_b), \qquad \ell = e^{m_a - m}\,\ell_a + e^{m_b - m}\,\ell_b, \qquad o = e^{m_a - m}\,o_a + e^{m_b - m}\,o_b
$$

The merge gives the same result in any order and with any grouping, so the row can be cut into pieces anywhere, the pieces processed in parallel, and the partial states combined at the end. The tile update is the special case where one side is a single tile. FlashAttention-2 keeps $o$ unnormalized in exactly this form and divides by $\ell$ once at the end. The first FlashAttention kept the output already divided by the running sum, which needs one extra rescaling per tile by the ratio of the old sum to the new one.

</details>

## Linear attention
Softmax ties every query to every key through an exponential, so nothing can be summed ahead of time. **Linear attention** replaces the exponential similarity with a dot product of transformed vectors, $\phi(q) \cdot \phi(k)$. It comes from [Katharopoulos and colleagues](https://arxiv.org/abs/2006.16236). The **feature map** $\phi$ is a fixed function that keeps entries positive. The sum over keys can then be computed once and reused, and under the causal mask it becomes a recurrence with a fixed-size state:

$$
S_t = S_{t-1} + \phi(k_t)\, v_t^{\top}, \qquad z_t = z_{t-1} + \phi(k_t), \qquad o_t = \frac{\phi(q_t)^{\top} S_t}{\phi(q_t)^{\top} z_t}.
$$

Here $S_t$ is a table that adds up each key's features times its value over every key seen so far. The vector $z_t$ adds up the features alone, and $o_t$ is the output for token $t$. A three-token example has key features $(1,0)$, $(1,1)$ and $(0,2)$ with values 4, 8 and 2. After three tokens $S = (12, 12)$ and $z = (2, 3)$. A query with features $(2,1)$ reads $2 \times 12 + 1 \times 12 = 36$ over $2 \times 2 + 1 \times 3 = 7$, giving 5.143. Its similarities to the three keys are 2, 3 and 2, so the explicit weighted average is $(2 \times 4 + 3 \times 8 + 2 \times 2)/7$, the same 5.143. The state never grew. It holds four numbers, while a cache adds three numbers per token.

The example works because the query's part of each weight is the same for every key. The weight on key $j$ is $\phi(q) \cdot \phi(k_j)$, so the query can be moved outside the sum over keys, leaving $\phi(q)^{\top} \sum_j \phi(k_j)\, v_j^{\top}$. That sum no longer mentions the query, so it can be kept as a running total and shared by every later query. The softmax weight $e^{q \cdot k}$ cannot be written as a short dot product of a part that depends only on $q$ and a part that depends only on $k$, so softmax attention has to revisit every cached key for each new query.

For the 7B shape a state of $128 \times 128$ per head is 1 MiB per layer and 32 MiB over 32 layers, the size of the 7B's cache for only 64 tokens. Updating and reading it costs about $4 h d_h^2$ FLOPs per token per layer, where $h = 32$ is the head count and $d_h = 128$ the head width. Softmax costs $4td$ at position $t$, so the recurrence is cheaper once $t$ passes $d_h = 128$.

The state is a lookup table that stores key and value pairs on top of each other, and that is where it loses. Store value 4 under key $(1,0)$ and later value 8 under $(1,1)$, and reading at $(1,0)$ returns $4 + 8 = 12$ before normalization, because the second key overlaps the first. Storing a new value 10 under the same key $(1,0)$ gives 14 instead of 10. Two fixes now appear in production models, both about what the state keeps.

The **delta rule** comes from [DeltaNet](https://arxiv.org/abs/2102.11174). It reads what the state currently predicts for a key and writes only the difference:

$$
S_t = S_{t-1} + \beta_t\, k_t \big(v_t - S_{t-1}^{\top} k_t\big)^{\top}.
$$

Here $S_{t-1}^{\top} k_t$ is what the state returns for the key before the write, $v_t$ is the new value, and the write strength $\beta_t$ lies between 0 and 1, with keys of unit length. In the example the state predicts 4 for key $(1,0)$, the error is $10 - 4 = 6$, and with $\beta = 1$ it writes 6, so reading returns 10. A **forget gate** multiplies the whole state by a factor $\alpha_t$ between 0 and 1 before writing, so with $\alpha = 0.5$ every old memory halves. [Gated DeltaNet](https://arxiv.org/abs/2412.06464) combines the two and describes them as complementary. Gating erases quickly, and the delta rule edits precisely. **Kimi Delta Attention** refines the gate so different key channels forget at different rates. It is the attention layer of [Kimi Linear](https://arxiv.org/abs/2510.26692). [RetNet](https://arxiv.org/abs/2307.08621) and other older decay-based designs used a fixed decay per head. With such a decay, $0.95^{100} = 0.006$ erases a token 100 steps back and $0.999^{100} = 0.90$ keeps it.

**Lightning attention** is an IO-aware way to compute linear attention for training, used in [MiniMax-01](https://arxiv.org/abs/2501.08313). Within a block of tokens it uses the ordinary query-times-key product, and between blocks it passes the running state. That avoids the slow step-by-step running sum over the whole sequence. Whatever the update rule, a fixed state holds a bounded number of distinct facts, so exact recall of one specific earlier token is weaker than with a cache. That is why the production models in the [state space models](#state-space-models) section keep some softmax layers.

## State space models
A running summary offers another way to carry information forward. When a token arrives, the model can keep some of the old summary and add information from the new token. A **state space model** does this by keeping a fixed-size state for each channel and updating it with a linear recurrence $h_t = \bar{A}_t h_{t-1} + \bar{B}_t x_t$. It then reads an output $y_t = C_t h_t$. Here $x_t$ is the token's input, $h_t$ the state, and $\bar{A}_t$, $\bar{B}_t$ and $C_t$ say how much to keep, how much to write and what to read. Earlier models fixed these numbers for every token, so the model could not decide what to remember from what it read. [S4](https://arxiv.org/abs/2111.00396) is one example. [Mamba](https://arxiv.org/abs/2312.00752) computes them from the token, which is called selectivity. A per-token **step size** $\Delta_t$ sets $\bar{A}_t = e^{\Delta_t A}$. With $A = -1$, a step size of 0.01 keeps 0.990 of the state and writes 0.010 of the input, while a step size of 3 keeps only 0.050 and writes 0.950. A name can be written with a large step and then held across hundreds of tokens with small ones.

Because $\bar{A}_t$ changes with the token, the convolution shortcut S4 used no longer works. With fixed numbers, every output is the same weighted sum of earlier inputs. Each weight depends only on how far back the input is, so a whole sequence can be computed as one long convolution. Once the keep factor changes from token to token, the weights differ at every position and no single convolution describes them. Mamba instead runs a **selective scan** in a kernel that keeps the state in SRAM, the same IO-aware idea as FlashAttention. The scan is a parallel prefix computation, which works because the update is linear in the state.

A single channel shows why linearity allows parallel work. Each step has the form $h_t = a_t h_{t-1} + b_t$, with keep factor $a_t$ and write $b_t = \bar{B}_t x_t$. Two steps in a row give $h_2 = a_2 a_1 h_0 + (a_2 b_1 + b_2)$. That is again one step of the same form, with keep factor $a_2 a_1$ and write $a_2 b_1 + b_2$. With $a_1 = 0.5$, $b_1 = 2$, $a_2 = 0.8$, $b_2 = 1$ and $h_0 = 0$, running the steps gives $h_1 = 2$ and $h_2 = 2.6$, and the merged step with keep factor 0.4 and write 2.6 gives the same 2.6. Merging gives the same answer under any grouping, so neighboring steps can be merged in pairs, then pairs of pairs, as a tree. The tree for 4,096 tokens has only $\log_2 4{,}096 = 12$ levels, where the plain recurrence takes 4,096 steps one after another. The online softmax merge of the [online softmax](#online-softmax) section relies on the same property.

A Mamba layer of the 7B's width with an inner width of 8,192 and state size 16 holds $8{,}192 \times 16 = 131{,}072$ numbers, so 8 MiB over 32 layers in bf16 (teaching estimate), whatever the length. [Mamba-2](https://arxiv.org/abs/2405.21060) shows this selective recurrence is a structured form of linear attention, which lets it use larger states and run on tensor cores. What these layers keep is a running summary. What they lose is reliable exact lookup of one token from far back, such as copying a string or answering from a long list. For those tasks attention's cache is an explicit index.

A **hybrid model** stacks mostly recurrent layers with a few attention layers, so the recurrent layers carry most of the sequence mixing cheaply and the attention layers supply exact lookup. Only the attention layers hold a cache, so the cache shrinks by the fraction of layers that are attention. The figure shows that for the 7B shape with one attention layer in eight.

![Sequence memory by layer mix](/images/llm-deep-dive/16a-sequence-memory-by-layer-mix.png)

Beyond a few hundred tokens the hybrid's memory is almost all cache. Its 4 attention layers add 64 KiB per token, so they pass the 28 MiB of recurrent states at 448 tokens, and from there on the hybrid tracks the all-attention stack at one eighth of its size. At 262,144 tokens that is 16 GiB plus 28 MiB against 128 GiB, while the all-recurrent stack still holds 32 MiB. A hybrid therefore does not stop the growth. It slows it by the share of layers that are attention. After the 13.48 GB of weights, an H100 holds three hybrid sequences at that length, no all-attention sequence at all, and about 2,000 all-recurrent ones. The few attention layers keep exact lookup available, and their cache is the price of it. Several production models now use this design.

| Model | Recurrent layer | Recurrent to attention | Reported effect |
|---|---|---|---|
| [Jamba](https://arxiv.org/abs/2403.19887), 52B total, 12B active | Mamba | 7 to 1 | 4 GB of cache at 256K tokens against 32 GB for Mixtral |
| [Nemotron-H](https://arxiv.org/abs/2504.03624), 8B and 56B | Mamba | most attention layers replaced | up to 3 times faster inference than similar transformers |
| MiniMax-01, 456B total, 45.9B active | lightning attention | 7 to 1 | trained at 1M tokens, extrapolates to 4M |
| Qwen3-Next-80B-A3B | Gated DeltaNet | 3 to 1, gated attention | over 10 times the throughput of Qwen3-32B beyond 32K tokens |
| Kimi Linear, 48B total, 3B active | Kimi Delta Attention | 3 to 1, MLA | up to 75% less cache, up to 6 times decode throughput at 1M tokens |

Where the attention layers go and how many remain is the main design choice. Ratios of 3 to 1 and 7 to 1 are both in use, and the recall tasks that a fixed state handles worst are the ones that decide the ratio.

## Method selection
Each method in this chapter acts on one of the two costs from the opening, so the choice starts by measuring which one dominates. Training and prefill are measured by score arithmetic and score memory, and decode by cache size and cache reads. The table maps each bottleneck to the methods and to what current models choose.

| Bottleneck | Symptom | Methods | What current models choose | Main cost |
|---|---|---|---|---|
| Score table memory in training and prefill | Out of memory at long sequences, slow kernels | FlashAttention with online softmax | Universal, with FlashAttention-3 on Hopper | Quadratic arithmetic remains |
| Score arithmetic past about 33K tokens | Attention dominates the step time | Local and global layers, block-sparse or learned selection | Gemma 3 at 5 to 1, gpt-oss alternating, DeepSeek-V3.2 with DSA | Long-range recall must be tested |
| Cache size limits users per GPU | Few concurrent sequences | Grouped-query attention, MLA, local layers | Llama 3, Qwen3 and gpt-oss use 8 key value heads, and DeepSeek-V3 and Kimi K2 use MLA | Needs training or uptraining, and MLA needs custom kernels |
| Cache reads slow each decode step | Time per token grows with context | Fewer key value bytes, top-k selection | MLA with DSA in DeepSeek-V3.2 | Indexer cost and selection quality |
| Memory must stay flat for very long inputs | Context of hundreds of thousands of tokens | Linear attention with gates and the delta rule, state space models, hybrids | Qwen3-Next and Kimi Linear at 3 to 1, Jamba and MiniMax-01 at 7 to 1 | Weaker exact recall, so some attention layers stay |
| Training instability in attention | Exploding scores, loss spikes | QK-norm, output gates, learned sinks | Qwen3 and Gemma 3 with QK-norm, Qwen3-Next gated attention, gpt-oss sinks | Small extra parameters |

The rows fall into three groups. The first two belong to training and prefill, where the score table is the problem. The next three belong to decode, where the cache is. The last row is about keeping training stable and combines with any of the others. The symptom column is what shows up first in a profile or an error log, and one symptom can come from different rows. A step that slows as the context grows points to score arithmetic in training and to cache reads in decode, so the phase decides the row before any method is picked. Methods from different rows also stack. DeepSeek-V3.2 uses MLA for cache size and DSA for cache reads, and Gemma 3 pairs local layers with QK-norm. The last column is the price each method adds, and that price is usually why a model stops at a partial fix, such as keeping a few global layers instead of making every layer local.

A worked diagnosis shows the table in use on the 7B served at batch 1. The symptom is that a new token at 32,768 tokens of context takes 9.2 ms, about twice the 4.7 ms at 4,096, although the weights read per step have not changed. The first measurement is the bytes each step reads, since the [prefill and decode bottlenecks](#prefill-and-decode-bottlenecks) section showed that decode attention does about 1 FLOP per byte and is never limited by arithmetic. The weights are 13.48 GB and the cache is 17.2 GB, so 56% of the bytes read are cache. That points to the fourth row, cache reads. A 17.2 GB cache also leaves room for only three such sequences in the 66.5 GB beside the weights, which points to the third row as well. Both rows share one fix, fewer key value bytes per token. Holding the weights at 13.48 GB, 8 key value heads cut the cache read to 4.3 GB and the step to 5.3 ms and fit 15 sequences. An MLA-style latent cuts it to 1.2 GB and 4.4 ms and fits 55. Score sparsity from the second row would barely help here, because arithmetic was never the limit. After the latent, the weights are 92% of the bytes read again, and weight quantization becomes the next lever.

The training side reads the same way. A plain implementation that runs out of memory training the 7B on 4,096-token sequences is holding 32 GiB of softmax probabilities, as the [attention cost](#attention-cost) section showed. That is more than twice the weights. It is the first row. FlashAttention replaces the table with log-sum-exp statistics of 512 KiB per layer, or 16 MiB across 32 layers. The arithmetic stays the same.
