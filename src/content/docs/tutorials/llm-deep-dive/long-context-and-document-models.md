A 120-page annual report filed as a 10-K comes to about 96,000 tokens, at an estimated 800 tokens per page. That is 23 times the 4,096-token window the reference 7B model was trained on, and well inside the 131,072-token window that many current models advertise. Fitting is the easy part. A question as plain as "what was net debt under the credit agreement at year end?" needs three passages from three different parts of the filing. They are a definition in the liquidity discussion on page 58, the cash balance on page 66, and a debt table with a footnote on page 91. The answer is $1{,}840 - 140 - 310 = 1{,}390$ million, and a model that misses the footnote answers 1,530 with the same confidence.

![Evidence in a 10-K](/images/llm-deep-dive/16b-evidence-in-a-10-k.png)

All three passages sit between 48% and 76% of the way through the document, which is exactly where long-context models tend to read least carefully. They are also far apart. About 26,000 tokens separate the liquidity definition from the debt table, more than six times the 7B's trained window, so in training the model never saw an offset that large between any two tokens. After extension to 131,072 tokens the filing fills about three quarters of the window, and nothing in the text marks that a sentence on page 58 changes how a table on page 91 should be read. A model can accept all 96,000 tokens without an error and still answer from the wrong two of them.

That gap between accepting a long input and using it runs through every section. The first half stays inside the model and takes the problems in the order they bite. Rotary position embedding produces angles the model has never seen as soon as an input passes the trained length, so position interpolation, NTK-aware scaling and YaRN come first, each slowing the rotations in its own way to keep the angles familiar, and some current models also mix position schemes across layers. Familiar angles only stop the damage. The model still has to learn to use evidence far back, which is what continued training at long length pays for. Even a model trained that way spreads its attention unevenly, and attention sinks and the lost-in-the-middle effect explain why it still favors a few tokens.

The second half moves outside the model, because many failures happen before any token reaches it. A footnote dropped during parsing cannot be recovered by any model, so turning filings into text that keeps tables, units and sources comes first. With good records in hand, a long input can be read in pieces through summaries or segment memory, or replaced by retrieval, which costs far less but can miss a passage. Long reports add errors that compound with length and need their own planning and checks. The closing sections cover evaluations that measure usable rather than advertised context, and a debugging table that maps each failure to the check that separates it from the others.

## Effective context length
A model's context window is a limit on how many tokens it accepts, and it says nothing about how well the model uses them. Three separate things have to go right for the net debt question. The positions of all 96,000 tokens must produce attention scores the model knows how to read. Attention must actually find the three relevant passages among 95,000 tokens of plausible financial text. The model must then combine them correctly, subtracting the leasing debt only because the credit agreement says so.

The **effective context** of a model is the longest input at which it still performs a given task at a fixed quality bar. The advertised window, by contrast, only says how long an input the code accepts. Effective context depends on the task. A model can find one planted sentence at 128,000 tokens and fail to add up four segment revenue figures spread across 30,000 tokens.

The cleanest way to tell the three failures apart is an **oracle evidence test**, which runs the same question three ways. The first run gives the model the whole filing. The second gives it only the three gold passages, about 1,500 tokens. The third gives the gold passages buried in 90,000 tokens of other companies' filings. If the second run fails, the problem is reasoning or reading the table, and no amount of context engineering fixes it. If the second succeeds and the third fails, the model cannot pick evidence out of distractors at that length. If both succeed and the first fails, something about the real document breaks it, such as a footnote separated from its table during parsing.

Financial text has one more quirk that matters for capacity. The Llama 2 tokenizer gives every digit its own token, so "1,840" costs about five tokens, and a page of financial statements uses far more tokens than a page of risk-factor prose. Capacity estimates made from page or word counts therefore run low for exactly the sections that hold the numbers.

## RoPE extrapolation
The reference 7B uses [rotary position embedding](/tutorials/llm-fundamentals/attention-and-positional-information/#rotary-position-embedding) with head width 128, so each head has 64 coordinate pairs, and pair $i$ turns by $\theta_i = 10{,}000^{-2i/128}$ radians per position. The score between a query and a key depends only on their offset $n$, through the angle $n\theta_i$ on every pair. During training the offset never exceeds 4,095, so each pair has only ever produced angles up to $4{,}095\,\theta_i$.

Those limits differ enormously across pairs. The **wavelength** of a pair is the number of positions it takes to complete one full turn, $\lambda_i = 2\pi/\theta_i$.

| Pair $i$ | Radians per position $\theta_i$ | Wavelength $\lambda_i$ | Turns within 4,096 | Largest angle at 131,072 |
|---|---|---|---|---|
| 0 | 1 | 6.3 | 652 | 131,071 |
| 16 | 0.1 | 63 | 65 | 13,107 |
| 32 | 0.01 | 628 | 6.5 | 1,311 |
| 46 | 0.00133 | 4,712 | 0.87 | 175 |
| 63 | 0.000115 | 54,410 | 0.075 | 15.1 |

Pair 0 wraps around 652 times inside the trained window, so it has produced every angle between 0 and $2\pi$ many times over. At an offset of 100,000 it still produces an angle it has seen, only paired with unfamiliar angles on the other pairs. Pair 63 is different. Its largest trained angle is $4{,}095 \times 0.000115 = 0.47$ radians, or 27 degrees. At offset 131,071 it reaches 15.1 radians, 2.4 full turns. The query and key vectors on that pair land in directions the attention weights were never fitted to. Pairs 46 to 63 are in the same situation, 18 of the 64 in all.

The attention score shows what an unfamiliar angle does. On one pair, a query and a key that point the same way at offset 0 contribute their full product times $\cos(n\theta_i)$ at offset $n$. Over training, pair 63 turned at most 0.47 radians, so for such a query and key its contribution only ever fell from the full product to 0.89 of it, a gentle signal that the key sits further back. At offset 131,071 the angle of 15.1 radians lies 147 degrees past the second full turn, and the same query and key contribute $-0.84$ of their full product. A match the model learned to read as similar and somewhat distant now reads as opposed. At offset 54,410 the pair completes exactly one turn, so on this pair a key that far back looks the same as the token right next to the query.

![Rotation range per pair](/images/llm-deep-dive/16b-rotation-range-per-pair.png)

Every pair's angle grows in proportion to the offset, so a 32 times longer input multiplies every pair's largest angle by 32. That does no harm to a pair whose trained angles already wrapped past a full turn, since it only wraps more. The harm falls on pairs 46 to 63, whose trained angles never reached a full turn, and those are the ones whose angles leave familiar territory. The slow pairs are also the ones the model relies on to judge long distances, because a fast pair cannot tell offset 10 from offset 16.3, which is one full turn later. The trouble also starts right at the boundary. Every pair from 46 to 63 reached its largest trained angle at offset 4,095, so any longer offset is new to all 18, and the faster of them move away quickest. Pair 46 saw angles up to 5.46 radians. An offset of 4,500 is only about 400 tokens past the boundary, yet it already takes pair 46 to 6.0 radians. Running the model unchanged at long length therefore corrupts exactly the signal that long inputs need, and [length extrapolation](/tutorials/llm-fundamentals/attention-and-positional-information/#alibi-and-length-extrapolation) fails within a few hundred tokens past the trained length.

One way to avoid unseen angles is to make the slow pairs slower before pretraining starts, by raising the base from 10,000. [Code Llama](https://arxiv.org/abs/2308.12950) raised it to 1,000,000 when fine-tuning on long code, and [Llama 3](https://arxiv.org/abs/2407.21783) pretrains with a base of 500,000. With base 500,000 the slowest pair of a 128-wide head has a wavelength of $2\pi \times 500{,}000^{126/128} = 2.56$ million tokens, so even a 128,000-token input moves it through only 5% of a turn. A large base does not remove the need for long-context training, since the model still has to learn to use distant evidence. It does mean the extension stage starts from angles the model has partly seen.

## Position interpolation
Every practical extension method keeps the angles inside the trained range by slowing the rotations. They differ in which pairs they slow. The **extension factor** $s$ is the ratio of the target length to the trained length, here $s = 131{,}072 / 4{,}096 = 32$.

The attention chapter introduced position interpolation at a factor of 4. It divides every position by $s$, which is the same as dividing every rate. Each rate becomes $\theta_i' = \theta_i / s$. Position 131,071 is then read as 4,095.97, so every position in the long input lands inside the trained range, and whole-number positions become fractions that fall between the ones the model saw. The method takes its name from this, since the model reads between familiar positions instead of beyond them. The price is that all 64 pairs slow by the same factor, including the fast pairs that already wrapped many times and needed no help. Those fast pairs carry the fine spacing that tells adjacent words apart, and dividing their rates by 32 squeezes that spacing until fine-tuning teaches the model to read it again.

**NTK-aware scaling** slows each pair by a different amount instead. The user bloc97 proposed it in a 2023 community post. Its name comes from a [neural tangent kernel result](https://arxiv.org/abs/2006.10739) that networks learn high-frequency detail poorly when their input is low-dimensional and lacks high-frequency components. A position is a single number, and the fast pairs are the high-frequency components that rotary encoding builds from it, so stretching them is the damage to avoid. The rule leaves the fastest pair alone, slows the slowest pair by the full factor $s$, and does both with one change, a larger base:

$$
b' = b \cdot s^{d/(d-2)}, \qquad \theta_i' = b'^{-2i/d}.
$$

Here $b = 10{,}000$ is the original base, $d = 128$ is the head width, and $i$ runs from 0 to 63. The exponent $d/(d-2)$ is chosen so that the slowest pair $i = 63$ is slowed by exactly $s$. Substituting gives $\theta_{63}' = b^{-126/128} \cdot s^{-1}$. The fastest pair has exponent zero, so it keeps $\theta_0' = 1$ for any base. Pairs in between are slowed by $s^{2i/126}$, a factor that grows smoothly from 1 to 32. The smooth curve has its own cost in the middle of the head. The pairs just below the slowest never completed a turn in training either, yet the curve slows them by less than $s$, so part of their range at 131,072 tokens is still new. Neither rule matches a pair's slowdown to whether that pair actually left its trained range, and that mismatch is what YaRN corrects.

Interpolation's weakness is step 3. The pairs that told "the" from the word after it now see two tokens as 1/32 of a position apart, so local word order blurs and quality drops until fine-tuning teaches the model the new spacing. The [Position Interpolation paper](https://arxiv.org/abs/2306.15595) reports that about 1,000 fine-tuning steps recover it. NTK-aware scaling often works with little or no fine-tuning at small factors, but it has its own flaw. Pairs 46 to 62 never completed a turn in training, yet NTK-aware scaling slows them by less than 32. Pair 46 is slowed 12.6 times, so at 131,072 tokens it still reaches 13.9 radians against the 5.5 it saw in training, and those pairs stay partly out of range.

## YaRN
In rotary position embeddings, some coordinate pairs complete many turns inside the original window while others barely turn at all. The amount of rescaling can depend on which kind of pair we are working with. **YaRN** comes from [Peng and colleagues](https://arxiv.org/abs/2309.00071). It treats each pair according to how many turns it completes inside the trained window, $r_i = L/\lambda_i$, where $L = 4{,}096$ is the trained length. A pair that wraps many times needs no help, a pair that never wraps needs full interpolation, and pairs in between get a blend. The blend weight is the **ramp function**:

$$
\gamma(r) = \begin{cases} 0 & r < \alpha \\ (r - \alpha)/(\beta - \alpha) & \alpha \le r \le \beta \\ 1 & r > \beta \end{cases}, \qquad \theta_i' = (1 - \gamma(r_i))\,\frac{\theta_i}{s} + \gamma(r_i)\,\theta_i.
$$

Here $\alpha = 1$ and $\beta = 32$ are the turn counts the paper uses for Llama models, $\theta_i$ is the original rate and $\theta_i'$ the new one. A $\gamma$ of 1 keeps the pair as it was and a $\gamma$ of 0 interpolates it fully. On the three pairs from the [position interpolation](#position-interpolation) section, pair 0 completes 652 turns, so $\gamma = 1$ and it is untouched. Pair 63 completes 0.075 turns, so $\gamma = 0$ and it is divided by 32. Pair 32 completes 6.52 turns, so $\gamma = (6.52 - 1)/31 = 0.178$ and

$$
\theta_{32}' = 0.822 \times \frac{0.01}{32} + 0.178 \times 0.01 = 0.000257 + 0.00178 = 0.00204,
$$

a slowdown of 4.9. Across the head, pairs 0 to 20 are untouched, pairs 21 to 45 sit on the ramp, and pairs 46 to 63 are divided by 32. The paper reports that YaRN needs 10 times fewer tokens and 2.5 times fewer training steps than earlier extension methods.

![Yarn frequency ramp](/images/llm-deep-dive/16b-yarn-frequency-ramp.png)

YaRN and NTK-aware scaling agree only at the fastest and slowest pairs, and in between they disagree in both directions. Pairs 46 to 62 never completed a turn, so YaRN divides each of them by the full 32 and none of their angles leaves the trained range, where NTK-aware scaling slows pair 46 only 12.6 times. Lower in the head YaRN slows pairs less than NTK-aware scaling does, 4.9 times against 5.8 for pair 32, and pairs 0 to 20 not at all. Those pairs already wrapped many times in training and gain nothing from being slowed, while slowing them squeezes the fine spacing between neighbouring tokens. YaRN spends the slowdown only where an angle would otherwise be new.

YaRN has a second ingredient. **Attention temperature** is a factor applied to every attention logit. YaRN multiplies the query and key each by $0.1 \ln s + 1$, so the logits grow by $(0.1 \ln s + 1)^2$, which is 1.81 at $s = 32$. The factor grows with the logarithm of $s$, so it is 1.30 at $s = 4$ and 1.46 at $s = 8$, and each doubling of the length adds about 0.07 to the multiplier on the query and key. Longer inputs spread each softmax row over more tokens, and sharper logits push the weights back toward the shape the model learned. The authors fitted the formula empirically on Llama models.

Softmax spreads its weight over every key in the row, so one relevant key holds a smaller share as the row grows. Take one matching key whose logit is 5 above all the others, which are tied. Its weight is $e^5/(e^5 + n - 1)$. That is 0.035 at $n = 4{,}096$ and 0.0011 at $n = 131{,}072$, 31 times less for the same content. Multiplying every logit by 1.81 turns the margin of 5 into 9.07, and the weight at 131,072 becomes $e^{9.07}/(e^{9.07} + 131{,}071) = 0.062$. The real effect is less clean, because the other logits are not tied and interpolation also changes them. Still, the arithmetic shows why a length-dependent sharpening is needed at all.

YaRN is now the usual extension in open model families. [DeepSeek-V3](https://arxiv.org/abs/2412.19437) applies it with $s = 40$, $\alpha = 1$, $\beta = 32$ and the same temperature formula while training from 4K to 32K and then 128K tokens. [Qwen3](https://huggingface.co/Qwen/Qwen3-8B) runs 32,768 tokens natively and 131,072 with YaRN at a factor of 4. Its model card warns that the static form can hurt short inputs, because it applies the factor to every request. **Dynamic scaling** avoids that by choosing $s$ from the current request length. [gpt-oss](https://arxiv.org/abs/2508.10925) also reaches 131,072 tokens with YaRN.

Other designs vary the position scheme by layer instead of by pair. [Gemma 3](https://arxiv.org/abs/2503.19786) alternates five local layers with one global layer. The local layers attend over a 1,024-token sliding window with base 10,000, so they never meet an unfamiliar offset at any input length. The global layers use base 1,000,000. After pretraining at 32K they are rescaled to reach 128K with a method close to position interpolation. The report gives the factor as 8. The report notes that quality falls quickly beyond 128K. [Llama 4](https://ai.meta.com/blog/llama-4-multimodal-intelligence/) removes position encoding from some layers entirely, a design Meta calls iRoPE. A layer with **no position encoding**, or NoPE, scores keys by content alone and gets order only indirectly from the causal mask. In the default configuration of the Hugging Face implementation every fourth layer is NoPE, the rotary layers attend within chunks of 8,192 tokens, and the NoPE layers multiply each query at position $p$ by a temperature

$$
1 + 0.1 \ln\big(1 + \lfloor (p+1)/8{,}192 \rfloor\big),
$$

where $\lfloor \cdot \rfloor$ rounds down. It is 1.07 at position 8,191, 1.28 at 131,071 and 1.71 at 10 million. Meta reports Scout was trained at 256K tokens and advertises 10 million, with needle retrieval and loss on long code as the published evidence. **Partial RoPE** rotates only some coordinates of each head. [Pythia](https://huggingface.co/EleutherAI/pythia-6.9b/blob/main/config.json) rotates 32 of 128. All three designs rest on the idea that only part of the attention needs exact positions far away. [Efficient Attention](/tutorials/llm-deep-dive/efficient-attention-mechanisms/) covers the local attention patterns they pair with.

## Long-context continued training
Rescaled frequencies only make the inputs look familiar. The model still has to learn to find and use evidence tens of thousands of tokens back, which almost never happens in short pretraining windows. **Long-context continued training** is a short extra training stage on long sequences after the frequencies are changed, and it is usually part of [mid-training](/tutorials/llm-fundamentals/pretraining-at-scale/#mid-training).

The data matters more than the length. A 128K window of concatenated web pages teaches nothing about long dependencies, because no page depends on another. **Long-dependency data** is text in which later tokens need earlier ones far back. Examples are books, code repositories ordered by imports, filings whose notes refer to tables 30 pages earlier, and synthetic tasks that plant evidence far from its question. A useful filter keeps documents whose per-token loss drops noticeably when the context grows from 4K to the full length. [Fu and colleagues](https://arxiv.org/abs/2402.10171) found that 500 million to 5 billion tokens of continued training let Llama 2 models retrieve information anywhere in 128K, that the domain mixture should stay balanced, and that naively upsampling long books works poorly. [Xiong and colleagues](https://arxiv.org/abs/2309.16039) found that upsampling long texts during continued training mattered more than having many long texts in the original pretraining set.

A **length curriculum** raises the training length in stages rather than jumping straight to the target. Llama 3 went from 8K to 128K in six stages over about 800 billion tokens, moving on only once short-context scores had recovered and needle retrieval was perfect at the current length. DeepSeek-V3 used two phases of 1,000 steps each. The first ran at 32K with a batch of 1,920 sequences and the second at 128K with a batch of 480. Both phases therefore hold the same 62.9 million tokens per step, and about 126 billion tokens in total by that arithmetic. Mixing short documents into every stage keeps short-task quality from drifting, and the [document mask](/tutorials/llm-fundamentals/pretraining-at-scale/#sequence-packing) keeps unrelated documents in one packed window from attending to each other.

The cost per token climbs with length because attention grows with the square of the sequence. Training costs $6N$ [FLOPs per token](/tutorials/llm-fundamentals/the-transformer-block-and-model-anatomy/#flops-per-token) for the weights plus about $6Lnd$ for causal attention averaged over the window, where $L = 32$ layers, $d = 4{,}096$ and $n$ is the sequence length.

| Sequence length | Weights, GFLOPs per token | Attention, GFLOPs per token | Total | Relative to 4,096 |
|---|---|---|---|---|
| 4,096 | 40.4 | 3.2 | 43.7 | 1.00 |
| 32,768 | 40.4 | 25.8 | 66.2 | 1.52 |
| 131,072 | 40.4 | 103.1 | 143.5 | 3.29 |

At 128K the attention arithmetic is two and a half times the weight arithmetic. Ten billion tokens of continued training at 131,072 then cost $10^{10} \times 143.5 \times 10^9 = 1.44 \times 10^{21}$ FLOPs. That is 1.8% of the $8.09 \times 10^{22}$ spent on 2 trillion pretraining tokens, or about 1,000 H100-hours at 40% utilization (a teaching estimate). Memory is the harder limit. [Korthikanti and colleagues](https://arxiv.org/abs/2205.05198) estimate 34 bytes per token per unit of width per layer, with attention scores never stored. By that estimate, one 131,072-token sequence of the 7B holds about 584 GB of activations across its 32 layers if nothing is recomputed. A single sequence therefore no longer fits on one GPU. Long-context training splits the sequence itself across GPUs, which [Parallelism](/tutorials/llm-deep-dive/distributed-training-and-parallelism/) covers as context parallelism. The kernels that compute attention without storing the score table are in [Efficient Attention](/tutorials/llm-deep-dive/efficient-attention-mechanisms/).

## Attention sinks and lost in the middle

Inside a working long context, attention is not spread evenly, and two biases matter most. The first is that many heads put a large share of their weight on the first few tokens regardless of content. [StreamingLLM](https://arxiv.org/abs/2309.17453) named such tokens **attention sinks**. Softmax forces every row of weights to sum to 1, so a head with nothing relevant to read still has to put its weight somewhere. Models learn to park it on the first tokens. The value vectors of those tokens end up small, so the parked weight adds almost nothing to the output.

The toy row in the figure shows why this matters. One query gives the sink a logit of 3.0 and seven recent tokens 0.5 each. The sink gets $e^{3}/(e^{3} + 7e^{0.5}) = 0.635$ and each recent token 0.052. A plain sliding window evicts the sink once the text outgrows the cache. Then each recent token jumps to $1/7 = 0.143$, 2.7 times its trained share. The head now writes 2.7 times more of content it meant to ignore into the residual stream. The StreamingLLM authors found that plain window attention breaks down as soon as the text outgrows the cache.

![Attention sink](/images/llm-deep-dive/16b-attention-sink.png)

StreamingLLM's fix follows from the toy row. The sink's weight is what keeps the recent tokens at their trained share, so the sink must never be evicted. The **StreamingLLM cache** always keeps the first 4 tokens plus a rolling window of recent tokens, and numbers positions by cache slot rather than by place in the text, so rotation angles never exceed the cache size. The paper reports stable language modeling over 4 million tokens and up to a 22.2 times speedup over recomputing a sliding window, and found that a dedicated placeholder sink token during pretraining helps further. The evicted tokens are gone for good, though, so the cache keeps an endless chat fluent and does nothing for a question about page 58 read 40,000 tokens ago.

Some models now build the sink into the softmax itself. The gpt-oss models give each head a **learned sink logit**. It is a bias $b$ added to the softmax denominator, so that $a_j = e^{z_j}/(e^{b} + \sum_k e^{z_k})$. A head can then give weight to no token at all. With $b = 3.0$ the seven recent tokens in the toy row get 0.052 each, exactly as with a real sink token. The remaining 0.635 goes nowhere.

The second bias is [lost in the middle](/tutorials/llm-fundamentals/using-llms-in-applications/#long-context-use). Accuracy is highest when evidence sits near the start or end of the prompt and lowest in between. Three causes are usually offered, each only partly established. Early tokens are visible to every later position, so they collect attention in every layer. Rotary encoding gives a mild preference for nearby tokens, which favors the end. And training data usually puts the important text at the ends, with instructions first and the question last. The net debt question is the bad case, since all three passages sit between 48% and 76% through the filing. The common mitigations are cheap. The question is stated both before and after the document, retrieved passages are placed at the ends, and training uses examples whose evidence position is spread uniformly.

## Document representation
A filing is a tree of sections, tables whose meaning depends on row and column headers, footnotes attached to specific cells, and units stated once in a heading. Plain text extraction flattens all of that, and the damage is invisible until an answer is wrong by a factor of a million or ignores an exception. **Document representation** is the form a document takes before any model sees it, and for long documents it decides more answers than the model does.

The debt row on page 91 shows what has to survive. The table header says "in millions", the row reads "Leasing (a) 140 95", and footnote (a) says the leasing debt is non-recourse to the company. Plain extraction keeps the row and loses both the unit and the meaning of (a), so a model given that text can neither scale the number nor know that the credit agreement excludes it. The fix is to parse the layout into cells, attach the header's unit and the footnote's text to each cell, and normalize the value while keeping the printed form.

![Ingestion with provenance](/images/llm-deep-dive/16b-ingestion-with-provenance.png)

The pipeline ends in a **chunk record**, the unit that gets indexed and later cited. Besides the text it carries **provenance**, which records the filing, item, note, page, table, row, column and character span the text came from. Provenance is what lets an answer cite page 91 row 3, lets a checker reopen the exact cell, and lets a corrected filing replace exactly the records it changed. SEC filings also carry Inline XBRL tags on the financial statements. These attach a concept name, period, unit and scale to each reported number, so a pipeline can cross-check parsed table values against the tagged facts.

Tables need a deliberate **table serialization**, the way rows are written out as text. A markdown grid is compact but leaves a chunk that starts mid-table without its headers. Writing each row as "Leasing facility, fiscal 2025, debt in USD millions: 140, non-recourse (footnote a)" costs more tokens and makes every chunk self-contained. Earnings call transcripts need different handling. They have speaker turns, the split between prepared remarks and analyst questions, and spoken numbers such as "about one point four billion" that should be normalized and linked back to the reported figure. In both cases, [chunking](/tutorials/llm-fundamentals/using-llms-in-applications/#embedding-models-and-vector-search) should cut at section and table boundaries rather than every fixed number of tokens. Document text should be treated as data and never as instructions, since filings and transcripts can quote anything.

## Hierarchical processing
A document that is longer than the window or too expensive to read in one pass can be read in pieces. **Hierarchical processing** reads each chunk separately, writes a short output per chunk, and then reasons over those outputs. **Map-reduce summarization** is the simplest version. The 96,000-token filing becomes 47 chunks of 2,048 tokens. Each is summarized in 128 tokens, so the second stage reads 6,016 tokens. The first stage costs $47 \times 2.87 \times 10^{13} = 1.35 \times 10^{15}$ FLOPs, 36% of one full-length prefill. Its 47 chunks run in parallel. The danger is a **summary bottleneck**. A summary of Note 9 that says "total debt of 1.84 billion dollars" has dropped the 140 million exception, and no later stage can recover it. The damage is limited when the first stage writes structured records of amounts, units, periods, exceptions and source spans rather than prose, and when every record points back to its source so the second stage can reopen the original text.

**Segment recurrence** builds memory into the model instead. [Transformer-XL](https://arxiv.org/abs/1901.02860) processes text in fixed segments and lets each layer attend to its own segment plus a **segment memory**. The memory holds the hidden states the layer below produced for the previous segment, stored and reused. It carries a **stop-gradient**. Training sends no gradient back into it, so each step backpropagates through one segment only. Because each layer's memory comes from the layer below, information can travel one extra segment back per layer.

## Retrieval versus long context

For a single question about one filing, [retrieval augmented generation](/tutorials/llm-fundamentals/using-llms-in-applications/#retrieval-augmented-generation) and a long prompt compete directly, and the cost gap is large enough to decide most deployments.

A long prompt pays in three places, and each grows with the prompt length in its own way. Prefill runs every prompt token through the weights and through causal attention. The weight cost grows in proportion to the length. Causal attention compares each token with all the tokens before it, so its cost grows with the square of the length. For a prompt the size of a filing, the attention term is the larger of the two. The KV cache then holds a key and a value for every prompt token in every layer, so its memory grows in proportion to the length and decides how many requests can share one GPU. Decode is the third cost. Every generated token reads the weights and the whole cache from memory, so a long prompt slows each step of the answer as well as the first one. Retrieval avoids all three by putting a few thousand tokens in the prompt whatever the length of the filing, and its search step costs little next to the model.

Retrieval pays in recall instead. A question answered from several passages needs every one of them retrieved. If each passage is retrieved independently, the chance of a complete set is the product of the individual retrieval probabilities. In practice the misses can be correlated, so complete-set recall is a separate measurement. The full-document example places all parsed passages in the prompt. In a real system, parsing and truncation can remove evidence before the model sees it. Even when the passage is present, its position can affect whether the model uses it, as the [attention sinks and lost in the middle](#attention-sinks-and-lost-in-the-middle) section shows. The choice therefore weighs a large and certain compute bill against a small bill that sometimes arrives without its evidence. The walkthrough prices one net debt question both ways on the reference 7B extended to 128K, running on one H100.

Step 6 is why the choice is not purely about cost. Retrieval wins when a question needs a few passages that a search can find by their words or meaning, such as "what was the cash balance". Long context wins when the evidence is scattered, linked by reference rather than by shared words, or needs the whole document, such as "list every risk factor that mentions a single supplier" or a question whose exception sits in a footnote nobody would search for. Many questions about one document also change the arithmetic. If the filing's cache is computed once and reused across questions, each further question pays only for its own tokens and decode, which [Serving Systems](/tutorials/llm-deep-dive/inference-systems-at-scale/) covers as prefix caching. With the walkthrough's numbers, a 50-token follow-up about a cached filing needs about 8 milliseconds of prefill, but its 200-token answer still reads the full 50.3 GB cache at every step and takes 3.8 seconds. The gap with retrieval narrows from 11 times to about 3. Ten questions cost about 48 GPU-seconds against 12, and the cached filing holds most of the GPU's memory between questions.

The two also combine well. [Xu and colleagues](https://arxiv.org/abs/2310.03025) found that a 4K-window model with simple retrieval matched a 16K-window model extended by interpolation at much lower cost. Retrieval improved long-context models too, and their best results came from a 32K Llama 2 70B with retrieval. A practical pattern for filings retrieves at the section level rather than the chunk level. It pulls in the whole liquidity section and the whole debt note, roughly 15,000 tokens. That keeps tables and footnotes together at a fraction of the full prompt's cost. Priced the same way, a 15,000-token prompt takes 0.66 seconds to prefill and 1.27 seconds to decode, about 1.9 GPU-seconds in all. That is 7 times less than the full filing and 1.6 times the cost of six chunks, and eight such requests fit beside the weights. The debt table and its footnote also arrive together in one retrieved section, so the footnote no longer has to be found by its own words.

## Long document generation

Writing a long report from a filing is harder than answering one question, because errors compound with length. If each numerical claim in a 40-claim earnings summary is right with probability 0.98, the chance that all 40 are right is $0.98^{40} = 0.45$. A long report also has to stay consistent with itself. The liquidity section and the debt section must use the same definition of net debt. That gives 1,390 million in both, rather than 1,390 in one and 1,530 in the other.

The usual structure separates deciding what to say from saying it. A **section plan** lists each section's purpose, the facts it will use and the sections it depends on. The conclusion about leverage is then written after the debt discussion and from the same facts. A **fact ledger** holds every number the report may use as a structured record with entity, period, unit, definition and source span, drawn from the chunk records of the [document representation](#document-representation) section. **Section-wise generation** then writes one section at a time from the plan, its ledger entries and the accepted earlier sections, rather than generating 5,000 tokens in one pass where an early slip conditions everything after it.

Checks run between sections, and the cheapest ones are deterministic. Every derived number is recomputed by code from the ledger. Revenue rising from 2,140 to 2,310 million is growth of $(2{,}310 - 2{,}140)/2{,}140 = 7.9\%$, and a draft that divides by the new value and says 7.4% fails the check. **Coherence checks** compare entities, periods and metric definitions across sections and flag any number that appears twice with different values. Citation checks then test whether each cited span actually supports its claim, measured with the claim-level [citation precision and recall](/tutorials/llm-fundamentals/evaluation-reliability-and-safety/#grounding-and-citation-checks) already defined for grounded answers. A failed check sends only the failing section back for revision, with a cap on retries so the loop always ends. A claim the evidence cannot support is reported as uncertain rather than smoothed over.

## Long context evaluation

Long-context claims have to be tested at the lengths and evidence positions that matter, and the most common test is too easy to separate models. The **needle in a haystack test** plants one sentence at a chosen depth inside filler text and asks for it back, then repeats over a grid of lengths and depths. Greg Kamradt popularized it in 2023. It checks that positions work and that attention can reach every depth. It is too easy for three reasons. The planted sentence usually shares its key words with the question, so a single attention head can match it. It needs one hop and no reasoning. And the filler is unrelated to the needle, so nothing competes with it. Many models score nearly perfectly on it at lengths where they fail harder tasks.

![Long context task types](/images/llm-deep-dive/16b-long-context-task-types.png)

[RULER](https://arxiv.org/abs/2404.06654) keeps the synthetic, controllable format and removes those shortcuts one at a time. Needles among **distractors** hide one target among similar keys, so matching the words "code for" finds four candidates and the model has to choose by the one word that differs. **Variable tracking** is a multi-hop task, where the answer is the value at the end of a chain of assignments spread across the input. In the four-variable chain shown, the value 31415 appears near the start. To recover the value of X4, the reader follows three variable references spread over about 80,000 tokens. Each hop is one lookup, and each lookup depends on the one before. **Aggregation** asks for something no single passage contains, such as the most frequent words. A count over 12 mentions is wrong if any one of them is missed, so it tests whether attention covers the whole input rather than whether it can find one place in it. The net debt question needs both of the harder skills, since a definition on page 58 changes how a table on page 91 is read and the answer combines three passages. Across 13 tasks and 17 models, the authors found that only half of the models claiming 32K or more held satisfactory performance at 32K. That is the clearest published measurement of effective context falling short of advertised windows.

Two newer evaluations are what labs now report next to needle results. OpenAI's [MRCR](https://huggingface.co/datasets/openai/mrcr) is modeled on the multi-round coreference task from Google's [Michelangelo](https://arxiv.org/abs/2409.12640). It builds a long synthetic conversation that hides 2, 4 or 8 identical requests among similar distractors. The requests might be several poems about tapirs. It then asks the model to return a specific one prefixed with a random string, for example the second. It tests ordering and disambiguation rather than lookup, and its samples run in bins from 4K to 1 million tokens. [LongBench v2](https://arxiv.org/abs/2412.15204) instead uses 503 hard multiple-choice questions over real documents of 8,000 to 2 million words. Human experts with 15 minutes per question reached 53.7%, the best model answering directly reached 50.1%, and a reasoning model reached 57.7%.

For a domain like filings, the most useful evaluation is a small custom one built from the documents actually served. Each question records where its evidence sits, and the set mixes single-fact lookups, cross-section questions such as net debt, aggregations such as total segment revenue across four tables, and comparisons across years whose prior-year column is a built-in distractor. The evaluation moves the same evidence to the start, middle and end of the prompt and pads the same question to 16K, 64K and 128K tokens. That gives an accuracy grid over **evidence depth** and length. Answers are scored for correctness and citation support separately. [Perplexity](/tutorials/llm-fundamentals/language-modeling-and-next-token-prediction/#perplexity) on long documents belongs in the extension stage as a sanity check only, because it can stay flat while retrieval of a specific fact fails. Every extension should also be rerun on the short-context benchmarks it started from, since gaining 128K while losing three points on short tasks is a trade that has to be judged on the actual workload.

## Long document diagnosis
A failure on a long document usually has one of a handful of causes, and each has a check that separates it from the others in minutes. The table maps each symptom to that check and the usual fix, roughly in the order a debugging session should try them.

Each row starts from what is observed, so the left column is where a session enters the table. The first check is chosen to be cheap and to settle one cause on its own. Most take a single rerun or one look at a parsed chunk, and none needs retraining. The rows run from the data toward the model and then to the system around it. The first two are parsing faults. The next two separate reasoning from retrieval, starting with the oracle evidence test of the [effective context length](#effective-context-length) section. The middle four concern how the model handles length and position, and the last two cover long reports and serving. The parsing rows come first because a parsing fault imitates almost every other failure. A model that never received the footnote behaves exactly like a model that cannot reason about exceptions.

| Symptom | First check | Likely cause | Usual fix |
|---|---|---|---|
| Number off by a factor of 1,000 or 1,000,000 | Look at the parsed chunk for the unit | Header unit lost in extraction | Attach header units and footnotes to cells, as in the [document representation](#document-representation) section |
| Answer ignores an exception | Search the chunk record for the footnote text | Footnote split from its table, or summarized away | Section-aware chunking, structured summaries with source links |
| Wrong answer even with the three gold passages | Oracle evidence test on 1,500 tokens | Reasoning or table reading | Better prompt or model, worked examples, domain fine-tuning in [Domain Adaptation](/tutorials/llm-deep-dive/domain-adaptation-and-fine-tuning/) |
| Right with gold passages, wrong with retrieval | Recall of each gold passage in the top results | Retriever misses one hop | Section-level retrieval, query rewriting, rerankers |
| Right on short inputs, garbled past the trained length | Perplexity against position on long text | Rotation angles out of range | YaRN or NTK-aware scaling with continued training |
| Passes needle tests, fails multi-hop at the same length | RULER-style variable tracking at that length | Effective context shorter than the window | Long-dependency training data, retrieval to shorten input |
| Accuracy dips when evidence is mid-prompt | Same question with evidence moved to each end | Lost in the middle | Question before and after the document, reorder passages |
| Fluent output after the cache rolls over, but early facts forgotten | Ask about content older than the window | Sliding or streaming cache evicted it | Retrieval or explicit notes for content that must persist |
| Long report contradicts itself | Diff metric values across sections | Section-wise drift | Fact ledger, deterministic recomputation, coherence checks |
| Requests time out or crowd out other users | Prompt length distribution and cache memory | Full-document prompts on every question | Retrieval first, prefix caching for repeated documents |

The net debt question shows the table in use. A typical case is a deployment that answers 1,530 million instead of 1,390. The error is exactly 140 million, which is the leasing row. So the unit is intact and the first row does not apply, while an ignored exception fits both the second row and the third. The oracle evidence test tells them apart. Given only the three gold passages of about 1,500 tokens, the model answers 1,390, so its reasoning and table reading are sound. Given the same passages inside 90,000 tokens of other filings, it still answers 1,390, so length and distractors are not the cause either. Only the real filing fails, which points back at the document. Searching the parsed text for the footnote shows the debt row as "Leasing 140 95" with no (a) marker, and the footnote text at the bottom of the page with nothing tying it to the row. Attaching the footnote to its cell brings the full-filing answer back to 1,390. The [document representation](#document-representation) section describes how. The question then joins the custom evaluation set with its evidence depths recorded, so a later parser change that drops footnotes again shows up as a failed question before it reaches users.

The design choice follows the same logic. Retrieval over well-built chunk records is cheaper and easier to audit when questions need a few findable passages. A long-context model with a measured effective context above the document length earns its cost when evidence is scattered or linked by reference, ideally fed whole sections rather than the whole filing. Hierarchical processing with source-linked records scales furthest when documents exceed any window. The evaluation from the [long context evaluation](#long-context-evaluation) section, run on the actual documents at the actual lengths, decides between them.
